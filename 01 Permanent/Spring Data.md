# Spring Data

---

## 📄 본문
### JDBC
어플리케이션 서버와 DB의 사용과정은 커넥션을 연결하고 SQL을 전달하고 결과를 응답하는 과정이다. 문제는 각각의 데이터베이스마다 커넥션을 연결하는 방법, SQL을 전달하는 방법, 결과를 받는 방법이 모두 다르다. 이런 문제를 해결하기 위해 JDBC라는 자바 표준이 등장했습니다. JDBC 표준 인터페이스를 통해 개발자는 이 표준 인터페이스만 사용해서 개발하면 됩니다.

#### point
##### jdbcTemplate
JDBC로 개발할 때 발생하는 반복을 대부분 해결해준다. 트랜젝션을 위한 커텍션 동기화, 예외 시 스프링 예외 변환기도 자동으로 실행해준다. jdbcTemplate는 템플릿 콜백 패턴을 사용해서, JDBC의 반복 작업을 대신 처리해준다. SQL Mapper이고 SQL을 작성하고 전달한 파라미터를 정의하고, 응답 값을 매핑하기만 하면된다.

### SQL Mapper
JDBC를 편리하게 사용하도록 도와준다. SQL 응답 결과를 객체로 편리하게 변환해주며, JDBC의 반복 코드를 제거해준다. 개발자가 모든 SQL을 직접 작성해야한다는 단점을 가지고 있다. 대표 기술로는 JdbcTemplate, MyBatis가 있다.

#### point
##### Mybatis
JdbcTemplate보다 더 많은 기능을 제공하는 SQLMapper이다. SQL을 XML에 편리하게 작성할 수 있고, 동적 쿼리를 매우 편리하게 작성 할 수 있다는 점이다. MyBatis가 제공하는 최고의 기능이자, MyBatis를 사용하는 이유는 바로 동적 SQL 기능 때문이다.

##### @Mapper
Mybatis에서 해당 어노테이션이 있어야지 MyBatis에서 인식할 수 있다. 인터페이스에서 메서드를 호출하면 XML의 해당 SQL을 실행하고 결과를 돌려준다.

### ORM
ORM은 객체를 관계형 데이터베이스 테이블과 매핑해주는 기술이다. 이 기술 덕분에 개발자는 반복적인 SQL을 직접 작성하지 않고 ORM 기술이 개발자 대신 SQL을 동적으로 만들어 실행해준다. 추가로 각각의 데이터베이스마다 다른 SQL을 사용하는 문제도 중간에서 해결해준다. 대표기술로는 JPA, 하이버네이트, 이클립스링크가 있다. JPA는 자바 진영의 ORM 표준 인터페이스이고, 이것을 구현한 것으로 하이버네이트와 이클립스 링크 등의 구현 기술이있다.

#### point
##### JPA
JPA는 ORM을 위해서 자바에서 제공하는 API이며, 자바 객체와 DB 테이블을 매핑해준다. 구현체로는 하이버네이트가 대표적이다.

##### ORM vs JPA vs Hibernate
비즈니스 로직에 집중하고 객체중심의 개발을 할 수 있게 된다. 그리고 메소드를 호출하는 것만으로도 쿼리를 수행하기에 생산성이 향상되고, 유지보수 비용이 줄어든다. 단점으로는 직접 SQL을 호출하는 것보다 상대적으로 느리며, 복잡한 쿼리는 메소드로 처리하기 힘들다는 점이다.

##### @Repository
- `@Repository` 가 붙은 클래스는 **컴포넌트 스캔의 대상**이 된다.
- `@Repository` 가 붙은 클래스는 **예외 변환 AOP의 적용 대상**이 된다.
    - 스프링과 JPA를 함께 사용하는 경우 스프링은 JPA 예외 변환기 ( `PersistenceExceptionTranslator` )를 등록한다.
    - **예외 변환 AOP 프록시**는 **JPA 관련 예외가 발생하면 JPA 예외 변환기를 통해 발생한 예외를 스프링 데이터 접근 예외로 변환**한다.

### 커넥션 풀
커넥션을 새로 만드는것은 시간이 많이 소모되는 일이다. 이것을 해결하기 위해 커넥션을 미리 생성해두고 사용하는 방식을 사용하는데 이것을 "커넥션 풀"이라고 한다. 어플리케이션을 시작하는 시점에 커넥션 풀은 필요한 만큼 커넥션을 미리 확보해서 풀에 저장한다. 기본 값은 보통 10개이며, 대표적인 커넥션 풀로는 오픈소스 HikariCP가 있다.

#### point
##### 커넥션을 얻는 방법
DriverManager를 통해 얻는 방법은 커넥션을 획득할 때 마다 URL, USERNAME, PASSWORD 같은 파라미터를 계속 전달하면서 얻을 수 있는 방식이다.
DataSource를 사용하는 방식은 처음 객체를 생성할 때만 필욯나 파라미터를 넘기고 나중에는 커넥션 메소드만 호출하면 얻을 수 있는 방식이다.

##### 히카리풀, DB 커넥션

### @Transactional
스프링에서 반복적인 트랜잭션 로직을 해결하기 위해 트랜젝션 템플릿을 적용하여 해결했었지만, 서비스 계층에 부가적인 코드가 추가되기에 순수한 비즈니스 로직만 남길 수 없는 문제가 있었다. 이 문제를 해결하기 위해 스프링에서는 트랜잭션 AOP를 제공하게 되었는데, 이것이 @Transactional이다.

어노테이션을 메소드나 클래스에 달아주면 AOP를 통해서 Target이 상속하고 있는 인터페이스나 Target 객체를 상속한 프록시 객체가 생성된다. 프록시 객체의 메서드를 호출하면 Target 메서드 전 후로 트랜젝션 처리를 수행한다.

#### point
##### ACID
###### 원자성
트랜젝션 내에 작업들이 하나의 작업인 것 처럼 모두 성공하거나 모두 실패해야된다.

###### 일관성
모든 트랜젝션은 일관성 있는 데이터베이스 상태를 유지해야한다.
(예: 데이터베이스에서 정한 무결성 제약조건을 항상 만족시킨다.)

###### 격리성
동시에 실행되는 트랜젝션들이 서로에게 영향을 미치지 않도록 격리한다. 즉 동시에 같은 데이터를 수정하지 못하도록한다.

###### 영속성
트랜젝션을 성공적으로 끝내면 그 결과가 항상 기록되어야한다. 즉, 중간에 시스템에 문제가 발생해도 데이터베이스 로그 등을 사용해서 성공한 트랜잭션 내용을 복구한다.

##### 격리 수준
- READ UNCOMMITED(커밋되지 않은 읽기)
- READ COMMITTED(커밋된 읽기)
- REPEATABLE READ(반복 가능한 읽기)
- SERIALIZABLE(직렬화 가능)
기본 값은 데이터베이스에서 설정한 트랜잭션 격리 수준을 사용한다. 즉, 대부분 데이터베이스에서 설정한 기준을 따른다. 어플리케이션 개발자가 트랜잭션 격리 수준을 직접 지정하는 경우는 드물다.

##### 인터페이스의 @Transactional
인터페이스에 @Transactional을 사용하는 것은 스프링 공식 메뉴얼에서 권장하지 않는 방식이다. AOP를 적용하는 방식에 따라서 인터페이스에 어노테이션을 두면 AOP가 적용이 되지 않는 경우도 있기 때문이다. 가급적 구체 클래스에 @Transactional을 사용하자.

##### public에만 트랜잭션이 적용된다.
클래스 레벨에 트랜잭션을 적용하면 모든 메서드에 트랜젝션이 걸릴 수 있다. 의도 하지 않는 곳까지 트랜젝션이 과도하게 적용이 될 수 있다는것이고 트랜잭션은 주로 비즈니스 로직의 시작점에 걸기 때문에 대부분 외부에 열어준 곳을 시작점으로 사용한다. 따라서 public 메서드에만 트랜젝션이 적용된다.

##### @Transactional(readOnly = false)
읽기 전용 트랜젝션이 생성된다. 성능 향상이 일부있다. JdbcTemplate 같은 경우에는 읽기에서 변경 기능을 실행하면 예외를 던진다. JPA 같은 경우에는 트랜잭션 커밋 시점에 플러시를 호출하지 않는다. 추가적으로 변경이 필요없으니 더티 체킹 즉 변경 감지를 위한 스냅샷 객체도 생성하지 않는다.
