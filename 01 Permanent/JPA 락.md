# JPA 락

---

## 📄 본문

### 낙관적 락 (Optimistic Lock)

==대부분의 경우 데이터 충돌이 발생하지 않을 것==이라는 관점으로 동시성을 제어하는 방식이다.

JPA에서는 `@Version`을 사용하여 엔티티의 버전을 관리하며, 데이터 수정 시 버전이 일치하지 않으면 예외가 발생한다.

- 별도의 비관적 DB 락을 선점하지 않아 동시 처리에 유리하다.
- 충돌이 적고 읽기 작업이 많은 환경에 적합하다.
- 충돌이 빈번하면 예외 처리 및 재시도로 인해 성능이 저하될 수 있다.

#### **사용 예시**

```java
@Version
private Long version;
```

Hibernate는 일반적으로 다음과 같은 SQL을 실행한다.

```sql
UPDATE bid
SET cost = 100000,
    version = 2
WHERE id = 1
  AND version = 1;
```

수정된 행이 0개라면 버전 충돌로 판단하여 낙관적 락 예외가 발생할 수 있다.

### 비관적 락 (Pessimistic Lock)

==데이터 충돌이 발생할 가능성이 높다==는 관점으로 동시성을 제어하는 방식이다.

JPA에서는 `@Lock`을 사용하여 DB 수준의 락을 획득하며, 다른 트랜잭션의 충돌하는 데이터 접근을 제한한다.

- 동시 수정으로 인한 데이터 충돌을 사전에 제어할 수 있다.
- 충돌이 빈번하고 데이터 정합성이 중요한 환경에 적합하다.
- 락 대기로 인한 성능 저하 및 데드락 발생 가능성이 존재한다.

#### 사용 예시

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT b FROM Bid b WHERE b.id = :id")
Optional<Bid> findByIdWithLock(@Param("id") Long id);
```

MySQL에서는 일반적으로 다음과 같은 SQL을 실행한다.

```sql
SELECT *
FROM bid
WHERE id = 1
FOR UPDATE;
```

해당 행에 배타적 락을 획득하여 다른 트랜잭션의 충돌하는 수정 작업을 대기시킨다.

### 낙관적 락과 비관적 락 비교

|**구분**|**낙관적 락**|**비관적 락**|
|---|---|---|
|관점|충돌이 적을 것으로 예상|충돌 가능성이 높음|
|JPA 적용|`@Version`|`@Lock`|
|동작 방식|버전 검증|DB 락 획득|
|충돌 처리|예외 발생|대기 또는 예외|
|성능 부담|충돌이 적으면 낮음|락 대기 비용 발생|
|적합한 상황|충돌이 적은 환경|충돌이 빈번한 환경|

핵심 차이
- 낙관적 락은 데이터 충돌을 감지하는 방식이다.
- 비관적 락은 데이터 충돌이 발생할 수 있는 접근을 사전에 제어하는 방식이다.
