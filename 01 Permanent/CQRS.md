# CQRS
---

## 📄 본문

### CQRS란?
Command and Query Responsibility Segregation 데이터 저장소에 대한 읽기와 업데이트 작업에 대한 책임을 분리하는 패턴을 의미합니다. 명령(Command)을 처리하는 책임과 조회(Query)를 처리하는 책임을 분리하는 패턴을 말합니다.

![[attachments/screenshots/CQRS_IMAGE.png]]

### CQRS 규칙

1. 읽기와 쓰기를 각각 다른 모델로 분리합니다. 명령(Command)을 통해서 데이터를 쓰고, 쿼리(Query)를 통해 데이터를 읽습니다.
2. 명령은 데이터 중심적이 아니라, 비즈니스 업무(도메인) 중심이 되어야 합니다. 예를 들면, “호텔룸의 상태를 ‘예약됨’으로 변경한다”가 아니라, “호텔룸 예약”과 같이 생성되어야 합니다.
3. 명령은 보통 동기적으로 처리하기 보다는 큐에 쌓은 후에 비동기적으로 수행됩니다. 쿼리는 DB Table의 Row를 결코 수정하지 않습니다. 어떤 도메인 로직도 캡슐화하지 않은 DTO만 반환합니다.

이렇게 Read/Write 모델들은 서로 격리 될 수 있습니다. 이 처럼 모델을 분리하는 것은 Application 디자인과 구현을 더욱 간단하게 만들어 줍니다. 하지만, CQRS 코드는 ORM Tools을 통해 DB 스키마로부터 자동으로 생성되도록 할 수는 없는 단점을 가지고 있습니다.


### CQRS의 장단점

#### 장점

1. Application의 퍼포먼스, 확장성, 보안성을 극대화 할 수 있습니다.
2. 시스템의 유연성을 바탕으로 시간이 지나면서 지속적으로 시스템을 발전 시켜 나갈 수 있습니다.
3. 여러 요청으로부터 들어온 복수의 업데이트 명령들에 대한 충돌도 방지할 수 있습니다.

#### 단점

1. 설계 단계에서 고려해야 할 문제들이 많습니다. 멱등한 이벤트 발행 - 중복 이벤트를 제거하고 멱등한 이벤트만 발행해야 합니다. 이벤트 ID를 기록해 중복된 이벤트가 발행되지 않도록 해야 합니다.
2. 아키텍처가 복잡해집니다. 여러 종류의 DB를 사용하게 되고, 분리되는 만큼 쿼리 서비스를 작성해야하는 단점이 있습니다.
3. 일시적으로 일관성이 깨질 수 있습니다. 데이터 쓰기 관련 이벤트 처리 도중에 데이터의 일관성이 깨질 수 있습니다.
