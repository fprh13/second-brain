# k6

---

## 📄 본문

### 개념

**k6는 Grafana Labs에서 개발하는 오픈소스 성능 및 부하 테스트 도구**로, JavaScript 기반의 테스트 스크립트를 통해 가상의 트래픽을 발생시키고 시스템의 처리 성능과 안정성을 검증한다.

동시 사용자 수, 초당 요청 처리량, 응답 시간, 오류율 등의 지표를 수집하여 서비스가 특정 부하에서 정상적으로 동작하는지 확인할 수 있다.

단순히 서버에 많은 요청을 보내는 것이 아니라, **성능 목표를 정의하고 부하를 발생시킨 뒤 측정 결과를 분석하여 병목과 개선 효과를 검증하는 것**이 주된 목적이다.

#### 주요 특징

- JavaScript 기반 테스트 스크립트 작성
    
- CLI를 통한 실행 및 자동화
    
- VU(Virtual User)를 활용한 사용자 부하 생성
    
- 응답 시간, 처리량, 오류율 등 다양한 성능 지표 수집
    
- Threshold를 통한 성능 통과 및 실패 기준 정의
    
- 내장 Web Dashboard와 HTML 보고서 지원
    
- CI/CD 파이프라인 연동 가능
    
- HTTP, WebSocket, gRPC 등 다양한 프로토콜 지원
    
- 로컬, Docker, Kubernetes, 클라우드 환경에서 실행 가능
    

Docker 또는 Kubernetes 설치는 필수가 아니며, 로컬 환경에서도 독립적으로 실행할 수 있다.

### k6와 다른 부하 테스트 도구 비교

| 도구       | 특징                                      | 적합한 환경                 |
| -------- | --------------------------------------- | ---------------------- |
| nGrinder | Groovy 기반, Controller/Agent 구조, 웹 UI 제공 | 기존 nGrinder 운영 환경      |
| JMeter   | GUI 기반 테스트 작성, 다양한 프로토콜과 확장 기능          | 복잡한 테스트 및 기존 JMeter 환경 |
| k6       | JavaScript 기반, CLI 중심, 자동화에 유리          | 신규 API 성능 테스트 및 CI/CD  |

k6는 성능 테스트를 코드로 관리하기 편리하며, 백엔드 프로젝트와 함께 버전 관리하고 자동화하는 데 적합하다.

### k6로 테스트할 수 있는 대상

| 대상          | 테스트 가능 내용                                 |
| ----------- | ----------------------------------------- |
| REST API    | 요청 처리량, 응답 시간, 오류율                        |
| GraphQL     | Query 및 Mutation 처리 성능                    |
| WebSocket   | 연결, 메시지 송수신, 지연 시간                        |
| gRPC        | RPC 요청 처리 성능                              |
| 인증 API      | 로그인, JWT 인증 API 처리 성능                     |
| 브라우저        | 실제 브라우저 기반 사용자 동작 및 성능                    |
| MySQL / JPA | DB 조회 API를 통한 간접 성능 측정                    |
| Redis       | 캐시 적용 전후 API 성능 비교                        |
| RabbitMQ    | HTTP 기반 비동기 작업의 종단 간 성능 검증, 필요 시 확장 기능 활용 |

k6는 기본적으로 **부하 발생 및 외부 관점의 성능 측정 도구**이다.

따라서 JVM GC, DB 내부 쿼리 실행 시간, CPU 사용률 등을 직접 분석하려면 다음과 같은 도구를 함께 사용한다.

- Spring Boot Actuator / Micrometer: 애플리케이션 지표
    
- Prometheus: 시계열 지표 수집 및 저장
    
- Grafana: 지표 시각화
    
- MySQL EXPLAIN ANALYZE: SQL 실행 계획과 실행 시간
    
- MySQL Performance Schema: DB 내부 성능 분석

### 주요 용어

|용어|설명|
|---|---|
|VU (Virtual User)|사용자 행동을 모방하는 가상 사용자|
|Iteration|테스트 함수를 한 번 실행하는 단위|
|Scenario|사용자 실행 함수와 부하 패턴을 정의한 시나리오|
|Executor|VU 또는 Iteration 실행 방식을 제어하는 구성요소|
|RPS|Requests Per Second, 초당 HTTP 요청 수|
|TPS|Transactions Per Second, 초당 트랜잭션 처리 수|
|Throughput|단위 시간당 처리한 작업량|
|Latency|요청 처리 과정에서 발생하는 지연 시간|
|Threshold|성능 테스트의 통과 및 실패 기준|
|Check|API 응답과 비즈니스 결과를 검증하는 조건|
|Tag|API 또는 시나리오별 지표를 구분하는 식별값|
|Baseline|개선 효과를 비교하기 위한 기준 성능|
|Bottleneck|전체 시스템의 처리 성능을 제한하는 병목|

#### VU와 RPS의 차이

VU는 동시에 실행되는 가상 사용자 수이고, RPS는 실제 발생한 초당 HTTP 요청 수이다.

동일한 VU 수라도 요청 응답 시간, 대기 시간, 사용자 행동에 따라 RPS는 달라질 수 있다.

또한 Iteration 하나에서 HTTP 요청을 여러 번 수행할 수 있으므로 Iteration 처리량이 반드시 RPS와 동일한 것은 아니다.

### 성능 테스트 종류

|종류|목적|주요 확인 지표|
|---|---|---|
|Smoke Test|적은 부하로 기본 동작 확인|상태 코드, Check, 오류율|
|Load Test|예상되는 일반 트래픽 처리 성능 검증|RPS, P95, 오류율|
|Stress Test|일반적인 처리 수준을 넘어서는 부하 검증|처리량 포화, 지연, 오류율|
|Spike Test|갑작스러운 트래픽 증가에 대한 대응 검증|오류율, 응답 지연, 회복 시간|
|Soak Test|장시간 부하에서 안정성 검증|메모리, GC, 응답 시간 변화|
|Breakpoint Test|시스템이 감당할 수 있는 한계 탐색|최대 처리량, 실패 시작 지점|

#### 학습 권장 순서

1. Smoke Test
    
2. Load Test
    
3. Stress Test
    
4. Spike Test
    
5. Soak Test
    
6. Breakpoint Test
    

각 테스트는 목적이 다르므로 모든 테스트에서 동일한 부하나 Threshold를 사용할 필요는 없다.

예를 들어 Load Test에서는 정상 트래픽에서 P95가 500ms 이하인지 검증할 수 있지만, Stress Test에서는 부하 증가에 따른 성능 저하와 시스템 복구 특성을 분석하는 것이 목적일 수 있다.

### Executor 종류

|Executor|역할|
|---|---|
|`shared-iterations`|전체 VU가 정해진 Iteration 수를 나누어 실행|
|`per-vu-iterations`|각 VU가 정해진 Iteration 수를 실행|
|`constant-vus`|일정한 VU 수를 유지|
|`ramping-vus`|시간에 따라 VU 수를 변경|
|`constant-arrival-rate`|일정한 비율로 Iteration 시작|
|`ramping-arrival-rate`|시간에 따라 Iteration 시작 비율을 변경|

#### VU 기반 테스트

```
export const options = {
  vus: 10,
  duration: '1m',
};
```

10명의 가상 사용자가 1분 동안 테스트 함수를 반복 실행한다.

동시 사용자 수가 고정된 상태에서 실제 처리량과 응답 시간을 측정할 수 있다.

#### Arrival Rate 기반 테스트

```
export const options = {
  scenarios: {
    search: {
      executor: 'constant-arrival-rate',
      rate: 20,
      timeUnit: '1s',
      duration: '3m',
      preAllocatedVUs: 20,
      maxVUs: 40,
    },
  },
};
```

초당 20번의 Iteration 시작을 목표로 한다.

Iteration마다 HTTP 요청을 한 번만 수행한다면 목표 RPS와 대응시킬 수 있다.

단, 충분한 VU가 없거나 부하 발생기가 감당하지 못한다면 실제 목표 부하를 유지하지 못할 수 있다.

**동시 사용자 수준을 검증할 때는 VU 기반, 일정한 요청 유입량을 검증할 때는 Arrival Rate 기반을 고려한다.**

### 핵심 성능 지표

|k6 지표|의미|
|---|---|
|`http_reqs`|전체 HTTP 요청 수 및 평균 초당 요청 수|
|`http_req_duration`|HTTP 요청의 응답 시간|
|`http_req_waiting`|첫 응답 바이트까지 기다린 시간(TTFB)|
|`http_req_failed`|실패로 분류된 HTTP 요청의 비율|
|`checks`|검증 조건의 성공률|
|`iterations`|실행한 Iteration 수|
|`iteration_duration`|Iteration 전체 소요 시간|
|`vus`|현재 활성 가상 사용자 수|
|`vus_max`|확보된 최대 VU 수|
|`dropped_iterations`|예정되었지만 시작하지 못한 Iteration 수|

#### 응답 시간의 통계

|지표|의미|
|---|---|
|Average|평균 응답 시간|
|Median / P50|전체 요청의 50%가 해당 시간 이하|
|P90|전체 요청의 90%가 해당 시간 이하|
|P95|전체 요청의 95%가 해당 시간 이하|
|P99|전체 요청의 99%가 해당 시간 이하|
|Max|가장 오래 걸린 응답 시간|

평균 응답 시간만으로 성능을 판단하면 일부 느린 요청을 놓칠 수 있으므로 **P95와 P99를 함께 확인하는 것이 중요하다.**

#### 결과 해석 방법

|관측 결과|검토할 내용|
|---|---|
|RPS 증가, 응답 시간 유지|부하 증가에도 안정적으로 처리되는지 확인|
|RPS 정체, P95 증가|서버 포화 또는 병목 가능성|
|P95와 P99 차이가 큼|일부 요청의 심한 지연 가능성|
|오류율 증가|서버 오류, 타임아웃, 리소스 부족 등|
|`dropped_iterations` 증가|부하 생성기의 VU 부족 및 처리 능력 확인|
|장시간 실행 시 응답 지연 증가|메모리, GC, DB 연결 및 리소스 누적 확인|

k6 지표만으로 병목 원인을 확정하지 않는다.

CPU, JVM GC, DB 커넥션 풀, Slow Query 등의 정보를 함께 확인해야 원인을 구체적으로 분석할 수 있다.

### Threshold와 Check

#### Threshold

성능 테스트의 성공 및 실패 기준을 정의한다.

```
export const options = {
  thresholds: {
    http_req_duration: ['p(95)<500'],
    http_req_failed: ['rate<0.01'],
    checks: ['rate>0.99'],
  },
};
```

- P95 응답 시간 500ms 미만
    
- HTTP 요청 실패율 1% 미만
    
- Check 성공률 99% 초과
    

위 기준은 학습용 예시이며, 실제로는 서비스의 성능 요구사항을 바탕으로 설정한다.

Threshold를 충족하지 못하면 k6는 실패 상태로 종료하므로 CI/CD에서 성능 검증 결과로 활용할 수 있다.

#### Check

API 응답의 정상 여부를 검증한다.

```
check(response, {
  'HTTP 200': (r) => r.status === 200,
});
```

HTTP 상태 코드가 200이어도 비즈니스 응답이 실패할 수 있으므로 필요하다면 응답 본문까지 검증한다.

`http_req_failed`와 `checks`는 서로 다른 지표다.

### 설치 및 기본 사용법

#### macOS 설치

```
brew install k6
```

```
k6 version
```

#### 기본 스크립트 작성

`health.smoke.js`

```
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  vus: 5,
  duration: '30s',

  thresholds: {
    http_req_duration: ['p(95)<500'],
    http_req_failed: ['rate<0.01'],
  },
};

export default function () {
  const baseUrl = __ENV.BASE_URL || 'http://localhost:8080';

  const response = http.get(
    `${baseUrl}/actuator/health`
  );

  check(response, {
    'HTTP 200': (r) => r.status === 200,
  });

  sleep(1);
}
```

Spring Boot Actuator의 Health 엔드포인트가 활성화된 환경을 가정한 예시이다.

#### 테스트 실행

```
k6 run health.smoke.js
```

VU와 시간을 CLI에서 지정할 수도 있다.

```
k6 run --vus 10 --duration 1m health.smoke.js
```

환경변수를 전달하려면 다음과 같이 사용한다.

```
k6 run \
  -e BASE_URL=http://localhost:8080 \
  health.smoke.js
```

### Web Dashboard 사용법

k6는 별도의 Grafana 서버 없이 내장 Web Dashboard를 사용할 수 있다.

#### 실행

```
K6_WEB_DASHBOARD=true k6 run health.smoke.js
```

기본 주소:

`http://localhost:5665`

#### 주요 화면

|화면|용도|
|---|---|
|Overview|요청량, 응답 시간, 실패율, VU 등|
|Timings|HTTP 요청 단계별 소요 시간|
|Summary|테스트 전체 결과의 통계|
|Report|HTML 성능 보고서 생성|

#### 지표 확인 순서

1. **실제 부하 확인:** VU 또는 목표 RPS가 의도대로 적용되었는지 확인
    
2. **오류 확인:** HTTP 실패율, Check 실패 여부 확인
    
3. **응답 시간 확인:** 평균, P95, P99 확인
    
4. **처리량 확인:** 부하가 증가했을 때 RPS 변화 분석
    
5. **시간별 그래프 확인:** 부하 증가 시점과 응답 지연 발생 시점 비교
    
6. **서버 자원 확인:** CPU, 메모리, GC, DB 지표와 비교
    
7. **Threshold 확인:** 정의한 성능 기준을 통과했는지 판단

```
K6_WEB_DASHBOARD=true \
```

보고서에는 테스트 결과의 통계와 그래프를 남길 수 있다.

대시보드의 집계 결과만으로 원인을 단정하지 말고, 시간별 지표와 애플리케이션 모니터링 정보를 함께 분석하는 것이 좋다.

### 프로젝트 관리 방식

#### 백엔드 레포지토리에서 관리

개인 프로젝트 또는 단일 Spring Boot 서비스라면 백엔드 레포지토리 내부에서 함께 관리하는 방식을 추천한다.

장점:

- API 변경과 성능 테스트 코드를 같은 버전으로 관리
    
- 기존 Git 브랜치 및 PR 워크플로우 활용
    
- CI/CD 연동이 쉬움
    
- 테스트 대상 API와 관련 코드를 함께 추적
    
- 초기 설정과 유지보수 부담이 적음
    

#### 독립 레포지토리에서 관리

여러 서비스를 통합 테스트하거나 별도의 성능 테스트 인프라를 운영할 때 고려한다.

적합한 사례:

- 마이크로서비스 여러 개의 통합 성능 테스트
    
- 여러 팀이 동일한 부하 테스트 환경 공유
    
- 별도 성능 테스트 조직 운영
    
- 테스트 코드 배포 주기가 백엔드와 다른 경우
    
- 독립된 CI/CD 및 대규모 부하 발생 환경 운영
    

**처음에는 백엔드 레포지토리 내부에서 시작하고, 분리가 필요한 상황이 발생했을 때 독립시키는 것이 관리하기 편하다.**

#### 디렉터리별 역할

|디렉터리|관리 대상|
|---|---|
|`config/`|실행 환경, Threshold, 부하 설정|
|`api/`|API별 HTTP 요청 코드|
|`flows/`|여러 API를 조합한 사용자 행동|
|`suites/`|실제 실행 가능한 성능 테스트|
|`data/`|테스트용 검색어, ID 등의 데이터|
|`results/`|실행 결과 및 HTML 보고서|
|`docs/performance/`|성능 테스트 설계 및 개선 보고서|

이 구조는 k6의 강제 규칙이 아니라 프로젝트에서 사용할 수 있는 권장 관례이다.

#### 핵심 설계 원칙

**API 호출 로직, 사용자 행동, 부하 설정을 분리한다.**

예를 들어 동일한 검색 API를 Smoke, Load, Stress 테스트에서 사용한다면 HTTP 요청 코드를 반복해서 작성할 필요가 없다.

- `api/`: 실제 API 호출
    
- `flows/`: 호출 순서와 검증
    
- `config/`: 부하 조건 및 공통 설정
    
- `suites/`: 테스트 종류별 실행 진입점
    

API가 추가되어도 기존 공통 코드를 재사용할 수 있고, 부하 조건만 변경하여 여러 테스트를 수행할 수 있다.

다만 초기에는 지나친 추상화를 피하고, 중복되는 코드가 생기기 시작할 때 분리해도 충분하다.

### 파일 명명 관례

k6에서 파일명에 대한 강제 규칙은 없지만, 일관된 규칙을 정해 관리하는 것이 좋다.

#### 테스트 파일

추천 형식:

`<대상>.<테스트 종류>.js`

|파일명|역할|
|---|---|
|`search.smoke.js`|검색 API 기본 동작 검증|
|`search.load.js`|검색 API 일반 부하 검증|
|`search.stress.js`|검색 API 높은 부하 검증|
|`search.spike.js`|검색 API 순간 부하 검증|
|`search.soak.js`|검색 API 장시간 안정성 검증|
|`browse.load.js`|사용자 탐색 흐름 부하 테스트|

#### 공통 코드

|파일명|역할|
|---|---|
|`anime.api.js`|애니메이션 API 요청 모음|
|`auth.api.js`|로그인 및 인증 API 요청 모음|
|`env.js`|환경변수 및 실행 환경|
|`thresholds.js`|공통 성능 기준|
|`workloads.js`|부하 테스트 프로파일|

#### 명명 규칙 가이드

- 디렉터리는 기능 또는 도메인 기준으로 구분
    
- 테스트 파일은 테스트 대상과 종류를 표현
    
- 파일명은 소문자와 하이픈을 기본으로 사용
    
- `.smoke.js`, `.load.js`처럼 테스트 종류를 접미사로 사용
    
- API 호출용 파일에는 `.api.js` 사용
    
- 팀에서 정한 명명 규칙을 일관되게 유지
    

API 엔드포인트마다 반드시 파일 하나를 만들 필요는 없다.

여러 API를 조합한 하나의 사용자 시나리오라면 해당 시나리오를 대표하는 파일명으로 관리할 수 있다.

### 공통 코드 재사용 예시

#### 환경 설정

`config/env.js`

```
export const BASE_URL =
  __ENV.BASE_URL || 'http://localhost:8080';
```

#### API 요청 코드

`api/anime.api.js`

```
import http from 'k6/http';
import { BASE_URL } from '../config/env.js';

export function searchAnimes(keyword) {
  const url =
    `${BASE_URL}/api/animes?keyword=${encodeURIComponent(keyword)}&size=20`;

  return http.get(url, {
    tags: {
      name: 'GET /api/animes',
      endpoint: 'anime_search',
    },
  });
}
```

Tag를 지정하면 동일한 API의 요청을 그룹화하여 지표를 분석하기 쉬워진다.

검색어와 같은 동적 파라미터가 달라져도 정규화된 요청 이름을 사용하면 집계가 편리하다.

#### 사용자 행동 정의

`flows/browse-animes.js`

```
import { check } from 'k6';
import { searchAnimes } from '../api/anime.api.js';

export function browseAnimes() {
  const response = searchAnimes('사랑');

  check(
    response,
    {
      '검색 API 성공': (r) => r.status === 200,
    },
    {
      endpoint: 'anime_search',
    }
  );
}
```

#### 부하 조건 정의

`config/workloads.js`

```
export const workloads = {
  smoke: {
    executor: 'per-vu-iterations',
    vus: 1,
    iterations: 2,
    maxDuration: '30s',
  },

  load: {
    executor: 'constant-arrival-rate',
    rate: 20,
    timeUnit: '1s',
    duration: '3m',
    preAllocatedVUs: 20,
    maxVUs: 40,
  },
};
```

#### Smoke Test

`suites/anime/search.smoke.js`

```
import { browseAnimes } from '../../flows/browse-animes.js';
import { workloads } from '../../config/workloads.js';

export const options = {
  scenarios: {
    anime_search: workloads.smoke,
  },
  thresholds: {
    'checks{endpoint:anime_search}': ['rate==1'],
  },
};

export default function () {
  browseAnimes();
}
```

#### Load Test

`suites/anime/search.load.js`

```
import { browseAnimes } from '../../flows/browse-animes.js';
import { workloads } from '../../config/workloads.js';

export const options = {
  scenarios: {
    anime_search: workloads.load,
  },
  thresholds: {
    'http_req_duration{endpoint:anime_search}': [
      'p(95)<500',
    ],
    'http_req_failed{endpoint:anime_search}': [
      'rate<0.01',
    ],
    dropped_iterations: ['count==0'],
  },
};

export default function () {
  browseAnimes();
}
```

실행할 때 테스트 파일만 변경하면 된다.

```
k6 run tests/performance/suites/anime/search.smoke.js
```

```
k6 run tests/performance/suites/anime/search.load.js
```

이후 Stress Test를 추가할 때도 API 호출 로직은 재사용하고 실행 설정만 확장할 수 있다.

### 테스트 데이터 관리

부하 테스트에서는 테스트 데이터에 따라 성능 결과가 크게 달라질 수 있다.

예를 들어 검색어마다 DB에서 조회되는 데이터 수가 다르면 동일한 API라도 응답 시간이 달라질 수 있다.

#### 관리 원칙

- 테스트 데이터 크기와 분포를 명확하게 기록
    
- 동일 조건 비교에서는 가능한 한 동일한 데이터 사용
    
- 검색어, ID 등의 테스트 입력 데이터를 별도 관리
    
- 성능 비교 시 캐시 상태를 동일하게 유지
    
- 인증이 필요한 테스트는 전용 계정과 토큰 사용
    
- 데이터 생성·수정 API는 테스트 후 정리 방법 마련
    
- 개인정보 및 실제 운영 데이터 사용 주의
    
- 부하 테스트 전용 환경 사용 권장
    

읽기 API와 쓰기 API의 성능 테스트를 구분하는 것이 좋다.

POST/PATCH/DELETE 요청은 테스트 데이터가 계속 변경되므로 데이터 충돌과 누적을 고려해야 한다.

또한 로컬 컴퓨터에서 부하 발생기와 Spring Boot, MySQL을 동시에 실행하면 리소스 경쟁으로 측정 결과가 왜곡될 수 있다.

정확한 성능 비교가 필요한 경우 가능하면 부하 발생기와 테스트 대상 서버를 분리한다.

### 성능 테스트 설계 가이드

실무에서의 성능 테스트는 단순히 많은 요청을 보내는 것보다 목표를 명확하게 정의하는 과정이 중요하다.

#### 1. 테스트 목적 정의

예시:

- 애니메이션 검색 API가 목표 트래픽을 처리할 수 있는가?
    
- DB 인덱스를 추가하면 API 응답 시간이 개선되는가?
    
- 동시 사용자 증가 시 오류 없이 동작하는가?
    
- 트래픽이 급증했을 때 서버가 정상적으로 회복되는가?
    

#### 2. 성능 요구사항 정의

예시:

|항목|목표|
|---|---|
|대상 API|`GET /api/animes`|
|목표 RPS|20|
|테스트 시간|5분|
|P95 응답 시간|500ms 미만|
|HTTP 오류율|1% 미만|
|Dropped Iterations|0|

위 수치는 예시이며, 실제로는 예상 트래픽과 서비스 요구사항에 따라 결정해야 한다.

#### 3. Baseline 측정

최적화 전 API의 기준 성능을 측정한다.

- 평균 응답 시간
    
- P95 / P99
    
- 실제 RPS
    
- HTTP 오류율
    
- CPU 및 메모리
    
- DB 쿼리 실행 시간
    

#### 4. 병목 분석

k6 지표와 애플리케이션 내부 지표를 비교한다.

주요 확인 대상:

- 비효율적인 DB 쿼리
    
- 인덱스 미적용
    
- DB 커넥션 풀 부족
    
- N+1 문제
    
- 불필요한 외부 API 호출
    
- JVM GC 및 메모리 문제
    
- Redis 캐시 미적용 또는 낮은 적중률
    
- 애플리케이션의 CPU 병목
    

#### 5. 성능 개선

발견된 문제에 따라 인덱스 적용, 쿼리 변경, 캐시 도입 등의 개선을 수행한다.

한 번에 여러 요소를 변경하기보다 변경 사항을 구분하여 성능 개선 효과를 확인하는 것이 좋다.

#### 6. 동일 조건 재측정

최적화 전후 비교 시 다음 조건을 최대한 동일하게 유지한다.

- 서버 및 DB 사양
    
- 데이터셋 크기와 내용
    
- 요청 파라미터 분포
    
- 부하 조건
    
- 실행 시간
    
- 캐시 워밍업 조건
    
- 애플리케이션 설정
    
- 테스트 환경
    

가능하면 여러 번 반복하여 일관된 결과인지 확인한다.

### 성능 테스트 보고서 작성

성능 테스트 결과는 단순한 수치 나열보다 목표와 개선 효과가 명확해야 한다.

#### 보고서 구성

|항목|작성 내용|
|---|---|
|테스트 목적|검증하려는 API 및 문제|
|대상 환경|Spring Boot, MySQL, 서버 사양|
|테스트 데이터|데이터 수 및 검색 조건|
|테스트 도구|k6 버전 및 실행 환경|
|테스트 유형|Load, Stress 등의 종류|
|부하 조건|VU 또는 목표 RPS, 실행 시간|
|성공 기준|P95, 오류율, 처리량|
|Baseline|최적화 전 측정 결과|
|개선 사항|쿼리 수정, 인덱스 적용 등|
|개선 결과|최적화 후 측정 결과|
|결론|개선 효과와 남아 있는 문제|

#### 성능 비교 예시

다음은 가상의 측정 결과이다.

|지표|개선 전|개선 후|
|---|---|---|
|P95|620ms|230ms|
|RPS|42|67|
|오류율|0.5%|0.1%|
|평균 응답 시간|180ms|85ms|

P95는 약 62.9% 감소했고, RPS는 약 59.5% 증가했다.

단, 실제 비교에서는 동일한 부하 생성 조건을 유지하고 결과의 재현성을 확인해야 한다. 목표 요청량을 고정하는 테스트에서는 RPS 증가보다 동일 요청량에서의 응답 시간과 오류율 개선을 우선 비교할 수도 있다.

기준 성능과 개선 후 성능을 여러 번 측정하고, 결과의 변동 폭까지 기록하면 신뢰도를 높일 수 있다.

### CI/CD 연동 가이드

k6는 테스트 결과에 따라 성공 또는 실패 상태로 종료할 수 있으므로 CI/CD 파이프라인에 활용할 수 있다.

#### 권장 실행 전략

|테스트|실행 시점|
|---|---|
|Smoke|배포 후 또는 전용 테스트 환경에서 자주 실행|
|Load|릴리스 전 또는 정기 실행|
|Stress|성능 검증이 필요할 때 수동·예약 실행|
|Spike|트래픽 급증 대응 검증 시 실행|
|Soak|전용 환경에서 장시간 예약 실행|
|Breakpoint|격리된 환경에서 계획적으로 실행|

일반적인 PR마다 높은 부하의 테스트를 실행하면 비용과 실행 시간이 증가하고 공유 환경에 영향을 줄 수 있다.

따라서 CI에서는 가벼운 검증을 수행하고, 본격적인 성능 테스트는 별도 환경과 실행 파이프라인으로 분리하는 것이 좋다.

성능 테스트는 기능 단위 테스트를 대체하지 않는다. 응답의 정확성은 별도 테스트로 검증하고, k6에서는 성능과 부하 상황에서의 안정성에 집중한다.

### 학습 로드맵

#### 1단계. 기초 개념 이해

**학습 내용**

- 성능 테스트와 부하 테스트의 목적
    
- VU, RPS, TPS, Iteration의 차이
    
- Average, P95, P99의 의미
    
- Check와 Threshold의 차이
    
- VU 기반과 Arrival Rate 기반의 차이
    

**실습**

Spring Boot에 간단한 GET API를 만들고 k6에서 호출한다.

**완료 기준**

- 각 성능 지표를 설명할 수 있다.
    
- VU와 RPS가 다른 이유를 설명할 수 있다.
    
- k6 결과에서 오류율과 P95를 읽을 수 있다.
    

#### 2단계. 기본 API 부하 테스트

**학습 내용**

- k6 설치 및 실행
    
- `http.get()`, `check()`, `sleep()`
    
- `options` 설정
    
- Smoke 및 Load Test
    
- CLI 결과 확인
    

**실습**

동일한 API에 VU 1명, 5명, 10명, 20명으로 부하를 발생시킨다.

각 실행의 RPS, P95, 오류율을 비교한다.

**완료 기준**

- 직접 테스트 스크립트를 작성할 수 있다.
    
- VU 증가에 따른 성능 변화를 해석할 수 있다.
    

#### 3단계. Web Dashboard 분석

**학습 내용**

- 내장 Web Dashboard 실행
    
- Overview 및 Timings 분석
    
- 시간별 응답 지연 관찰
    
- Threshold 설정
    
- HTML 보고서 저장
    

**실습**

Load Test를 실행하고 Dashboard에서 RPS와 P95 변화를 확인한다.

**완료 기준**

- 성능 테스트 결과를 그래프로 설명할 수 있다.
    
- HTML 보고서를 생성할 수 있다.
    
- 성능 기준의 통과 여부를 판단할 수 있다.
    

#### 4단계. 테스트 종류 및 부하 패턴

**학습 내용**

- Smoke, Load, Stress, Spike, Soak
    
- Executor별 차이
    
- `constant-vus`와 `constant-arrival-rate`
    
- `ramping-vus`와 `ramping-arrival-rate`
    
- `dropped_iterations` 분석
    

**실습**

동일한 API에 일반 부하, 점진적 증가 부하, 급격한 증가 부하를 적용한다.

**완료 기준**

- 테스트 목적에 적합한 Executor를 선택할 수 있다.
    
- 응답 지연과 처리량 포화 현상을 설명할 수 있다.
    

#### 5단계. 프로젝트 구조 및 유지보수

**학습 내용**

- API 호출 코드 분리
    
- 사용자 행동 Flow 구성
    
- 공통 부하 설정 관리
    
- Tag 기반 지표 분류
    
- 파일 명명 규칙
    
- 테스트 결과 및 문서 관리
    

**실습**

검색 API의 Smoke, Load, Stress 테스트를 공통 API 호출 함수로 구성한다.

**완료 기준**

- 중복 코드 없이 테스트를 확장할 수 있다.
    
- 새로운 API 테스트를 일관된 구조로 추가할 수 있다.
    

#### 6단계. 백엔드 성능 최적화

**학습 내용**

- Baseline 측정
    
- MySQL EXPLAIN ANALYZE
    
- 인덱스 최적화
    
- JPA 쿼리 성능 분석
    
- 캐시 적용 전후 비교
    
- 반복 측정 및 개선 효과 분석
    

**실습**

애니메이션 검색 API를 대상으로 인덱스 적용 전후의 API 응답 시간과 처리량을 비교한다.

**완료 기준**

- 성능 병목을 찾기 위한 근거를 수집할 수 있다.
    
- 동일한 테스트 조건에서 개선 효과를 측정할 수 있다.
    
- 성능 개선 보고서를 작성할 수 있다.
    

#### 7단계. 실무형 복합 시나리오

**학습 내용**

- 인증이 필요한 API 테스트
    
- JWT 토큰 처리
    
- API 간 호출 순서 구성
    
- 사용자 행동 기반 시나리오
    
- 읽기/쓰기 트래픽 분리
    
- 테스트 데이터 충돌 및 정리
    

**실습**

로그인 → 애니메이션 검색 → 상세 조회 → 시청 완료 등록 흐름을 구현한다.

**완료 기준**

- 개별 API와 사용자 시나리오 테스트의 차이를 이해한다.
    
- 인증이 필요한 API를 포함한 부하 테스트를 작성할 수 있다.
    

#### 8단계. 모니터링 및 자동화

**학습 내용**

- Spring Boot Actuator
    
- Micrometer
    
- Prometheus
    
- Grafana
    
- DB 모니터링
    
- GitHub Actions를 이용한 테스트 자동화
    

**실습**

k6의 RPS 및 P95 그래프와 Spring Boot의 CPU, JVM, DB 커넥션 지표를 비교한다.

**완료 기준**

- 외부 응답 성능과 내부 리소스 지표를 연결해 분석할 수 있다.
    
- 성능 테스트 결과를 문서화하고 자동으로 검증할 수 있다.

- 산출물: 성능 모니터링 대시보드 및 분석 문서
    

### 실무 적용 시 주의사항

- 운영 서버에 허가 없이 높은 부하를 발생시키지 않는다.
    
- 성능 테스트 환경은 가능한 한 실제 운영 환경과 유사하게 구성한다.
    
- 부하 발생기 자체의 CPU 및 메모리 사용률도 확인한다.
    
- 실제 목표 RPS가 유지되었는지 확인한다.
    
- 네트워크 환경이 결과에 영향을 줄 수 있음을 고려한다.
    
- 테스트 전 워밍업과 캐시 상태를 관리한다.
    
- 성능 비교 시 변경 사항을 명확하게 기록한다.
    
- 테스트를 여러 번 반복하여 결과의 일관성을 확인한다.
    
- 동일한 API라도 요청 데이터 분포에 따라 성능이 달라질 수 있다.
    
- 인증 및 쓰기 API 테스트에서는 계정과 데이터 충돌을 관리한다.
    
- 비동기 API는 HTTP 응답 시간과 실제 작업 완료 시간을 구분한다.
    
- 부하 테스트 결과만으로 병목을 단정하지 않는다.
