# bisect

---

## 📄 본문

### 개념

`git bisect`는 **이진 탐색(Binary Search)을 이용하여 버그가 최초로 발생한 커밋을 찾아내는 Git 명령어**이다.

정상적으로 동작하던 기능에 버그가 발생했을 때, 정상 커밋(Good)과 문제가 발생한 커밋(Bad)을 지정하면 Git이 두 커밋 사이의 이력을 탐색한다.

중간 커밋을 체크아웃하고 정상 여부를 판단하는 과정을 반복하여 문제를 발생시킨 최초 커밋을 찾아낸다.

- `Good`: 버그가 발생하지 않는 정상 커밋
    
- `Bad`: 버그가 발생하는 문제 커밋
    
- `HEAD`: 현재 체크아웃한 커밋
    
- `Binary Search`: 탐색 범위를 반복적으로 절반씩 줄이는 알고리즘
    

### 동작 원리

예를 들어 100개의 커밋 사이에서 문제가 발생했다고 가정한다.

|탐색 방식|최대 확인 횟수(대략)|
|---|---|
|순차 탐색|100회|
|이진 탐색|7회|

```
정상                                      버그 발생
 C1 ─ C2 ─ C3 ─ C4 ─ C5 ─ C6 ─ C7 ─ C8
 GOOD                                   BAD
                       ↓
                중간 커밋 테스트
                       ↓
               Good 또는 Bad 판단
                       ↓
                  탐색 범위 축소
                       ↓
               최초 문제 커밋 발견
```

Git이 중간 커밋으로 이동시키며 개발자는 해당 커밋에서 테스트를 수행하고 정상 여부를 알려준다.

이 과정에서 `detached HEAD` 상태가 되는 것은 정상이다.

### 기본 명령어

|명령어|설명|
|---|---|
|`git bisect start`|Bisect 탐색 시작|
|`git bisect bad`|현재 커밋을 문제 커밋으로 지정|
|`git bisect good`|현재 커밋을 정상 커밋으로 지정|
|`git bisect bad <hash>`|특정 커밋을 문제 커밋으로 지정|
|`git bisect good <hash>`|특정 커밋을 정상 커밋으로 지정|
|`git bisect start <bad> <good>`|정상·문제 커밋을 함께 지정하여 시작|
|`git bisect skip`|테스트할 수 없는 커밋 건너뛰기|
|`git bisect log`|Bisect 진행 기록 확인|
|`git bisect run <command>`|테스트 명령어를 자동 반복 실행|
|`git bisect reset`|탐색 종료 및 기존 체크아웃 상태로 복귀|

### 기본 사용법

#### 1. 정상·문제 커밋 확인

```
git log --oneline
```

버그가 있는 커밋과 정상적으로 동작했던 커밋을 확인한다.

#### 2. Bisect 시작

```
git bisect start
git bisect bad HEAD
git bisect good abc1234
```

또는 한 줄로 실행한다.

```
git bisect start HEAD abc1234
```

- `HEAD`: 현재 버그가 발생하는 커밋
    
- `abc1234`: 정상 동작이 확인된 과거 커밋
    

**실무에서는 정상 커밋 해시 대신 배포 태그를 사용하기도 한다.**

```
git bisect start HEAD v1.2.0
```

#### 3. 테스트 실행

Git이 중간 커밋으로 자동 이동하면 해당 버전에서 테스트를 실행한다.

```
./gradlew test
```

테스트에 성공하여 버그가 없다면:

```
git bisect good
```

테스트에서 동일한 버그가 재현된다면:

```
git bisect bad
```

이 과정을 반복하면 Git이 최초 문제 커밋을 출력한다.

```
abc1234 is the first bad commit
```

단, 테스트 실패가 다른 환경 문제로 발생한 경우에는 잘못된 판단을 내릴 수 있으므로 주의한다.

#### 4. 원인 커밋 분석

```
git show abc1234
git show abc1234 -- path/to/file
```

문제 커밋에서 실제로 변경된 코드를 확인하고 버그의 원인을 분석한다.

#### 5. 탐색 종료

```
git bisect reset
```

기본적으로 Bisect 시작 전의 체크아웃 상태로 돌아간다.

### 자동 탐색: git bisect run

테스트 실행과 Good/Bad 판정을 자동화할 수 있다.

```
git bisect start HEAD abc1234

git bisect run ./gradlew test

git bisect reset
```

테스트 명령어의 종료 코드를 기준으로 자동 판단한다.

|종료 코드|의미|
|---|---|
|`0`|Good|
|`1~127` (125 제외)|Bad|
|`125`|Skip|
|기타|탐색 중단 또는 특수 처리|

**주의사항**

- 테스트가 해당 버그를 실제로 검출해야 한다.
    
- 과거 커밋에서도 테스트를 실행할 수 있어야 한다.
    
- 외부 DB, Redis 등의 테스트 환경을 일정하게 유지해야 한다.
    
- 기존에 존재하던 무관한 테스트 실패를 버그 발생으로 오판하지 않아야 한다.
    
- 불안정한 테스트(Flaky Test)는 탐색 결과의 신뢰도를 떨어뜨린다.
    

테스트 코드가 특정 커밋에 없거나 빌드 자체가 불가능하다면 `git bisect skip`을 사용할 수 있다.

### 백엔드 실무 활용 사례

|상황|활용 방법|
|---|---|
|API 오류|특정 API가 최초로 잘못된 응답을 반환한 커밋 탐색|
|JPA 성능 저하|쿼리 실행 시간이 증가하기 시작한 커밋 탐색|
|동시성 버그|정원 초과, 중복 신청 등이 발생한 최초 커밋 탐색|
|인증 오류|JWT 또는 Spring Security 인증 장애가 발생한 커밋 탐색|
|서버 시작 실패|Spring Boot 애플리케이션이 실행되지 않기 시작한 커밋 탐색|
|데이터 처리 오류|잘못된 계산이나 데이터 변환이 발생한 커밋 탐색|

성능 회귀를 추적하는 경우에는 일정한 부하, 데이터, 실행 환경에서 기준치를 이용해 Good/Bad를 판단해야 한다.

### 다른 Git 명령어와 비교

|명령어|역할|
|---|---|
|`git log`|커밋 이력 확인|
|`git diff`|파일 또는 커밋 간 변경 사항 비교|
|`git blame`|코드의 각 줄을 마지막으로 변경한 커밋 확인|
|`git show`|특정 커밋의 변경 내용 분석|
|`git reflog`|로컬 HEAD 및 참조 이동 기록 확인|
|`git bisect`|버그가 최초로 발생한 커밋 추적|

### 실무 디버깅 흐름

```
버그 발생 확인
      ↓
로그 / 모니터링 / 테스트로 재현
      ↓
git log로 변경 이력 확인
      ↓
정상 커밋과 문제 커밋 지정
      ↓
git bisect로 최초 문제 커밋 탐색
      ↓
git show로 변경 내용 분석
      ↓
원인 파악 및 버그 수정
      ↓
회귀 테스트 추가
      ↓
PR 생성 및 코드 리뷰
```

### 주의사항

- Bisect를 시작하기 전 작업 트리의 변경 사항을 커밋하거나 안전하게 보관한다.
    
- 반드시 정상적으로 동작하는 커밋을 Good으로 지정해야 한다.
    
- 최초 문제 커밋이 발견되어도 해당 커밋의 변경이 실제 근본 원인인지 검증해야 한다.
    
- 여러 버그가 혼재하거나 버그가 발생했다가 사라지는 경우에는 탐색 결과가 부정확할 수 있다.
    
- DB 스키마 및 외부 인프라 변경이 있는 프로젝트는 과거 커밋 실행 환경을 고려해야 한다.
    
- `git bisect`는 커밋을 삭제하거나 수정하지 않는다.
    
- 단순한 장애라면 로그, 테스트, 최근 PR 분석으로 먼저 원인을 파악하는 것이 효율적일 수 있다.
    

### 실무 중요도

**사용 빈도는 낮지만 문제 해결 시 강력한 명령어이다.**

`git diff`, `git log`, `git status`처럼 매일 사용하는 명령어는 아니다.

그러나 커밋이 많이 쌓였고 문제가 처음 발생한 시점을 모르는 상황에서는 수동으로 커밋을 확인하는 것보다 효율적이다.

핵심 명령어는 다음 세 가지를 기억한다.

```
git bisect start <bad> <good>
git bisect good  # 또는 git bisect bad
git bisect reset
```
