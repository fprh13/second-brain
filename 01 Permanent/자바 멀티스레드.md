# 자바 멀티스레드

---

## 📄 본문
### 멀티태스킹
CPU 코어가 프로그램 A의 코드를 0.01초 정도 수행하다가 잠시 멈추고, 프로그램 B의 코드를 0.01초 정도 수행한다. 그리고 다시 프로그램 A의 이전에 실행중인 코드로 돌아가서 0.01초 정도 코드를 수행하는 방식으로 반복 동작한다. 
이렇게 각 프로그램의 실행 시간을 분할해서 마치 동시에 실행되는 것 처럼 하는 기법을 시분할기법이라 한다.

이런 방식을 사용하면 CPU 코어가 하나만 있어도 여러 프로그램이 동시에 실행되는것 처럼 느낄 수 있다.
이렇게 하나의 컴퓨터 시스템이 동시에 여러 작업을 수행하는 능력을 멀티태스킹이라고 한다.

### 멀티프로세싱
컴퓨터 시스템에서 둘 이상의 프로세서(CPU 코어)를 사용하여 여러 작업을 동시에 처리하는 기술을 의미한다. 멀티프로세싱 시스템은 하나의 CPU 코어만을 사용하는 시스템보다 동시에 더 많은 작업을 처리할 수 있다.

#### point
##### 멀티태스킹 vs 멀티프로세싱
멀티프로세싱은 하드웨어 장비의 관점이고, 멀티태스킹은 운영체제 소프트웨어의 관점이다.

##### 스케쥴링
CPU에 어떤 프로그램이 얼마만큼 실행될지는 운영체제가 결정하는데 이것을 스케줄링이라고 한다.
멀티태스킹이란 동시에 여러 작업을 수행하는 것을 말한다. 이를 위해 운영체제는 스케줄링이라는 기법을 사용한다. 스케줄링은 CPU 시간을 여러 작업에 나누어 배분하는 방법이다.

### 포로세스
프로그램을 실행하면 프로세스가 만들어지고 프로그램이 실행된다.
이렇게 운영체제 안에서 실행중인 프로그램을 프로세스라 한다.

#### point
##### 프로세스의 메모리 구성
- 코드섹션: 실행할 프로그램의 코드가 저장되는 부분
- 데이터 섹션: 전역 변수 및 정적 변수가 저장되는 부분
- 힙: 동적으로 할당되는 메모리 영역
- 스택: 메서드 호출 시 생성되는 지역변수, 반환 주소가 저장되는 영역(스레드에 포함)

##### 프로세스의 역할
프로세스는 실행 환경을 제공한다. 여기에는 메모리공간, 파일 핸들, 시스템 자원(네트워크 연결) 등이 포함된다.
이는 프로세스가 컨테이너 역할을 한다는 의미이다.
프로세스 자체는 운영 체제의 스케줄러에 의해 직접 실행되지 않으며 프로세스 내의 스레드가 실행된다. 참고로 1개의 프로세스 안에 하나의 스레드만 실행되는 경우도 있고, 1개의 프로세서 안에 여러 스레드가 실행되는 경우도 있다.

### 스레드
스레드는 프로세스 내에서 실행되는 작업의 단위이다.
프로세스는 하나 이상의 스레드를 반드시 포함한다.
한 프로세스 내에서 여러 스레드가 존재할 수 있으며, 이들은 프로세스가 제공하는 동일한 메모리 공간을 공유한다.
스레드는 프로세스보다 단순하므로 생성 및 관리가 단순하고 가볍다.

#### point
##### 스레드 메모리 구성
- 공유 메모리: 같은 프로세스의 코드 섹션, 데이터 섹션, 힙은 프로세스 안의 모든 스레드가 공유한다.
- 개별 스택: 각 스레드는 자신의 스택을 갖고 있다.

##### 프로세스 vs 스레드
프로세서는 실행 중인 프로그래매의 인스턴스이다. 각 프로세스는 독립적인 메모리 공간을 가지며, 운영 체제에서 독립된 실행 단위로 취급된다.

스레드는 프로세스 내에서 실행되는 작은 단위이다. 여러 스레드는 하나의 프로세서 내에서 자원을 공유하며, 프로세스의 코드. 데이터, 시스템 자원 등을 공유한다. 실제로 CPU에 의해 실행되는 단위는 스레드이다.

##### 스레드의 종류
###### non-daemon 스레드(사용자 스레드)
프로그램의 주요 작업을 수행한다. 작업이 완료될 떼 까지 실행된다. 모든 User 스레드가 종료되면 JVM도 종료된다.

###### daemon 스레드
백그라운드에서 보조적인 작업을 수행한다.
모든 user 스레드가 종료되면 데몬 스레드는 자동으로 종료된다.
즉 JVM은 **데몬 스레드의 실행 완료를 기다리지 않고 바로 종료**한다.
데몬 스레드가 아닌 모든 스레드가 종료되면, 자바 프로그램도 종료된다.

### 컨텍스트 스위칭
스레드 A와 B를 번갈아가면서 실행한다.
스레드 A를 멈추는 시점에 CPU에서 사용하던 값들을 메모리에 저장해두어야한다.
그리고 이후에 스레드A를 다시 실행할 때 값들을 CPU에 다시 불러와야한다.
이런 과정을 컨텍스트 스위칭이라고 한다.

#### point
##### 컨텍스트 스위칭 비용 최적화
스레드의 숫자를 CPU의 숫자에 맞춘다면 CPU를 100% 활용 할 수 있고, 컨텍스트 스위칭 비용도 자주 발생하지 않기 때문에 최적의 상태가 된다. 이상적으로는 "CPU코어 수 + 1개" 정도로 스레드를 맞추면 특정 스레드가 잠시 대기할 때 남은 스레드를 활용할 수 있다.

이 스레드가 하는 작업은 크게 2가지로 CPU-바운드 작업, I/O-바운드 작업이 있다.

##### CPU-바운드 작업
CPU의 연산 능력을 많이 요구하는 작업을 의미한다.
이러한 작업은 주로 계산, 데이터 처리, 알고리즘 실행 등 CPU의 처리 속도가 작업 완료 시간을 결정하는 경우다.
(예: 복잡한 수학 연산, 데이터 분석, 비디오 이코딩, 과학적 시뮬레이션 등)

##### I/O-바운드 작업
디스크, 네트워크, 파일 시스템 등과 같은 입출력(I/O) 작업을 많이 요구하는 작업을 의미한다.
이러한 작업은 I/O 작업이 완료될 때 까지 대기 시간이 많이 발생하며, CPU는 상대적으로 대기 상태에 있는 경우가 많다. 쉽게 말해 스레드가 CPU를 사용하지 않고 I/O 작업이 완료될 때 까지 대기한다.
(예: 데이터베이스 쿼리 처리, 파일 읽기/쓰기, 네트워크 통신, 사용자 입력 처리)

###### WAS는 I/O-바운드 작업이 많다.
분야마다 다르겠지만, 실무에서는 CPU-바운드 작업 보다는 I/O-바운드 작업이 많다.
예를 들어서 백엔드 개발자의 경우 주로 WAS를 개발하는데, 스레드가 1~10000까지 더하는 CPU의 연산이 필요한 작업보다는, 대부분 사용자의 입력을 기다리거나, 데이터베이스를 호출하고 그 결과를 기다리는 등, 기다리는 일이 많다.

### 자바의 스레드
#### point
##### 스레드 생성 방법
스레드를 만들 때 Thread 클래스를 상속 받는 방법과 Runnable 인터페이스를 구현하는 방법이 있다.
Thread 클래스는 단일 상속의 제한으로 인해 유연성이 인터페이스에 비해 떨어진다.
그러므로 Runnable 인터페이스를 구현해서 사용하라.
상속의 자유로움, 스레드와 실행할 작업을 분리, 여러 스레드가 동일한 Runnable 객체를 공유할 수 있는 등 장점이 있다.
```java
public interface Runnable {
void run();
}
```

##### 스레드 생명 주기
![[../attachments/screenshots/스레드의생명주기.png]]
###### New (새로운 상태)
스레드가 생성되고 아직 시작되지 않은 상태이다.
이 상태에서는 Thread 객체가 생성되지만, **start() 메서드가 호출되지 않은 상태**이다.
예를 들어, "Thread thread = new Thread(runnable);"만 진행 해둔 상태

###### Runnable (실행 가능 상태)
스레드가 실행될 준비가 된 상태이다. 이 상태에서 스레드는 실제로 CPU에서 실행될 수 있다.
**start() 메서드가 호출되면 스레드는 이 상태**로 들어간다.
예를 들어, "Thread.start();"를 진행한 상태

**이상태는 스레드가 실행 될 준비가 된 상태**이다. 그러나 Runnable 상태에 있는 모든 스레드가 동시에 실행되는 것은 아니다. 운영체제의 스케줄러가 각 스레드에 CPU 시간을 할당하여 실행하기 때문에, Runnable 상태에 있는 스레드는 스케줄러의 실행 대기열에 포함되어 있다가 차례로 CPU에서 실행된다.

참고로 운영체제 **스케줄러의 실행 대기열에 있든, CPU에서 실제 실행되고 있든 모두 Runnable 상태**이다.
자바에서 둘을 구분해서 확인할 수는 없다. **보통 실행 상태라고 부른다.**

###### Blocked (차단 상태)
스레드가 다른 스레드에 의해 **동기화 락을 얻기 위해 기다리는 상태**이다.
예를 들어, "synchronized" 블록에 진입하기 위해 락을 얻어야하는 경우 이 상태에 들어간다.
(예: "synchronized (lock) { ... }")
즉 코드 블록에 진입하려고 할 때, 다른 스레드가 이미 "lock"을 가지고 있는 경우다.

###### Waiting (대기 상태)
스레드가 다른 스레드의 특정 작업이 완료되기를 무기한 기다리는 상태이다.
**wait(), join() 메서드가 호출될 때 이 상태**가 된다.
스레드는 다른 스레드가 notify() 또는 notifyAll() 메서드를 호출하거나 join()이 완료될 때 까지 기다린다.

###### Timed Waiting (시간 제한 대기 상태)
스레드가 특정 시간 동안 다른 스레드의 작업이 완료되기를 기다리는 상태이다.
**sleep(long millis), wait(long timeout), join(long millis) 메서드가 호출될 때 이 상태**가 된다.
주어진 시간이 경과하거나 다른 스레드가 해당 스레드를 깨우면 이 상태를 벗어난다.
(예: "Thread.sleep(1_000)")

###### Terminated(종료 상태)
스레드의 실행이 완료된 상태이다. **스레드가 정상적으로 종료되거나, 예외가 발생하여 종료된 경우 이
상태**로 들어간다. 스레드는 한 번 종료되면 다시 시작 할 수 없다.

##### sleep()
특정 스레드를 기다리게 하는 메소드이다. sleep을 통해 스레드를 대기하는 상태에서 스레드를 깨우기 위해 인터럽트가 필요하다.

##### Join()
스레드를 특정 시간 만큼 대기하는 기능이다. join()는 두가지 기능을 제공한다.
join()은 호출 스레드가 대상이 되는 스레드가 완료될 때 까지 무한정 대기한다.
join(ms)는 호출 스레드가 특정 시간 만큼만 대기한다. 특정 시간이 지나면 다시 Runnable 상태가 된다.

특정 스레드가 완료될 때 까지 무한정 대기하는것은 단점이며, 특정 시간 만큼 기다렸다가 특정 스레드가 완료 안됐을 경우에 따른 예외처리를 진행해야한다는 단점도 있다.

그렇기 때문에 인터럽트를 사용한다.

##### 인터럽트
"깨워줘! 신호, 지금 깨워줄게 이후는 네가 알아서 판단해"

특정 스레드가 예를 들어 "Tread.sleep()"을 통해 쉬고 있는 상태에서 처리해야하는 작업이 들어와 급하게 깨워줘야할 때 사용한다.
즉 인터럽트를 사용하면, **WATING, TIMED_WAITING 같은 대기 상태의 스레드를 직접 깨워서 작업하는 동안 Runnable 상태로 만들 수 있다.**

interrupt() 호출로 인터런트 true 플래그가 되면 예외가 발생한다.
예외가 발생하면 해당 스레드가 대기에서 Runnable이 된다.
인터럽트가 false 상태로 변환 시키고 해당 스레드는 예외를 통해 Runnable 상태로 진입되어 원하는 업무를 수행한다.

자바의 interrupt()는 스레드를 강제로 종료 시키는게 아니라 깨워주는 신호이다.
**만약 스레드가 sleep()이나 wait() 중이면 InterrupedException이 발생하면서 깨어나고** 실행 중이면 플래그만 세워져서 스스로 중단할 기회를 주는 구조이다.

##### yield()
현재 실행 중인 스레드가 자발적으로 CPU를 양보해서 다른 스레드가 샐행될 수 있게 한다.
즉 Runnable 상태는 유지하면서 스케줄링 큐에 들어가면서 다른 스레드에서 CPU 사용 기회를 준다.

### 메모리 가시성
![[../attachments/screenshots/메모리가시성.png]]

멀티스레드 환경에서 **한 스레드가 변경한 값이 다른 스레드에서 언제 보이는지에 대한 것**을 메모리 가시성이라고 한다. 이름 그대로 메모리에 변경한 값이 보이는가, 보이지 않는가의 문제이다.

캐시 메모리를 사용하면 CPU처리 성능을 개선할 수 있다. 하지만 때로는 이런 성능 향상보다는, 여러 스레드에서 같은 시점에 정확히 같은 데이터를 보는것이 중요할 수 있다.
해결방안은 **성능을 약간 포기하는 대신에, 값을 읽을 때, 값을 쓸 때 모두 메인 메모리에 직접 접근**하면 된다.

자바에서는 "volatile"이라는 키워드로 해당 기능을 제공한다. 해당 키워드를 사용하면 캐시 메모리를 쓰지 않고 메인 메모리에 직접 접근하여 수행한다.

### 임계 영역(크리티컬 섹션)
여러 스레드가 동시에 접근하면 데이터 불일치나 예상치 못한 동작이 발생할 수 있는 위험하고 중요한 코드의 부분을 뜻한다.

### synchronized 동기화
자바에서 동기화는 여러 스레드가 동시에 접근할 수 있는 자원에 대해 일관성 있고 안전한 접근을 보장하기 위한 메커니즘이다. 동기화는 주로 멀티스레드 환경에서 발생할 수 있는 문제를 방지하기 위해 사용된다. 모니터락을 가진 스레드가 작업을 수행하게 되는데, 이를 통해 2가지를 해결할 수 있다.

레이스 컨디션: 두 개 이상의 스레드가 경쟁적으로 동일한 자원을 수정할 때 발생하는 문제
데이터 일관성: 여러 스레드가 동시에 읽고 쓰는 데이터의 일관성을 유지

요청이 많이 들어오는데 하나만 처리되는 그런 병목현상이 일어날 수 있으니 조심해야한다.
```java
public synchronized boolean withdraw(int amount) {}
```

#### point
###### synchronized 단점
무한 대기: Blocked 상태의 스레드는 락이 풀릴 때 까지 무한 대기한다. (대기 타임아웃 X, 중간 인터럽트 X)
공정성: 락이 돌아왔을 때 Blocked 상태의 여러 스레드 중에 어떤 스레드가 락을 획득할 지 알 수 없다. (최악을 경우 특정 스레드가 너무 오랜기간 락을 획득하지 못한다.)

##### LockSupport
Synchronized의 단점을 보완해주는 동기화 방법이다.
LockSupport는 스레드를 Wating 상태로 변경합니다. 즉, 안전한 임계영역 안에서 기능을 개발해야한다.
특정 스레드가 락을 먼저 얻으면 Runnable로 실행하고 락을 얻지 못하면 park()라는 메소드로 대기 상태로 만든다.
락을 반납하면 unpark()를 사용해서 대기중인 다른 스레드를 깨운다. 안전한 임계영역에서 스레드 락을 조율하면서 구현하기는 어렵고 저수준의 기능이기 때문에 Lock인터페이스와 ReentrantLock을 사용해야한다.

##### Lock 인터페이스
Lock 인터페이스는 동시성 프로그래밍에서 쓰이는 안전한 임계영역을 위한 락을 구현하는데 사용된다.

"void lock();"을 통해 락을 획득한다. 만약 다른 스레드가 이미 락을 획득했다면, 락이 풀릴 때 까지 현재 스레드를 Wating 한다. 해당 상태는 인터럽트에 응답하지 않습니다. (예: 맛집 한번 줄 스면 끝까지 무슨일이 있어도 포기하지 않고 기다려야한다.) 내부적으로 모니터락을 가지고 있지 않으며, 가장 기본적인 락일 뿐이다.

Lock 인터페이스를 통해 synchronized의 단점 무한대기 문제를 해결했지만, 공정성 문제가 존재한다. 최악을 경우 특정 스레드가 너무 오랜기간 락을 획득하지 못하는 기아문제가 발생한다.

##### ReentrantLock
기아문제를 해결하기 위해 나온 Lock 인터페이스의 대표적인 구현체이다. ReentrantLock이다. 
```java
lock.lock(); // ReentrantLock 이용하여 lock을 걸기
try {
	// 작업 진행
	} finally {
		lock.unlock(); // ReentrantLock 이용하여 lock 해제
	}
return ; // 결과
```

###### 비공정모드
비공정 모드는 디폴트로 설정된 모드이다. **요청 순서에 관계없이 대기큐에 있는 스레드 아무나 락을 획득**할 수 있다. 락을 획득하는 속도가 빠르고 새로운 스레드가 기존 대기 스레드보다 먼저 락을 획득하는 선점이 가능하다.
따라서 **기아 현상을 해결**하지는 못한다.
```java
// 비공정 모드 락
private final Lock nonFairLock = new ReentrantLock();
```

###### 공정모드
생성자에 true를 입력하면 쉽게 설정할 수 있다. **요청한 순서대로 대기큐의 스레드가 락을 획득**할 수 있다.
먼저 대기한 스레드가 먼저 락을 획득하니 공정성으 보장되고 **기아현상도 방지**할 수 있다.
다만 **락을 획득하는 속도가 상대적으로 느리다.**
```java
// 공정 모드 락
private final Lock fairLock = new ReentrantLock(true);
```

##### 스핀락
스레드가 락이 해제되기를 기다리면서 반복문을 통해 계속 확인하는 모습 마치 재자리에서 회전하는것 처럼 보여서 스핀락이라고 불린다. 아주 짧은 CPU 연산에서 사용해서 효율적이지만, 잘못 사용하면 하루종일 반복문이 돌기 때문에 굉장히 조심해야한다.

### 생산자 소비자 문제
생산자 소비자 문제는 여러 스레드가 하나의 공유 장원을 사용할 때 발생하는 대표적인 동기화 문제이다.
생산자 스레드는 데이터를 생성해 공유 버퍼에 넣고, 소비자 스레드는 버퍼에서 데이터를 가져가는 구조이다.
이때 버퍼가 가득차거나 비어 있을 때의 접근을 제어하지 않으면 데이터 손실이나 동시성 문제가 발생한다.

따라서, wait() / notify(), BlockingQueue, Condition등을 사용해 생산자와 소비자의 작업 순서를 동기화해야한다.

#### point
##### wait()
현재 스레드가 가진 락을 반납하고 대기한다. 현재 스레드가 synchronized 메서드의 락을 소유하고 있을 때만 호출이 가능하며, 다른 스레드가 락을 획득하게 한다.
대기 상태로 전환된 스레드는 다른 스레드가 notify() 또는 notifyAll()해야 깨어난다.

##### notify()
대기 중인 스레드 중 하나를 깨운다. 깨운 스레드는 락을 다시 획득할 기회를 얻고 **여러 스레드 중 하나만 깨워진다.**

##### notifyAll()
대기중인 모든 스레드를 깨운다. 해당 메서드도 역시 synchronized 메서드에서 호출되어야하며, 모든 대기 중인 스레드가 락을 획득할 수 있는 기회를 얻게 된다.

##### wait(), notify(), notifyAll() 사용
스레드가 락을 가지고 임계영역안에 무한 대기하는 문제를 해결하기 위해 사용된다.
예를들어, 생산자 소비자 문제에 있어서 소비자 스레드가 큐에 빈공간이 주기적으로 체크하고 없다면 wait()을 한다. 특정 생산자 스레드가 데이터를 큐에 저장하고 나면 notify()를 통해 대기하는 소비자 스레드를 깨워서 데이터를 획득하게 한다.

notify()의 경우에는 모든 대기 스레드 중 랜덤으로 깨우기 때문에 생산자 소비자 문제에서는 Condition을 사용해서 소비자 생산자 대기 공간을 분리하여 관리한다.
```java
condition.await(); // == wait()
condition.signal(); // FIFO 순서로 깨움, notify()는 랜덤으로 깨움
```

따라서 Object의 wait(), notify()는 스레드간 협업 메커니즘의 기본이 되는 기능이다.

##### BlockingQueue 인터페이스
생산자 소비자 문제 그리고 한정된 버퍼라고 불리는 문제를 해결하기 위해 나온 멀티스레드 자료구조이다. 이름 그대로 스레드를 차단할 수 있는 큐이다.

### 원자적 연산
특정 연산이 더 이상 나눌 수 없는 단위로 수행된다는것을 의미한다. 멀티스레드 상황에서 다른 스레드의 간섭 없이 안전하게 처리되는 연산이다.
"i = 1" 같은 연산을 원자적 연산이라고 한다. "i = i + 1" 같은 연산은 원자적 연산이 아니다.

따라서 원자적 연산이 아닌 경우에는 synchronized를 통해 안전한 임계 영역을 만들고 수행해야한다.
레퍼 클래스의 경우 AtomicInteger, AtomicLong, AtomicBoolean등 다양한 AtomicXXX 클래스가 존재한다.

#### point
##### i = i + 1, i++ 은 원자적 연산이 아니다.
처음에 i = 0이라고 가정하겠다.
1. **스레드1**: i = i + 1 연산 수행
2. 스레드2: i = i + 1 연산 수행
3. **스레드1**: i의 값을 읽는다. i는 0이다.
4. 스레드2: i의 값을 읽는다. i는 0이다.
5. **스레드1**: 읽은 0에 1을 더해서 1을 만든다.
6. 스레드2: 읽은 0에 1을 더해서 1을 만든다.
7. **스레드1**: 더한 1을 왼쪽의 i변수에 대입한다.
8. 스레드2: 더한 1을 왼쪽의 i변수에 대입한다.
결과: i의 값은 1이다.

##### CAS연산
![[../attachments/screenshots/CAS.png]]

락을 사용하지 않고 원자적 연산을 처리하는 기법으로 락 프리 기법이라고도 불린다. 작은 단위의 일부 영역에 CAS 연산을 적용할 수 있다.

AtomicXXX 구현체의 compareAndSet() 메서드를 통해 자바에서는 CAS연산을 지원한다. CPU 하드웨어를 통해서 원자적인 연산으로 묶어서 제공하는 것이기에 중간에 다른 스레드가 개입할 수 없습니다.
```java
atomicInteger.compareAndSet(0, 1); // atomicInteger 가 가지고 있는 값이 현재 0이면 이 값을 1로 변경 (변경되면 true, 변경이 안되면 false 반환)
```

###### CAS vs Lock
락은 비관적으로 데이터에 접근하며, 데이터에 접근하기전 항상 락을 획득하고 있는 스레드의 접근을 막습니다.

CAS는 낙관적으로 데이터에 접근하며, 락을 사용하지 않고 데이터에 바로 접근한다. 충돌이 발생하면 그때 재시도를 하며 "대부분 충돌이 없을 것"이라고 가정한다. CPU 연산은 굉장히 빠르기 때문에 충돌이 거의 발생하지 않는다.

즉, CPU 연산에는 락 보다는 CAS를 사용하는것이 효과적이다.

### 동시성 컬렉션 프레임워크
자바의 유틸 패키지의 컬렉션 프레임워크는 스레드 세이프하지 않다. 따라서, 자바 유틸 Concurrent 패키지의 동시성 컬렉션을 사용해야한다.

ListCopyOnWriteArrayList: **ArrayList**의 대안
SetCopyOnWriteArraySet: **HashSet**의 대안
ConcurrentSkipListSet: **TreeSet**의 대안(정렬된 순서 유지, Comparator사용 가능)
MapConcurrentHashMap: **HashMap**의 대안
ConcurrentSkipListMap: **TreeMap**의 대안(정렬된 순서 유지, Comparator 사용 가능)
QueueDequeConcurrentLinkedQueue: 동시성 큐, 비 차단(non-blocking) 큐이다.
ConcurrentLinkedDeque: 동시성 데크, 비 차단(non-blocking) 큐이다.

### Executor 프레임워크
멀티스레딩, 병렬 처리를 쉽게 사용할 수 있도록 돕는 기능의 모음이다. 스레드 풀을 효율적으로 관리 및 처리하여 개발자가 직접 스레드를 관리할 때의 복잡함을 줄여준다.

#### point
##### 스레드 풀 관리
작업을 요청하면 core 사이즈 만큼 스레드를 만들고 core 사이즈를 초과하면 큐에 작업을 넣는다.
큐를 초과하면 max 사이즈 만큼 스레드를 만들며, 임시로 사용되는 초과 스레드가 생성된다.
max 사이즈를 초과하면 요청을 거절하며 예외를 발생 시킵니다.
즉, 큐도 가득차고, 풀에 최대 생성 가능한 스레드 수도 가득 찬다면 작업을 받을 수 없다.
- **corePoolSize**: 스레드 풀에서 관리되는 기본 스레드의 수
- **maximumPoolSize**: 스레드 풀에서 관리되는 최대 스레드의 수
- **keepAliveTime, TimeUnit unit**: 기본 스레드 수를 초과해서 만들어진 초과 스레드가 생존할 수 있는 대기시간, 이시간 동안 처리할 작업이 없다면 초과 스레드는 제거 된다.
- **BlockingQueue workQueue**: 작업을 보관할 블록킹 큐

##### 스레드 풀 전략
일반적인 상황이라면 고정 스레드 풀 전략이나, 캐시 스레드 풀 전략을 사용하면 충분하다.
고정 스레드 풀 전략은 서버 자원은 여유가 있는데, 사용자만 점점 느려지는 문제가 발생할 수 있다.
반면 캐시 스레드 풀 전략은 서버의 자원을 최대한 사용하지만, 서버가 감당할 수 있는 임계점을 넘는 순간 시스템이 다운될 수 있다.

###### 단일 스레드 풀 전략 newSingleThreadPool()
스레드 풀에 기본 스레드 한개만 사용한다.
큐 사이즈에 제한이 없으며, 주로 간단히 사용하거나 테스트 용도로 사용한다.
```java
new ThreadPoolExecutor(1, 1,0L, TimeUnit.MILLISECONDS, new LinkedBlockingQueue<Runnable>())
```

###### 고정 스레드 풀 전략 newFixedThreadPool(nThreads)
트래픽이 일정하고, 시스템 안전성이 가장 중요할 때 사용한다.
스레드 풀에 nThreads 만큼의 기본 스레드를 생성한다. 초과 스레드는 생성하지 않는다.
큐 사이즈에는 제한이 없으며, 스레드 수가 고정되어 있기 때문에 CPU, 메모리 리소스가 어느정도 예측 가능한 안정적인 방식이다.
```java
new ThreadPoolExecutor(nThreads, nThreads, 0L, TimeUnit.MILLISECONDS, new LinkedBlockingQueue<Runnable>())
```

###### 캐시 스레드 풀 전략 newCachedThreadPool()
일반적으로 성장하는 서비스에서 사용ㅎ나다.
기본 스레드를 사용하지 않고, 60초 생존 주기를 가진 초과 스레드만 사용한다.
초과 스레드의 수는 제한이 없고, 큐에 작업을 저장하지 않는다.
대신에 생산자의 요청을 스레드 풀의 소비자 스레드가 직접 받아서 바로 처리한다.
모든 요청이 대기하지 않고 스레드가 바로바로 처리한다. 따라서 빠른 처리가 가능하다.
```java
new ThreadPoolExecutor(0, Integer.MAX_VALUE, 60L, TimeUnit.SECONDS, new SynchronousQueue<Runnable>());
```

##### 종료 방법
고객의 주문을 처리하고 있는 도중에 갑자기 시스템이 재시작 된다면, 해당 고객의 주문이 제대로 진행되지 않으니 새로운 주문을 막고, 이미 진행 중인 주문을 모두 완료하고 서비스를 끄는게 좋다.
그래서 ExecutorService의 셧다운 메서드는 새로운 작업을 받지 않고 이미 제출된 작업을 모두 완료한 후에 종료한다. 논-블록킹 메서드이기 때문에 이 메서드를 호출한 스레드는 대기하지 않고 즉시 다음 코드를 호출한다.

##### callable vs Future
Runnable은 run메서드 하나만 존재한다.
작업 스레드를 간단히 값을 리턴하고 요청 스레드는 그 반환 값을 바로 받을 수 있도록 하기 위해 Executor 프레임 워크는 Callble과 Future라는 인터페이스를 도입했다.
callable은 call()이라는 메서드로 반환 타입이 제네릭이고 예외가 선언되어 하위에서 예외를 던질 수 있게 개선되었다.
```java
public interface Callable<V> {
	V call() throws Exception; 
}
```

Future는 미래의 결과를 받을 수 있는 객체이다. 즉 Futrue는 전달한 작업의 미래이며 이 객체를 통해 전달한 작업의 미래 결과를 받을 수 있다는 것이다.
```java
ExecutorService es = Executors.newFixedThreadPool(1);
Future<Integer> future = es.submit(new MyCallable());
```

### 블록킹
스레드가 어떤 결과를 얻기 위해 대기하는 것을 블록킹이라고 한다.
즉 taskA가 아직 수행되지 않았거나 또는 수행 중이라는 뜻이다. 이때는 어쩔 수 없이 요청 스레드가 결과를 받기 위해 대기해야한다. 요청 스레드가 마치 락을 얻을 때 처럼, 결과를 얻기 위해 대기한다.

#### point
##### 블록킹 메서드
Thread.join(), Future.get()과 같은 메서드는 스레드가 작업을 바로 수행하지 않고, 다른 작업이 완료될 때 까지 기다리게 하는 메서드이다. 이러한 메서드를 호출하면 호출한 스레드는 지정된 작업이 완료될 때까지 Blocked되어 다른 작업을 수행할 수 없다.
