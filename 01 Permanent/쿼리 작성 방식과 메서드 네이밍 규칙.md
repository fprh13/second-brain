쿼리 작성 방식과 메서드 네이밍 규칙

---

## 📄 본문

### Spring Data JPA의 쿼리 작성 방식

Spring Data JPA에서는 Repository를 통해 데이터베이스에 접근할 때 여러 방식으로 쿼리를 작성할 수 있다.

대표적으로 **메서드 네이밍(Derived Query Method), JPQL, QueryDSL, Native Query**가 있다.

각 방식은 쿼리의 복잡도와 요구사항에 따라 선택하며, 특정 방식이 무조건 더 좋은 것은 아니다.

|구분|특징|주요 사용 상황|
|---|---|---|
|기본 제공 메서드|JpaRepository에서 기본 제공|기본 CRUD|
|메서드 네이밍|메서드 이름을 분석하여 쿼리 생성|단순 조건 조회|
|JPQL|엔티티 중심의 쿼리를 직접 작성|복잡한 JOIN, Fetch Join, DTO 조회|
|QueryDSL|자바 코드로 타입 안전한 쿼리 작성|동적 검색 조건, 복잡한 조회|
|Native Query|데이터베이스 SQL 직접 작성|DB 전용 기능, 복잡한 SQL|

#### 선택 기준

- **기본 CRUD:** `JpaRepository` 기본 제공 메서드
- **단순한 조회:** 메서드 네이밍
- **복잡하지만 조건이 고정된 조회:** JPQL
- **조건이 동적으로 변경되는 조회:** QueryDSL
- **데이터베이스 고유 기능이 필요한 조회:** Native Query

선택 기준에서 가장 중요한 것은 쿼리의 복잡도, 가독성, 유지보수성이다.

### 메서드 네이밍 (Derived Query Method)

Spring Data JPA가 Repository의 **메서드 이름을 분석하여 쿼리를 자동으로 생성하는 기능**이다.

개발자가 JPQL을 직접 작성하지 않아도 정해진 네이밍 규칙에 따라 조회 조건과 정렬 등을 표현할 수 있다.

#### 기본 구조

```
findBy + 필드명 + 조건
```

예를 들어 `User` 엔티티에 `email` 필드가 존재한다면 다음과 같이 작성한다.

```java
public interface UserRepository extends JpaRepository<User, Long> {

    Optional<User> findByEmail(String email);
}
```

이는 다음 JPQL과 논리적으로 동일한 조회를 수행한다.

```sql
SELECT u
FROM User u
WHERE u.email = :email
```

Spring Data JPA가 메서드 이름을 분석하여 JPA 쿼리를 구성하고, 실제 SQL 생성과 실행은 Hibernate 등의 JPA 구현체가 담당한다.

#### 특징

- JPQL을 직접 작성하지 않아도 된다.
- 엔티티의 필드명을 기반으로 조회 조건을 생성한다.
- 기본적인 비교, 정렬, 페이징 등을 지원한다.
- 메서드 선언만으로 간단한 조회 로직을 구현할 수 있다.
- 복잡한 조건을 표현할수록 메서드 이름이 길어지는 단점이 있다.

### 메서드 네이밍 문법

메서드 이름은 크게 **접두어(Subject)와 조건부(Predicate)**로 구성된다.

```
findByEmail
```

- `find`: 수행할 작업
- `By`: 조회 조건의 시작
- `Email`: 조건으로 사용할 엔티티 필드

#### 1. 기본 조회 및 집계

|메서드|역할|
|---|---|
|`findByEmail`|이메일 조건으로 조회|
|`findAllByStatus`|상태 조건으로 목록 조회|
|`existsByEmail`|이메일 존재 여부 확인|
|`countByStatus`|특정 상태의 데이터 개수 조회|
|`deleteByEmail`|이메일 조건으로 삭제|
|`removeByEmail`|이메일 조건으로 삭제|

```java
public interface UserRepository extends JpaRepository<User, Long> {

    Optional<User> findByEmail(String email);

    List<User> findAllByStatus(UserStatus status);

    boolean existsByEmail(String email);

    long countByStatus(UserStatus status);

    long deleteByEmail(String email);
}
```

`deleteBy`와 `removeBy`는 동일한 종류의 파생 삭제 메서드이다.

주의할 점은 파생 삭제 메서드가 일반적인 벌크 DELETE와 다르게 동작한다는 것이다. Spring Data JPA의 파생 삭제는 대상 엔티티를 조회한 후 개별 삭제하므로 엔티티 생명주기 콜백 등이 적용될 수 있다.

대량 삭제가 필요하다면 `@Modifying`을 사용하는 벌크 삭제 쿼리 등을 별도로 검토한다.

#### 2. 비교 연산자

|키워드|예시|비교 조건|
|---|---|---|
|`Is`, `Equals`|`findByName`|`=`|
|`Not`|`findByStatusNot`|`<>`|
|`GreaterThan`|`findByAgeGreaterThan`|`>`|
|`GreaterThanEqual`|`findByAgeGreaterThanEqual`|`>=`|
|`LessThan`|`findByAgeLessThan`|`<`|
|`LessThanEqual`|`findByAgeLessThanEqual`|`<=`|
|`Between`|`findByAgeBetween`|`BETWEEN`|
|`In`|`findByStatusIn`|`IN`|
|`NotIn`|`findByStatusNotIn`|`NOT IN`|

```java
public interface UserRepository extends JpaRepository<User, Long> {

    List<User> findByAgeGreaterThan(int age);

    List<User> findByAgeLessThanEqual(int age);

    List<User> findByAgeBetween(int minAge, int maxAge);

    List<User> findByStatusIn(Collection<UserStatus> statuses);
}
```

`Between`은 시작값과 종료값을 포함한다.

#### 3. 문자열 검색

|키워드|예시|검색 조건|
|---|---|---|
|`Like`|`findByNameLike`|LIKE 패턴 검색|
|`NotLike`|`findByNameNotLike`|LIKE 패턴 제외|
|`Containing`|`findByNameContaining`|특정 문자열 포함|
|`StartingWith`|`findByNameStartingWith`|특정 문자열로 시작|
|`EndingWith`|`findByNameEndingWith`|특정 문자열로 종료|
|`IgnoreCase`|`findByNameIgnoreCase`|대소문자 구분 없는 비교|

```java
public interface UserRepository extends JpaRepository<User, Long> {

    List<User> findByNameContaining(String keyword);

    List<User> findByNameStartingWith(String keyword);

    List<User> findByNameEndingWith(String keyword);

    List<User> findByNameIgnoreCase(String name);
}
```

**Containing과 Like의 차이**

```
findByNameContaining("kim");
```

개념적으로 다음과 같은 검색을 수행한다.

```
WHERE name LIKE '%kim%'
```

반면 `Like`는 검색 패턴을 직접 전달한다.

```
findByNameLike("%kim%");
```

`Containing`은 검색어에 포함된 SQL LIKE 와일드카드 문자 `%`, `_`를 이스케이프하여 일반 문자로 취급하도록 처리한다. `Like`는 전달된 패턴을 사용한다.

#### 4. NULL 및 Boolean 조건

|키워드|예시|조회 조건|
|---|---|---|
|`IsNull`|`findByNameIsNull`|IS NULL|
|`IsNotNull`|`findByNameIsNotNull`|IS NOT NULL|
|`True`|`findByActiveTrue`|TRUE|
|`False`|`findByActiveFalse`|FALSE|

```java
public interface UserRepository extends JpaRepository<User, Long> {

    List<User> findByNameIsNull();

    List<User> findByNameIsNotNull();

    List<User> findByActiveTrue();

    List<User> findByActiveFalse();
}
```

Boolean 조건을 고정하지 않고 파라미터로 전달할 수도 있다.

```java
List<User> findByActive(boolean active);
```

#### 5. 여러 조건 조합

`And`와 `Or`를 사용하여 여러 조회 조건을 조합할 수 있다.

```java
public interface UserRepository extends JpaRepository<User, Long> {

    List<User> findByNameAndStatus(
        String name,
        UserStatus status
    );

    List<User> findByNameOrEmail(
        String name,
        String email
    );
}
```

JPQL로 표현하면 다음과 같다.

```
-- And
WHERE u.name = :name
  AND u.status = :status

-- Or
WHERE u.name = :name
   OR u.email = :email
```

**주의할 점**

`And`와 `Or`를 동시에 사용하면 논리적 결합 순서에 주의해야 한다.

```
findByStatusAndNameOrEmail(...)
```

이는 다음 조건을 의미한다.

```
WHERE (status = ? AND name = ?)
   OR email = ?
```

`status = ? AND (name = ? OR email = ?)`와는 다른 조건이다.

메서드 네이밍에는 임의의 괄호를 직접 표현하는 문법이 없으므로 복잡한 논리 조건은 JPQL이나 QueryDSL을 사용하는 것이 명확하다.

#### 6. 정렬

`OrderBy`를 사용하여 정렬 조건을 지정할 수 있다.

|키워드|의미|
|---|---|
|`OrderBy`|정렬 조건 지정|
|`Asc`|오름차순|
|`Desc`|내림차순|

```java
public interface UserRepository extends JpaRepository<User, Long> {

    List<User> findByStatusOrderByCreatedAtDesc(UserStatus status);

    List<User> findByStatusOrderByCreatedAtAsc(UserStatus status);

    List<User> findByStatusOrderByCreatedAtDescIdDesc(
        UserStatus status
    );
}
```

마지막 메서드는 다음과 같은 정렬을 수행한다.

```
ORDER BY created_at DESC, id DESC
```

조회할 때마다 정렬 조건이 달라져야 한다면 `Sort`를 전달할 수 있다.

```
List<User> findByStatus(UserStatus status, Sort sort);
```

호출 예시

```java
userRepository.findByStatus(
    UserStatus.ACTIVE,
    Sort.by(Sort.Direction.DESC, "createdAt")
);
```

#### 7. 조회 결과 개수 제한

`First` 또는 `Top`을 사용하여 조회 결과 개수를 제한한다.

```java
public interface UserRepository extends JpaRepository<User, Long> {

    Optional<User> findFirstByStatusOrderByCreatedAtDesc(
        UserStatus status
    );

    List<User> findTop5ByStatusOrderByCreatedAtDesc(
        UserStatus status
    );
}
```

|키워드|의미|
|---|---|
|`First`|첫 번째 결과 조회|
|`Top`|첫 번째 결과 조회|
|`First5`|최대 5개 조회|
|`Top5`|최대 5개 조회|

`First`와 `Top`은 기능적으로 동일하며, 숫자를 생략하면 최대 1개를 조회한다.

정렬 기준을 함께 지정해야 어떤 데이터가 먼저 조회되는지 명확해진다.

#### 8. 페이징

메서드 파라미터에 `Pageable`을 전달하여 페이징을 적용할 수 있다.

```java
public interface UserRepository extends JpaRepository<User, Long> {

    Page<User> findByStatus(
        UserStatus status,
        Pageable pageable
    );
}
```

호출 예시

```java
Pageable pageable = PageRequest.of(
    0,
    20,
    Sort.by(Sort.Direction.DESC, "createdAt")
);

Page<User> result = userRepository.findByStatus(
    UserStatus.ACTIVE,
    pageable
);
```

`PageRequest.of(0, 20)`은 첫 번째 페이지에서 최대 20개의 데이터를 조회한다.

반환 타입에 따라 페이징 동작이 달라진다.

|반환 타입|특징|
|---|---|
|`Page<T>`|조회 결과와 전체 데이터 수 등 페이징 정보 제공|
|`Slice<T>`|다음 페이지 존재 여부 제공|
|`List<T>`|조회된 데이터 목록만 제공|

`Page`는 전체 개수를 파악하기 위해 Count Query가 실행될 수 있다.

`Slice`는 전체 개수를 조회하지 않고 다음 데이터 존재 여부를 판단하므로 전체 페이지 수가 필요 없는 경우에 적합하다.

다만 `Slice` 자체가 커서 기반 페이징을 의미하는 것은 아니다.

#### 9. 연관 엔티티 필드 조회

메서드 네이밍은 현재 엔티티의 필드뿐 아니라 연관 엔티티의 필드를 조건으로 사용할 수도 있다.

예를 들어 다음과 같은 연관관계가 있다고 가정한다.

```java
@Entity
public class User {

    @ManyToOne(fetch = FetchType.LAZY)
    private Department department;
}
```

`Department` 엔티티의 `name`을 조건으로 조회하려면 다음과 같이 작성할 수 있다.

```java
List<User> findByDepartment_Name(String name);
```

이는 개념적으로 다음과 같은 조건을 의미한다.

```
WHERE u.department.name = :name
```

Spring Data JPA는 연관관계의 경로를 분석하여 필요한 쿼리를 구성한다.

`_`는 필드 경로를 명시적으로 구분할 때 사용할 수 있다.

단, **연관 엔티티의 필드를 검색 조건으로 사용한다고 해서 해당 엔티티가 Fetch Join으로 로딩되는 것은 아니다.**

연관 엔티티의 로딩 전략을 제어하려면 별도의 방법을 사용해야 한다.

### JPQL

JPQL(Java Persistence Query Language)은 테이블이 아니라 **엔티티와 엔티티의 필드를 기준으로 작성하는 객체 지향 쿼리 언어**이다.

Spring Data JPA에서는 일반적으로 `@Query`를 사용하여 JPQL을 직접 작성한다.

#### 패키지

```java
org.springframework.data.jpa.repository.Query
```

#### 기본 문법

```java
public interface UserRepository extends JpaRepository<User, Long> {

    @Query("""
        SELECT u
        FROM User u
        WHERE u.email = :email
        """)
    Optional<User> findByEmail(@Param("email") String email);
}
```

#### JPQL을 사용하는 상황

메서드 네이밍만으로 표현하기 어렵거나 쿼리 구조를 명시적으로 관리해야 하는 경우 사용한다.

대표적인 경우는 다음과 같다.

- 여러 엔티티를 JOIN하여 조회
- Fetch Join으로 연관 엔티티 로딩
- 복잡한 AND, OR 조건 조합
- DTO 생성자 표현식을 사용한 조회
- 서브쿼리 또는 집계 함수 사용
- 조회 대상과 JOIN 조건을 명시적으로 제어

#### Fetch Join 예시

```java
public interface BidRepository extends JpaRepository<Bid, Long> {

    @Query("""
        SELECT b
        FROM Bid b
        JOIN FETCH b.bodyShop
        JOIN FETCH b.estimate
        WHERE b.id = :bidId
        """)
    Optional<Bid> findByIdWithBodyShopAndEstimate(
        @Param("bidId") Long bidId
    );
}
```

일반적인 `findById()`와 달리 조회 과정에서 필요한 연관 엔티티를 함께 가져오도록 지정한다.

Fetch Join은 연관 엔티티의 로딩으로 인한 추가 쿼리를 줄이기 위해 사용한다.

단순히 연관 엔티티를 함께 로딩하는 목적이라면 `@EntityGraph`도 선택할 수 있다.

```java
@EntityGraph(attributePaths = {"bodyShop", "estimate"})
Optional<Bid> findById(Long id);
```

`@EntityGraph`는 조회 시점에 적용할 연관 엔티티 로딩 계획을 선언하는 방식이다.

### 메서드 네이밍과 JPQL의 차이

동일한 조회 조건이라면 두 방식은 논리적으로 같은 쿼리를 구성할 수 있다.

#### 메서드 네이밍

```java
Optional<User> findByEmail(String email);
```

#### JPQL

```java
@Query("""
    SELECT u
    FROM User u
    WHERE u.email = :email
    """)
Optional<User> findByEmail(@Param("email") String email);
```

두 방식 모두 같은 조건으로 사용자를 조회한다.

|비교 항목|메서드 네이밍|JPQL|
|---|---|---|
|쿼리 직접 작성|불필요|필요|
|단순 조건 조회|적합|가능|
|복잡한 조건 조합|가독성 저하 가능|적합|
|명시적인 JOIN|직접 지정 어려움|가능|
|Fetch Join|메서드 이름만으로 지정 불가|가능|
|동적 검색 조건|부적합|제한적|
|유지보수성|단순 조회에 유리|복잡한 고정 쿼리에 유리|

**성능 측면에서 메서드 네이밍이 JPQL보다 빠르거나 느리다고 일반화할 수 없다.**

실제 성능은 생성된 SQL, JOIN 구조, 인덱스, 실행 계획, 조회 데이터 양 등에 따라 결정된다.

### QueryDSL을 사용하는 상황

JPQL은 정적인 조회 조건에는 적합하지만, 검색 조건이 동적으로 변경되는 상황에서는 쿼리 관리가 복잡해질 수 있다.

예를 들어 견적 검색 API에서 다음 조건들이 선택적으로 전달되는 경우가 있다.

- 견적 상태
- 최소 및 최대 수리 비용
- 수리 지역
- 픽업 필요 여부
- 차량 브랜드 및 모델

이러한 조건을 메서드 네이밍으로 처리하려면 조건 조합에 따라 많은 메서드가 필요하거나 지나치게 긴 메서드 이름이 만들어진다.

JPQL에서도 다음과 같은 방법을 사용할 수 있다.

```java
@Query("""
    SELECT e
    FROM Estimate e
    WHERE (:status IS NULL OR e.status = :status)
    """)
List<Estimate> search(@Param("status") EstimateStatus status);
```

하지만 조건이 많아지면 JPQL이 복잡해지고, 선택적 조건을 표현하는 방식에 따라 쿼리 실행 계획에도 영향을 줄 수 있다.

이런 경우 QueryDSL을 사용하여 필요한 조건을 동적으로 조합하는 것이 적절하다.

```java
queryFactory
    .selectFrom(estimate)
    .where(
        statusEq(status),
        minRepairCostGoe(minCost),
        maxRepairCostLoe(maxCost)
    )
    .fetch();
```

각 조건 메서드에서 조건값이 없다면 `null`을 반환하도록 구현하여 해당 조건을 제외할 수 있다.

이처럼 QueryDSL은 동적 검색 조건을 관리하기에 적합하지만, 단순한 조회까지 무조건 QueryDSL로 작성할 필요는 없다.

### 메서드 네이밍 사용 시 주의사항

#### 1. 메서드 이름은 엔티티 필드명을 기준으로 작성한다.

```
findByCreatedAt(...)
```

이는 엔티티에 `createdAt`이라는 필드가 존재한다는 의미이다.

데이터베이스 컬럼명이 `created_at`이라고 해서 메서드에도 `created_at`을 작성하는 것은 아니다.

엔티티의 자바 프로퍼티 이름을 사용한다.

#### 2. 기본 제공 메서드를 중복 작성하지 않는다.

`JpaRepository`는 다음과 같은 메서드를 기본적으로 제공한다.

```
findById(id);
findAll();
save(entity);
deleteById(id);
existsById(id);
count();
```

별도의 조회 조건이나 동작이 필요하지 않다면 기본 제공 메서드를 사용한다.

특히 `findById`, `existsById`, `deleteById` 등은 식별자 필드를 대상으로 하는 예약된 메서드이다.

#### 3. 단순 조회에는 @Param이 필요하지 않다.

```
Optional<User> findByEmail(String email);
```

메서드 네이밍을 이용한 파생 쿼리는 메서드 이름과 파라미터 순서를 통해 조건을 구성하므로 `@Param`을 사용할 필요가 없다.

반면 JPQL에서 이름 기반 파라미터 바인딩을 명시적으로 지정하고 싶다면 `@Param`을 사용한다.

```java
@Query("""
    SELECT u
    FROM User u
    WHERE u.email = :email
    """)
Optional<User> findByEmail(@Param("email") String email);
```

컴파일 시 `-parameters` 옵션이 적용되어 메서드 파라미터 이름을 확인할 수 있다면 `@Param`을 생략할 수도 있다.

#### 4. 메서드 네이밍으로 모든 조회를 처리하지 않는다.

```
findByStatusAndNameContainingOrEmailContainingOrderByCreatedAtDesc(...)
```

조건이 복잡해질수록 메서드 이름의 가독성이 떨어지고 쿼리의 의도를 파악하기 어려워진다.

이런 경우 JPQL이나 QueryDSL로 쿼리를 명시적으로 작성하는 것이 유지보수에 유리하다.

---

### 정리

Spring Data JPA에서는 쿼리의 복잡도에 따라 적절한 작성 방식을 선택한다.

|상황|권장 방식|
|---|---|
|ID로 단건 조회|`findById()`|
|이메일 단건 조회|`findByEmail()`|
|존재 여부 확인|`existsByEmail()`|
|간단한 목록 조회|`findByStatus()`|
|간단한 조건 및 정렬|`findByStatusOrderByCreatedAtDesc()`|
|명시적인 JOIN|JPQL|
|Fetch Join|JPQL 또는 `@EntityGraph` 검토|
|복잡한 고정 조회 조건|JPQL|
|동적 검색 조건|QueryDSL|
|복잡한 DTO 조회|JPQL 또는 QueryDSL|
|DB 고유 기능 사용|Native Query|

**핵심은 메서드 네이밍과 JPQL을 경쟁 관계로 생각하지 않는 것이다.**

메서드 네이밍은 단순한 조회를 간결하게 표현하는 수단이며, JPQL은 쿼리 구조를 명시적으로 제어하기 위한 수단이다.

QueryDSL은 동적으로 변경되는 검색 조건을 관리할 때 유용하다.

따라서 실무에서는 각 방식의 장단점을 이해하고 조회 요구사항에 맞게 선택하는 것이 중요하다.

---

## ✏️ 메모

- 메서드 네이밍은 JPA 자체가 아니라 Spring Data JPA에서 제공하는 기능이다.
- JPQL은 엔티티를 기준으로 작성하며, 실제 SQL은 JPA 구현체가 생성한다.
- 메서드 네이밍과 JPQL은 동일한 SQL을 생성할 수 있으므로 작성 방식 자체로 성능 우위를 판단하지 않는다.
- 메서드 네이밍을 사용하더라도 실제 발생하는 SQL을 확인하는 습관이 필요하다.
- `Page`를 사용하는 조회는 Count Query가 추가로 발생할 수 있다.
- 연관 엔티티 필드 조건을 사용하더라도 자동으로 Fetch Join이 적용되지는 않는다.
