# 인기 검색어 순위

---

## 📄 본문
### 인기 검색어 순위 구현
인기 검색어 순위 기능은 실시간성과 성능 사이의 균형을 고려하여 Redis Sorted Set과 Cache Aside 전략으로 구현했다. 

초기 요구사항은 하루 동안 가장 많이 검색된 음식을 보여주는 기능이었다. 하지만 이후 요구사항이 실시간 인기 검색어로 변경되었다. 다만 팀원과 논의해보니, 사용자가 정확한 실시간 순위를 보는 것이 목적이 아니라 현재 어떤 음식이 많이 검색되고 있는지 대략적인 트렌드를 보여주는 것이 목적이었다. 즉, 엄격한 실시간성을 필요하지 않지만 조회 성능은 빨라야 하는 기능이라고 판단했다.

그래서 RedisSorted Set을 이용해 검색어를 집계했다. 검색이 발생할 때마다 현재 시간 기준의 분 단위 Sorted Set에 검색 횟수를 증가시키도록 했다. 그리고 최근 10분 동안의 Sorted Set을 합산한 인기 검색어 캐시를 별도로 생성했다. 조회 시에는 먼저 이 캐시를 조회하고, 캐시가 존재하면 그대로 반화하고, 없으면 최근 10분 데이터를 다시 합산하여 캐시를 생성한 뒤 반환하는 Cache Aside 전략으로 구현했다. 이렇게 해서 검색이 발생할 때마다 전체 순위를 다시 계싼하지 않고도 빠르게 인기 검색어를 제공할 수 있었다.

그 결과 사용자는 빠르게 인기 검색어를 조회할 수 있었고, 실시간에 가까운 트렌드도 함께 제공할 수 있었따. 또한 요구사항이 변경되더라도 Redis의 Sorted Set과 캐시 전략만으로 유연하게 대응할 수 있었고, 해당 경험을 통해 요구사항에 맞는 수준의 실시간성을 선택하는 것도 중요한 설계 요소라는 점을 배웠다.

### Redis
Key Value 구조의 비정형 데이터를 저장하고 관리하기 위한 저장소이다. 인메모리 데이터 구조를 가진 저장소이다. 인메모리는 주기억장치인 RAM에 데이터를 올려서 사용하는 방식이며, 하드디스크를 오고가는 과정을 거치지 않아도 되서 빠르다는 특징이 있는데, 따라서, 레디스 데이터를 디스크에 쓰는 구조가 아니라 메모리에서 데이터를 처리하기 때문에 속도가 빠르다. 하지만 RAM의 특성인 휘발성에 따라 데이터가 유실 될 수 있다.

레디스는 싱글 스레드이다. 한번에 하나의 명령만 처리할 수 있다. 그렇기 때문에 중간에 처리 시간이 긴 명령어가 들어오면 그 뒤에 명령어 들은 모두 앞에 있는 명령어가 처리될 때까지 대기가 필요하다. 따라서, 연산이 긴것을 조심해야한다. Get, Set 명령어의 경우 10만 TPS라는 성능을 자랑하기 때문에 부담이 없다.

#### 레디스를 사용한 이유
팀원 분이 재발급 토큰을 저장하기 위해 이미 사용중인 기술이였으며, 해당 자원의 sorted set을 이용하고 TTL을 활용하면 충분히 요구사항을 충족할 수 있다고 판단했다.

실시간성이 높고, 검색어를 타임스탬프 기준으로 더 정밀하게 집계해야하며, 검색/분석 기능 확장까지 고려했다면 Redis Sorted Set만으로 처리하기 보다 ElasticSearch 도입도 고려할 수 있었다.

#### 레디스 복구 전략
AOF(Append On File) 방식: 레디스의 모든 쓰기 갱신 연산 자체를 모두 log 파일에 기록하는 형태
RDB(Snapshotting) 방식: 순간적으로 메모리에 있는 내용 전체를 디스크에 담아 영구 저장하는 방식

#### 캐싱 전략
캐시 서버는 Look aside cache 패턴, Write Back 패턴이 존재한다.

Lokk aside cache
1. 클라이언트가 데이터를 요청
2. 웹서버는 데이터가 존재하는지 Cache 서버에 먼저 확인
3. Cache 서버에 데이터가 있으면 DB에 데이터를 조회하지 않고 Cache 서버에 있는 결과를 반환 (Cache Hit)
4. Cache 서버에 데이터가 없으면 DB에 데이터를 조회하여 Cache 서버에 저장하고 결과값을 클라이언트에게 반환 (Cache Miss)

Write Back
1. 웹서버는 모든 데이터를 Cache 서버에 저장
2. Cache 서버에 특정 시간 동안 데이터가 저장됨
3. Cache 서버에 있는 데이터를 DB에 저장
4. DB에 저장된 Cache 서버의 데이터를 삭제

즉, insert 쿼리를 한 번씩 500번 날리는 것보다 insert 쿼리 500개를 붙여서 한번에 날리는 것이 더 효율적이라는 원리이다. 이방식은 들어오는 데이터들이 저장되기 전에 메모리 공간에 머무르는데 이때 서버에 장애가 발생하여 다운된다면 데이터가 손실될 수 있다는 단점이 있다.

#### 레디스 자료구조
**String**: 일반적인 문자열 String-String으로되는 바이너리 데이터, JPEG, 이미지 등 저장 가능하다.
```shell
set <key> <value>
get <key> <value>
```

**Lists**: Array형식의 데이터 구조이며 데이터를 순서대로 저장한다.
- 추가/ 삭제/조회하는 것은 O(1)의 속도를 가지지만, 중간의 특정 index 값을 조회할 때는 O(N)의 속도를 가지는 단점이있다. 그러므로 head-tail에서 push, pop 연산을 통해 추가 삭제해야며, 따라서 Lists는 메세지 queue로 사용하기 적절하다. 

**Hashes**: 필드-벨류로 구성 되어있는 전형적인 hash의 형태이다. key 하위에 subkey를 이용해 추가적인 Hash Table을 제공하는 자료구조이다.
- 메모리가 허용하는 한, 제한 없이 필드들을 넣을 수 있다. 다만 명령어 비용 즉 네트워크 비용이 증가할 수 있으며, 해시는 필드별 TTL이 없어서 조심해야한다.

**Set**: 중복된 데이터를 담지 않기 위해 사용하는 자료구조이다. 유니크한 key값을 가지며, 데이터는 정렬되지 않은 상태이다. 중복된 데이터를 여러번 저장하면 최종 한번만 저장된다.
 - 모든 데이터를 전부 다 갖고올 수 있는 명령어가 존재함으로 사용에 주의해야한다.

**Sorted Sets**: Set에 score라는 필드가 추가된 데이터형이다. 일반적으로 Set은 정렬이 되어있지 않고 insert한 순서대로 들어간다. 그러나 Sorted Set은 Set의 특성을 그대로 가진 상태로 추가적으로 저장된 member들의 순서를 관리한다.
- 데이터가 저장될 때 부터 score 순으로 정렬되며 저장
- Sorted Set에서 데이터는 오름차순으로 내부 정렬
- value는 중복이 불가능하지만, score는 중복이 가능하다.

#### Sorted Set (ZSet)
Redis의 Sorted Set은 중복되지 않는 Member와 Score로 구성된 자료구조이다. Score를 기준으로 자동 정렬이 되며, 순위 조회나 랭킹 시스템 구현에 주로 사용된다.
```shell
Member Score
apple 100
banana 80
orange 50
```
Redis Sorted Set은 내부적으로 Hash Table과 Skip List를 함께 사용한다. HashTable은 member-> score 형태로 저장된다. 그렇기 때문에 특정 Member의 Score를 빠르게 조회 수정 할 수 있고 시간 복잡도는 O(1)이다.

Skip List는 Score 기준으로 정렬된 상태를 유지하는 자료구조이다. 순위 조회, 범위 조회, 정렬 기능을 담당한다.
```shell
apple(100)
	↓ 
banana(80)
	↓ 
orange(50)
```
레디스가 Hash Table과 Skip List를 같이 사용하는 이유는 Hash만 사용하면 member 조회 O(1)이 가능하지만, 순위 조회, 정렬 조회, 범위 조회가 어렵다. score 기준으로 정렬하기 위해 Skip List를 함께 사용해두는 것이다. 

반대로 Skip List만 사용하면 정렬 조회, 순위 조회는 쉽지만 특정 member 조회 score 수정이 O(log N)이 필요하다.

따라서 레디스는 Hash -> member 조회, Skip List -> 정렬/순위 조회 를 각각 담당하여 두 장점을 모두 활용한다.

##### Skip List
일반 연결 리스트는 원하는 데이터를 찾기 위해 처음부터 하나씩 순차 탐색해야한다.
A-B-C-D / O(N)
하지만 Skip List는 일부 노드에 여러 레벨의 포인터를 두어 중간 노드를 건너 뛸 수 있다.
```shell
A ---------> D
|            |
v            v
A -> B -> C -> D -> E
```
평균적인 시간복잡도는 다음과 같다.
- 탐색 : O(log N)
- 삽입 : O(log N)
- 삭제 : O(log N)

#### TTL
TTL은 레디스에서 특정 키의 유효기간을 설정하는 기능이다. TTL이 설정된 키는 지정된 시간이 지나면 자동으로 삭제된다. TTL 삭제 방식은 다음과 같다.

**Lazy 삭제**
- 키를 조회 할 때, 만료된 키를 발견하면 즉시 삭제
- 오래된 키가 남아 있을 수 있다는 단점 존재

**주기적 스캔 삭제**
- 레디스가 주기적으로 일정 비율의 키를 검사하고 만료된 키를 삭제한다.
- 정책에 따라 캐시가 꽉 차면 오래된 TTL 키를 먼저 삭제한다.
