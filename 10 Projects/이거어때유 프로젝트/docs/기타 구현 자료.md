# 기타 구현 자료

---

## 📄 본문
### SQS, Lambda, EventBridge 사용
이벤트 기반 아키텍처를 구성하여 비동기 처리와 주기적인 작업 실행에 활용했다. 수집된 데이터는 S3에 저장하여 영속적으로 관리했다.

#### EventBridge - 스케줄러 역할
EventBridge를 사용하여 크롤링 작업이 주기적으로 실행되도록 구성했다. 예를 들어 매일 한 번 또는 1시간마다 작업을 실행하도록 스케줄을 설정했다.

#### Lambda - 작업 실행 역할
EventBridge에 의해 트리거된 Lambda가 실제 크롤링 작업을 수행했다. Lambda는 카카오 지도 리뷰 크롤링, 데이터 가공, 다음 처리 단계로의 전달과 같은 비즈니스 로직을 실행했다.

#### SQS - 비동기 처리를 위한 메시지 큐
크롤링 결과를 SQS에 전달하여 후속 작업이 비동기적으로 처리되도록 구성했다. 작업 간 결합도를 낮추고, 일시적인 트래픽을 버퍼링하며, 특정 작업의 장애가 다른 처리 과정에 직접 영향을 주지 않도록 분리하는 역할을 담당했다.

#### S3 - 데이터 저장소
수집된 리뷰 데이터를 S3에 저장하여 영속적으로 관리했다. 파일 형태의 데이터를 저장하기에 적합하고, 대용량 데이터를 비교적 저렴한 비용으로 보관할 수 있어 사용했다.

### 카카오 지도 데이터 요청
여러 지도 플랫폼을 참고한 결과, 검색 시 일반적으로 30개 이하의 장소를 표시하는 경우가 많았다. 카카오 API의 경우 한 번의 요청으로 최대 15개의 장소를 조회할 수 있었다.

서비스 대상 지역이 대전이었고, 시내가 아닌 지역에서는 음식점 검색 결과가 30개를 모두 채우지 못하는 경우도 많았다. 따라서 먼저 1페이지를 요청한 뒤 응답 결과를 확인하고, 추가 데이터가 존재할 때만 2페이지를 요청하는 방식으로 불필요한 API 호출을 줄였다.

#### RestClient
`RestClient`는 Spring에서 HTTP API를 호출하기 위한 동기 방식의 클라이언트이다. 기존 `RestTemplate`을 대체할 수 있는 클라이언트로 등장했으며, 보다 직관적인 API를 제공한다.

따라서 카카오 API와 같이 단순한 요청·응답 방식의 외부 API를 호출하는 데 적합하다고 판단하여 `RestClient`를 사용했다.

#### WebClient를 사용하지 않은 이유
비동기 또는 논블로킹 처리가 필요한 요구사항이 없었고, 단순한 요청·응답 구조였기 때문에 동기 방식인 `RestClient`로 충분하다고 판단했다.
