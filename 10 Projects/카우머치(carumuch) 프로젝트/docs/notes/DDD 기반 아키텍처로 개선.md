# DDD 기반 아키텍처로 개선

---

## 📄 본문
### DDD 기반 아키텍처 개선
당시 프로젝트는 이어폰 선이 꼬인것 처럼 의존성이 꼬여있는 유지보수하기 힘든 구조였다. "사고 레포트 작성 -> 견적서 작성 -> 공개 입찰"로 이어지는 복잡성 때문에 서비스 계층은 비대해졌고, 수정하고자 하니 변경의 전파를 가늠할 수 없었다.

A가 B를 의존한다는 것은 B의 변경에 A가 영향을 받는다는것 이다. 그래서 가장 먼저 Global 패키지와 다른 도메인 패키지의 의존성을 단방향으로 흐르도록 재설계했다. 이 과정에서 예상보다 많은 수정이 발생했고 프로젝트 전체가 강하게 결합되어 있다는 사실을 체감했다.

이문제를 해결하기 위해 DDD를 학습하고 적용했다. 각 도메인이 자신의 비즈니스 규칙을 직접 책임지도록 변경했고 DIP를 적용해 구현보다 인터페이스에 의존하도록 구조를 개선했다. 그 결과 새로운 기능을 추가하거나 정책을 변경할 때 영향을 받는 범위를 예측하기 쉬워졌고, 무엇보다 "이 로직을 어디에 작성해야 하는지"에 대한 기준이 명확해져 유지보수성이 크게 좋아졌다.

### DDD
DDD는 도메인 주도 설계를 뜻한다. 비즈니스 도메인에 깊이 집중하여 소프트웨어를 설계하는 방법론이다. 비즈니스 요구사항을 도메인 모델로 표현하고, 도메인의 책임과 역할을 명확히 반영하는것을 목표로 한다. 도메인 모델을 설계하고 나면 역할과 책임이 코드에 자연스럽게 반영이 되는데, 코드가 곧 문서화라는 철학과 연결된다. DDD에서는 별도의 문서 없이도 코드만으로 시스템의 설계와 동작을 이해할 수 있게된다는 특징이 있다.

Aggregate로 업무를 할당하고 Bounded Context를 이용해 업무간의 겅계를 명확하게 구분하여 여러 비즈니스 도메인들 간의 협력을 통해서 최종 기능을 완성 시킴으로써 결합도는 낮추고 응집도는 높이는 개발방법론이다.

#### point
##### 도메인
큰 의미로 문제를 해결하고자 하는 비즈니스 영역을 의미한다. 작은 의미로는 비즈니스를 구성하는 하나의 요소(업무, 모듈)로써, 유사한 업무의 집합체를 말한다.

##### 이벤트 스토밍
비즈니스의 프로세스의 트리거가 되는 핵심 이벤트를 큰 서브젝트에 정의하고, 그 이벤트 중심의 정책이나, 어그리게이트 등 을 정의한다. 흐름은 이벤트가 흘러가는 시간 기준으로 진행한다.

##### 데이터 중심 설계 vs 도메인 주도 설계
데이터 중심의 설계를 진행하면 트랜잭션 스크립트 패턴으로 서비스 계층에 비즈니스를 구현하게 되는데, 그렇기 때문에 서비스 계층이 비대해진다. 복잡하고 큰 규모가 아니라면 간단하기에 데이터 중심 설계가 좋은 선택일 수 있다. 하지만, 변경이나 확장에는 취약하기에 주의가 필요하다.

DDD 구조는 비즈니스 도메인 중심으로 설계를 진행하기에, 초기 구현의 시간이 상대적으로 더 소모 될 수 있지만, 변경이나 확장에 효과적인 방법론이다.

즉, 고객의 니즈가 빠르게 변화하거나 규모가 커, 변경의 전파에 리스크가 있다면 DDD가 효과적일 수 있다.

##### DDD 강조
고객의 니즈는 과거보다 매우 다양해졌고 빠르게 변하기 때문에 DDD가 강조되고 있다. 그리고 단순히 비개발자 직군이 작성한 요구사항 정의서만 보고 기능을 구현하는 것은 어렵다. 왜냐하면 비즈니스의 복잡성으로 인해 도메인의 의도와 목적을 정의서만을 통해서 전달할 수는 없기 때문이다.

또한, 빠르게 변하는 비즈니스의 속도에 발 맞춰서 어플리케이션도 변화에 적을 할 수 있어야한다. 즉, 변경이 쉬운 어플리케이션 구조와 설계가 요구되고 있기에 시장에서 DDD가 강조되고 있다.

##### 도메인 계층
도메인 계층은 도메인의 핵심 규칙을 구현한다. 업무 규칙을 도메인 모델에 위치시키는 이유는 규칙을 바꾸거나 확장할 때 다른 코드에 영향을 덜 주고 모델에 반영할 수 있기 때문이다.

###### 도메인 언어 vs 유비쿼터스 언어
도메인에서 사용하는 용어는 매우 중요하다. 아래는 OrderState enum을 도메인 용어로 작성한 예이다.
```java
public enum OrderState {
	PAYMENT_WAITING, PREPARING, SHIPPED, DELIVERING, DELIVERY_COMPLETED
}
```

유비쿼터스언어는 도메인 주도 개발에서 강조된 용어이다. 관계자, 개발자 등 도메인과 관련된 공통의 언어를 만들고 이를 대화, 문서, 모데인 모델, 코드, 테스트 등 모든 곳에서 일관된 용어를 사용하게 한다. 이를 통해 소통 과정에서 오는 용어의 모호함을 줄일 수 있고 개발자는 도메인과 코드 사이에서 불필요한 해석을 줄일 수 있다.

적절한 용어를 영단어로 치환해 코드로 표현하는 것은 어렵지만 시간을 들여 찾는 노력을 해야한다.

###### 개념 모델
개념 모델은 순수하게 문제를 분석한 결과로 DB, 성능, 기술을 고려하지 않는다. 그래서 개념 모델을 구현 가능한 모델로 전환하는 과정을 거쳐야만 한다. 처음 부터 완벽한 개념을 만드는것을 거의 불가능하다.

이는 프로젝트를 진행하면서 도메인을 더 잘 이해함에 따라 다른 의미로 해석되는 문제가 발생하지 않도록, 전반적인 개요를 알 수 있는 수준으로 개념 모델을 작성해야한다.

구현하는 과정에서 개념 모델을 DB, 성능, 기술까지 고려한 구현 모델로 점진적으로 발전 시켜나가야한다.

###### 도메인 영역의 주요 구성 요소

| 요소      | 설멍                                                                                    |
| ------- | ------------------------------------------------------------------------------------- |
| 엔티티     | 고유의 식별자를 갖는 객체로 자신의 라이프 사이클을 갖고 도메인의 고유한 개념을 표현한다. 도메인 모델의 데이터를 포함하며 관련된 기능을 함께 제공한다. |
| 밸류      | 식별자를 갖지 않는 객체로 주로 개념적인 하나의 값을 표현할 때 사용된다. 엔티티의 속성 또는 다른 밸류 타입의 속성으로도 사용할 수 있다.        |
| 애그리거트   | 연관된 엔티티와 밸류 객체를 개념적으로 하나로 묶은 것이다.                                                     |
| 리포지터리   | 도메인 모델의 영속성을 처리한다.                                                                    |
| 도메인 서비스 | 특정 엔티티에 속하지 않은 도메인 로직을 제공한다. 도메인 로직이 여러 엔티티와 밸류를 필요로 하면 도메인 서비스에서 로직을 구현한다.           |

###### 엔티티와 벨류
도메인 모델은 크게 엔티티와 벨류로 구분한다. 엔티티의 가장 큰 특징은 식별자를 가진다는것이다.
벨류 타입은 완전한 하나를 표현할 때 사용한다. "돈"이라는 개념을 표현한 Money는 벨류 타입이다. 벨류 타입은 "돈"이라는 개념을 명확하게 표현하여 코드에 대한 이해를 높이고 있다. 벨류타입을 위한 기능을 추가할 수 도 있으며, 벨류 객체는 불변객체로 구현해 사용하기를 선호한다.
```java
    public class Money {
    	private int value;
    
    	// ...
    
    	public Money add(Money money) {
    		return new Money(this.value + money.value);
    	}
    
    	public int getValue() {
    		return this.value;
    	}
    }
    
    public class OrderLine {
    	private Money price;
    	// ...
    }
```

##### 어그리게이트
어그리게이트는 복잡한 도메인을 이해하고 쉽게 관리하기 위해 상위 수준에 서 모델을 바라보기 위한 방법이다. 도메인 관계를 파악하기 어렵다는건 코드를 변경하고 확장하는것이 어려워진다는것이다. 그렇기에 어그리게이트 단위로 일관성을 유지하며 관리해야한다.

어그리게이트는 경계를 갖는다. 한 어그리게이트에 속한 객체는 다른 어그리게이트에 속하지 않는다. 경계설정의 기본은 도메인 규칙과 요구사항이다. 함께 생성되는 요소는 한 어그리게이트일 가능성이 높다. 상품 개수, 배송지 정보, 주문자 정보는 “주문”과 함께 생성되므로 한 어그리게이트이다. 

“A가 B를 갖는다”라고 해서 무조건 한 어그리게이트는 아니다. 상품과 상품 리뷰는 함께 생성되지도 않고, 함께 변경되지도 않는다. 그렇기 때문에 서로 다른 어그리게이트를 독립적으로 갖게 된다

어그리게이트 루트는 어그리게이트 내부의 다른 객체를 조합해서 기능을 완성한다. 어그리게이트 루트가 구성 요소의 상태를 참조하는것 뿐만 아니라 기능실행을 위임하기도한다.

한 트랜젝션에서는 한 개의 어그리게이트만 수정해야한다. 즉, 한 어그리게이트는 최대한 서로 독립적이어야한다. 다른 어그리게이트의 상태까지 관리하게 되면 어그리게이트 간 결합도가 높아지고 유지보수 비용이 증가한다.
만약 한 트랙젝션에서 두개 이상의 어그리게이트를 수정해야한다면 application 계층에서 두 어그리게이트를 수정하는 로직이 들어가도록 구현해야한다.

##### 바운디드 컨텍스트
카테고리에서 "상품", 재고 관리에서의 "상품", 주문에서의 "상품"은 이름만 같지 실제 의미하는 것은 다르다. 모델은 특정한 컨텍스트 안에서 완전한 의미를 갖는다. 이 경계를 DDD에서는 바운디드 컨텍스트라고 부른다. 모든 바운디드 컨텍스트를 반드시 도메인 주도로 개발 할 필요는 없다. 한 바운디드 컨텍스트에서 여러 방식을 혼합해서 사용할 수 있으며, 서로 다른 구현 기술을 사용할 수 있다.

###### 작은 규모의 바운디드 컨텍스트
카우머치 프로젝트는 각 영역의 팀이 달라서 언어가 달라지고 의미가 달라질 정도의 규모는 아니기에 바운디드 컨텍스트로 나누지 않았다. 도메인 모듈 단위로 묶어서 경계를 만들었다. vhicle 패키지 내에 서로 다른 생명주기인 report를 포함해 각자 어그리게이트 루트로 바라보도록 설계했다. 어그리게이트 루트 경계에서 중요한 것은 "서로 생명주기가 다른가"이기 때문이다.

### DDD 계층
DDD는 presentation, application, domain, infrastructure라는 4개의 영역으로 구성된다.

#### point
##### presentation 영역
사용자의 요청을 받아 application 영역에 전달하고 결과를 전달하고 결과를 받아 다시 사용자에게 보여주는 역할을 한다. 스프링 MVC 프레임워크가 presentation 영역을 위한 기술이며, presentation의 사용자는 사람일 수도 있고 API를 호출하는 외부의 시스템일 수도 있다.

##### application
application 영역은 시스템이 사용자에게 제공해야할 기능을 구현한다. application 영역은 기능 구현을 위해 domain영역의 domain 모델을 사용한다.

##### domain
도메인 영역은 도메인 모델을 구현한다. 도메인 모델은 도메인의 핵심 로직을 구현한다.

##### infrastructure
infrastructure는 논리적 개념을 표현하기보다 실제 구현 기술에 대한것을 다룬다. (RDBMS, 메세지 큐, Redis 등) domain, application, presentation 영역은 구현 기술을 사용한 코드를 직접만들지 않는다.

### DIP
"구현체에 의존하지말고 추상체에 의존하라" 즉 고수준 모듈이 저수준 모듈에 직접 의존하지 않고 추상화에 의존하도록 만드는 원칙이다.

#### point
##### 고수준 모듈 vs 저수준 모듈
고수준 모듈은 무엇을 할것인가에 따른 비즈니스를 담당한다. CalculateDiscountService라는 클래스에 calculateDiscount()라는 기능이 있다고 가정한다면, "할인 금액을 계산한다"에 관심이 있지, 어떤 엔진을 쓰는지 관심이 없다. 즉, "할인을 해야한다"라는 비즈니스적 정책을 담당함으로 고수준 모듈이다.

저수준 모듈은 실제로 일을 시킬 구체적인 구현체이다. "어떻게 할인할 것인가"에 관심이 있는 영역이다.
즉, 고수준 모듈은 비즈니스 정책을 담당하는 코드이고, 저수준 모듈은 그 정책을 실제로 수행하는 구체적인 구현체이다.

##### 주의사항
단순히 인터페이스와 구현 클래스를 분리하는 정도로 받아들이면 안된다. 인터페이스의 위치가 저수준 모듈이 아닌 고수준 모듈에 위치해야한다. 저수준 모듈에 인터페이스가 위치하게 되면 여전히 고수준 모듈이 저수준 모듈을 의존하는 형태가 된다.

쉽게 말해 service와 service가 의존하는 인터페이스는 고수준 모듈로서 한 패키지에 있어야하고 언터페이스의 구현체인 세부 사항은 저수준 모듈의 패키지에 위치해야만 한다.
