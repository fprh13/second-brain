# AOP Filter Logging 모니터링

---

## 📄 본문
### AOP 로깅 모니터링
졸업 작품 전시회에서 실제 사용자들이 서비스 체험하던 중 오류가 발생했다. 문제는 당시에는 모든 예외를 동일한 에러 로그로 남기고 있었기 때문에 정말 중요한 서버 오류가 수 많은 클라이언트 오류에 묻혀버렸다는 점이다.

결국 실제 장애가 발생했는데도 어떤 로그가 중요한지 구분하지 못했고, EC2에 접속해서 Docker 컨테이너 로그를 직접 뒤져봤지만 원인을 빠르게 찾지 못했다.

그래서 이후에는 예외를 성격에 따라 분리했다. 클라이언트 요청 오류는 warn 수준으로 기록하고 실제 비즈니스 오류나 서버 장애는 에러로 기록하도록 변경했다. 또한 로그만 분리해서는 부족하다고 생각했다. 하나의 요청에서 발생한 로그를 모두 추적할 수 있어야 장애 분석이 가능했기 때문에 MDC를 이용해 요청마다 TraceId를 생성하도록 구현했다.

이 TraceId를 로그에 함께 남기고 수집하여 Grafana에서 하나의 요청 흐름 단위로 로그를 조회할 수 있는 환경을 구축했다. 그 결과 장애가 발생했을 때 어떤 요청에서 어떤 예외가 발생했는지 빠르게 확인할 수 있었고, 운영 중 원인 분석 속도를 크게 높일 수 있었다.

이 경험 이후에는 기능을 개발햇을 때도 예외를 단순히 처리하는 것이 아니라 운영자가 빠르게 장애를 찾을 수 있는 형태로 설계하는 것을 항상 함께 고려하게 되었다. 운영 가능한 서비스를 만드는 것도 백엔드 개발자의 중용한 역할이라고 생각한다.

### Spring AOP
AOP는 관점 지향 프로그래밍이다. 특정 부가 기능을 어디에 적용할지 정의해 놓는 것을 Aspect라고 하는데 이런 Aspect를 사용한 프로그래밍 방식을 AOP라고 한다. 핵심 기능(종단 관심사)와 부가 기능(횡단 관심사)를 효율적으로 처리하기 위해 나온 프로그래밍 방식이다.

### MDC
MDC는 스레드 단위로 데이터를 읽고 쓸 수 있는 기능이다. MDC를 사용하면 멀티스레드 환경에서 각 스레드의 실행 컨텍스트를 구분할 수 있어서 모니터링 시 추적에 용이하다. 예를 들어 멀티 스레드 환경에서는 요청 순서대로 로그가 찍히지 않고, 로그가 섞여서 쌓이게 되므로 동일한 스레드의 컨텍스트를 추적하기 위해 MDC를 사용한다.

MDC는 대부분의 로깅 라이브러리와 이미 통합되어 있기 때문에 개발자가 손쉽게 적용하여 사용할 수 있다. MDC를 사용하면 로그에 필요한 컨텍스트 데이터를 자동으로 추가할 수 있다는 장점이있다.

#### point
##### 스레드 로컬
ThreadLocal은 Thread 안에서 사용하는 저장공간이다. 스레드별로 따로 저장되며, 행동은 하지 않고 오직 저장하는 용도이다. 스레드 Thread Poll로 재활용도니다. 그래서 반드시 메모리 누수가 일어나지 않도록 요청이 끝나면 값을 지워야한다.

##### MDC vs 스레드 로컬
사실 MDC는 내부적으로 스레드 로컬을 사용하고 있어서 별도로 스레드 로컬을 선언할 필요없이 MDC를 바로 사용하면 된다.

##### 왜 MDC를 스레드 로컬 대신에 사용하는가
로킹 작업에서는 MDC가 더 적합하다. MDC는 로깅을 목적으로 설계되었기 때문에 로그 데이터에 추가적인 컨텍스트 데이터를 제공하는데 최적화 되어있다. 예를들어, 로깅시 스레드 로컬을 사용하면 로그 메시지를 생성할 때 매번 스레드 로컬에서 데이터를 꺼내어 로그 메세지에 추가해야한다. 반면 MDC는 컨텍스트 데이터를 자동으로 로그 메세지에 포함 시키므로, 개발자 코드 상에서 매번 데이터를 추출하고 로그 메세지에 추가하는 번거로움을 줄일 수 있다.

이유는 MDC는 로깅 시스템과 통합되어 있기 때문이다. 따라서, 개발자가 직접 스레드 별로 로깅 컨텍스트를 관리할 필요가 없다. MDC에 데이터를 설정하면 로깅 라이브러리가 자동으로 해당 스레드의 로그 메세지에 MDC 데이터를 포함 시킨다. 이는 매번 로그를 찍을 때 수동으로 컨텍스트 데이터를 추가해야하는 번거로움을 줄여준다.

### 로그백
로그백은 자바 애플리케이션을 위한 로깅 프레임워크이다. SLF4J의 공식 구현체 중 하나이다. Spring boot에서 기본 로깅 구현체로 채택되어, 애플리케이션에서 발생하는 로그를 콘솔, 파일, 외부 시스템 등으로 출력할 수 있도록 지원한다.

#### point
##### 로그백 전략
- 날짜별로 파일 분리
- 같은 날짜안에서 100MB를 넘으면 파일 분할
- 최근 5일치만 보관
- 전체 로그 용량이 500MB를 넘으면 오래된 로그부터 삭제

### Grafana
오픈소스 데이터 시각화/모니터링 툴이다. 무료 버전으로도 기본적인 시각화가 가능하다. 다른 오픈소스 도구 호환성이 좋으며, 쿼리 형식으로 데이터를 수집하기 때문에 SQL언어와 사용법이 비슷하다. alert 기능을 제공하기 때문에 특정 상황에 알림을 받게 끔 설정할 수 있다. 대시보드 라이브러리가 잘되어있으며, 단독으로 상요하기 어려워 서버 모니터링을 위해서는 외부 도구에 의존해야한다.

#### point
##### 데이터독과 차이
데이터독의 경우 데이터를 직접 저장하고 있는 것과 달리 그라파나는 외부 데이터 소스를 정의하고 해당 데이터 소스에 쿼리 데이터를 동적으로 가지고 와서 시각화 한다는 점이 차이가 있다.

데이터독에서 AWS 서비스를 연동하면 클라우드 와치의 매트릭 데이터를 일정 주기로 가져와서 데이터 독 데이터베이스에 저장한다. 이때문에 데이터독을 사용하는 경우 클라우드와치의 실시간 데이터와 15분 정도의 시차가 발생한다.

### Loki
로키는 로그 집계 시스템이다.로깅 및 이벤트 데이터 수집, 저장 및 검색을 하기 위한 오픈소스 플랫폼이다. 비용을 효율적으로 운영하기 쉽게 설계 되어있다. 로키는 로그 전체 TEXT가 아닌 metadata만 인덱싱하는 방식 취한다.

로키를 위해 만들어진 로그 수집 도구인 Promtail을 통해 로그를 가져와 로그를 저장한다. 이후 LogQL이라는 쿼리 언어를 통해 로그를 검색하게 된다. 그라파나와의 원활한 통합을 통해 강력한 시각화와 분석 기능을 제공한다.

#### point
##### 각 역할 체크
Promtail -> 각 서버에서 생성되는 로그백 로그 파일을 수집하여 Loki로 전송
Loki -> Promail을 통해 수집된 로그를 저장하면, 로그 본문은 chunk형태로 저장하고 메타데이터는 index로 관리한다.
grafana -> Loki를 데이터소스로 등록하고, LogQL을 사용해 로그를 조회 및 시각화한다.

### Promtail
Promtail은 Grafana Loki와 함께 사용되도록 Grafana Labs에서 공식으로 제공하는 외부 로그 수집기이다. 서버의 생성된 로그 파일을 수집하여 Loki로 전송하는 역할을 수행한다.

### Grafana + Loki + Promtail
로그 수집, 저장, 조회까지의 흐름이 일관된 설계 철학을 가지며, 설정과 운영 복잡도를 최소화할 수 있었기 땜누이다.

#### point
##### Promtail과 Loki의 자연스러운 결합
- 동일한 Label 개념
- Prometheus 스타일 설정
- 불필요한 파싱/변환 최소화
로그 수집 단계에서 **과한 복잡도 없음**

##### Grafana 단일 UI에서 통합 관측
- 로그 (Loki)
- 메트릭 (Prometheus)
- 커스텀 비즈니스 메트릭
**한 화면에서 장애 분석 가능**

##### 단계적 확장 가능성
- 현재: 로컬 스토리지
- 운영: S3 Object Storage
- 수집기 교체 가능 (Promtail → Fluent Bit)
**PoC → 운영 확장 경로 명확**

### Spring Actuator
애플리케이션의 상태를 모니터링, 메트릭 수집을 위한 HTTP Endpoint를 제공해주는 모듈이다. Spring boot 애플리케이션의 모니터링 및 관리 기능을 제공하는 라이브러리로, 개발자 애플리케이션의 상태와 운영 정보를 쉽게 확인하고 관리할 수 있도록 도와준다.
특히 어플리케이션의 상태와 성능 관련 데이터를 자동으로 수집하고 노출함으로써, 별도의 코드 작성 없이 JVM 메모리 사용량, CPU 사용률, 스레드 상태, 데이터베이스 커넥션 상태 등을 손쉽게 모니터링 할 수 있다. Acuator는 Spring과 Prometheus간의 통합을 간단하게 처리하여, 시스템 성능 모니터링과 운영 관리의 복잡성을 크게 줄여준다.

### 프로메테우스
Prometheus는 시스템의 상태를 수자 데이터(메트릭)로 수집하고 저장해서 모니터링과 알림으르 가능하게 하는 시계열 기반 모니터링 시스템이다.

#### point
##### 어떤 매트릭을 확인했는가
- 요청 수 (http_requests_total)
- 응답 시간 (latency)
- 에러율
- CPU / 메모리
- DB 커넥션 수
- AI 견적 처리 실패 카운트

### Filter
필터는 디스패처 서블릿에 요청이 던달되기 전/후 url 패턴에 맞는 모든 요청에 대해 부가 작업을 처리할 수 있는 기능을 제공한다. 디스패처 서블릿은 스프링의 가장 앞단에 존재하는 프론트 컨트롤러이므로, 필터는 스프링 컨테이너 범위 밖에서 처리가 되는것이다. 즉, 스프링 컨테이너가 아니 톰켓 같은 WAS에 의해 관리가 된다.

#### point
##### doFilter()
doFilter()는 url-pattern에 맞는 모든 http요청이 디스패처 서블릿으로 전달되기 전에 웹 컨테이너에 의해 실행되는 메소드이다. doFilter의 파라미터로는 FilterChain이 있는데, FilterChain의 doFilter를 통해 다음 대상으로 요청을 전달하게 된다.

예시: 로그 수행 (시큐리티에 도달하기 전에 수행해야하기에 시큐리티 필터의 기본값 @Order-100보다 작아야 처리된다.)
