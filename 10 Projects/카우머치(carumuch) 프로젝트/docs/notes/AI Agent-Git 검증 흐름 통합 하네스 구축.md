# AI Agent-Git 검증 흐름 통합 하네스 구축

---

## 📄 본문
### AI Agent, Git 검증 흐름 통합 하네스 구축
개발자가 직접 작업할 때는 Git의 Pre-commit을 이용하여 개발자의 코드가 문제 없는지 검증했습니다. 검증 시 문제가 발생하면, 스스로 문제를 식별하고 수정하고 다시 검증을 해야했습니다.

이후, 개발을 진행할 때 AI Agent를 활용하고자 했다. 개발자가 검증을 받고 실패 시 문제를 직접 수정하듯 AI Agent가 한명의 개발자 처럼 작업하고 검증 받고 검증 시 문제가 발생하면, 스스로 문제를 수정하고 재검증 받아야한다고 생각했다.

따라서 오케스트레이터를 구성해서 반복 루프 구조를 만들었다. Pre-commit에 사용되는 검증 스크립트를 통과하지 못하면 스스로 문제를 수정하고 재검증을 받도록 하는 구조였다.

하네스의 핵심은 규칙을 "권장"하는 것이 아닌 "강제"하는 것이었다. Skills와 Sub-Agent만으로는 검증 정책을 완전히 강제하기 어렵기 때문에,Hooks를 사용해 성공한 검증 스크립트 실행 기록이 없으면 작업이 종료되지 않고 수정 루프로 되돌아가도록 구성했다.

저와 동일하게 AI Agent가 한명의 개발자로 동일한 검증 환경에서 개발할 수 있는 환경을 세팅했다.

### 하네스
하네스는 에이전트가 실수를 할 때마다 그 실수가 다시는 반복되지 않도록 엔지니어링 하는것을 의미한다. 하네스의 핵심 철학은 에이전트에게 "권장" 혹은 "부탁"하는 것이 아닌 에이전트 행동을 "강제"한다는 점이다.
실수가 발생했을 때 프롬프트를 수정하여 다시 부탁하는것이 아닌, 그 실수 자체가 구조적으로 불가능하도록 시스템을 설계해야한다는 것이다.
하네스를 잘 구축하면, AI 컨텍스트 창이 꽉차면 이전 내용을 잊어버리거나 작업을 조기 종료하는 현상인 컨텍스트 부패를 해결할 수 있으며 AI가 정보를 알고 있음에도 엉뚱한 행동을 하는 규칙과 울타리 문제를 해결할 수 있다.

### 해당 환경의 장점
AI Agent가 카우머치 팀에 한명의 개발자로서, 같은 검증 환경을 기반으로 작업하니 AI가 산출하는 코드에 신뢰성이 올라갔다.

### 컨텍스트 관리 방법
Open AI에서 권장하기로는 AGENTS.md로 지도를 제공하라고 한다. 60줄 정도의 핵심이 되는 문서로 구성하고 연관 된 문서는 따로 정리해두어, 지도를 보고 따라갈 수 있게 하라고 한다.

AGENTS.md를 지도로 구성하고 세부 사항을 별도 문서로 정의하여 컨텍스트를 관리한다. 물론 컨텍스트 사용량의 차이가 많지 않지만, 컨텍스트가 쌓인 전 후 상관없이 문서 구분한 에이전트의 작업의 질이 좋았다. 즉, 모델의 집중력이 흐트러져서 추가되는 컨텍스트를 생각하면, 불어나는 컨텍스트를 줄이는 효과가 있다.

#### 세부 문서의 유무에 따른 사용 토큰 차이
세부 문서가 있는 경우 분석 결과의 질이 높았으며, 컨텍스트 사용량은 세부 문서가 큰 영향을 주지 않는다.

```
1. 전체 프로젝트 파악 해서 알려줘
2. XXX 수정 기능 분석해줘
3. XXX 수정 기능에 개선해야될 부분을 알려줘
```

### 개발 방법론
가장 많은 인사이트를 얻게 되었던 인프런에서 진행한 하네스 챌린지에서 실제 회사에서 쓰고 있는 하네스를 보여주었다. SDD 형식을 prase를 나눠서 흐름대로 처리하되 각 작업은 티켓 형식으로 만들어서, TiDD 형태로 AI Agent 개발을 시켰다. 환경은 커서와 Chat GPT를 이용했다.

카우머치 프로젝트는 리펙토링 프로젝트로서 리펙토링 사항이 발견되면 이슈를 생성하고 이슈에 맞는 작업을 수행합니다. 따라서 TiDD라고 불리는 티켓 주도 개발을 적용해서 사용중이다. 이슈를 기반으로 AI가 티켓을 만든다. AI가 티켓을 만드는 이유는 개발자가 작성한 이슈를 AI가 이해하기 쉬운 형식으로 변환하기 위함이다.

즉, TiDD 스킬을 사용하면 카우머치 검증 하네스로 구축된 개발 싸이클 흐름대로 해당 티켓을 개발하는 메커니즘이다.

### 검증 스크립트
통합 테스트를 제외한 전체 테스트를 돌린다. 통합 테스트 영역에 수정이 있을 때만 전체 테스트를 한다. push 이후에는 CI 과정에서 전체 테스트 및 커버리지 측정을 하고 AI를 통해 코드 포멧과 회귀 문제 등을 검증합니다. push 전 최소한의 검증 게이트 역할로 현재는 검증 스크립트가 구성되어있다.

### 병렬처리 유무
cmux를 이용해서 worktree를 분리하고 진행한다. 각 워크 트리에 각 오케스트레이터가 각 에이전트들을 일을 시키고 하네스 검증 정책을 통과 시켜둔다. 티켓 그대로 개발, + 유지보수성을 최대한 고려 이렇게 A- B로 서로다른 터미널 pane에서 2명의 에이전트 작업을 한다. 그 중에서 가장 마음에 드는것을 선택한다.

이렇게 병렬처리로 더 나은 선택지를 고르자니, 토큰 소모량이 Open AI Plus 모델로는 부담이 매우 컸다.
그리고 티켓 그대로 개발을 시켜도 컨텍스트 참조 파일에 코드 스타일 가이드가 있는데, 그걸 기반으로 하다보니, 기본적으로 유지보수성을 고려한 설계가 되었고, A B의 결과 차이가 거의 없는 수준이었다.

비용 대비 효옹 ROI가 굉장히 좋지 않았다. 병렬처리를 하던 모든 부분을 제외하고, 단일 에이전트가 루프에 맞게 수행하도록 변경했다.
