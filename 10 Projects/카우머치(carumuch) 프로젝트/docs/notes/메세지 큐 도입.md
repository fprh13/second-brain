# 메세지 큐 도입

---

## 📄 본문

### 메시지 큐 도입 이유

기존 구조에서는 클라이언트에서 작성된 사고 레포트를 바탕으로 AI 서버에서 견적서를 생성한다. AI 견적서를 받아온 뒤 프론트엔드에서 백엔드로 다시 요청하여 최종 저장되는 구조였다.

이 구조에서 발견된 문제는 다음과 같다.

1. 사용자가 AI 처리가 완료될 때까지 대기해야 한다.
2. 사용자 이탈 시 데이터가 최종 저장되지 못하고 유실될 수 있다.
3. 사용자 이탈로 최종 저장되지 않는 경우에도 AI 처리가 수행되어 리소스 낭비가 발생할 수 있다.

그래서 사고 레포트 저장과 AI 견적 생성을 분리하고, 클라이언트가 AI 서버에 직접 요청하는 것이 아닌 백엔드를 통해 처리하도록 변경했다.

단일 API로 백엔드 서버에 사고 레포트를 저장하면 이후 AI 견적서가 생성되고, 해당 AI 견적서를 기반으로 공개 입찰이 진행되는 구조이다.

### 진행 방법

사고 레포트 등록 이후 AI 견적 생성을 비동기로 처리했다. 전체 흐름은 다음과 같다.

1. 사용자가 사고 레포트를 등록한다.
2. 서버는 견적 생성을 즉시 수행하지 않고 견적 요청 메시지를 RabbitMQ의 요청 라우팅 키로 발행한다.
3. 별도로 분리된 Worker 서버가 해당 메시지를 소비하여 이미지 분석과 견적 계산을 수행한다.
4. 처리가 끝나면 Worker가 견적 결과 메시지를 RabbitMQ의 응답 라우팅 키로 발행한다.
5. 메인 서버의 리스너가 해당 결과 메시지를 받아 DamageReport를 조회하고, 최종적으로 Estimate 엔티티를 저장한다.

즉, 사용자 요청과 응답 흐름에서 무거운 AI 처리 작업을 분리하고, 메시지 브로커를 통해 메인 서버와 Worker 서버를 느슨하게 연결한 구조이다.

### 메시지

메시지의 의미는 우리가 일상에서 사용하는 스마트폰 문자 기능과 같다.

문자를 작성하고 전송하고 수신하는 과정이 있을 것이다. 문자를 전송하는 사람은 문자를 보냈다는 사실이 중요하고, 문자를 수신하는 사람은 문자를 받았다는 사실이 중요하다.

문자를 작성하고 전송하는 과정은 발신자의 관심사가 되고, 문자를 수신하는 것은 수신자의 관심사가 된다.

메시지 큐에서도 생산자(Producer/Publisher)와 소비자(Consumer)가 나뉜다. 생산자는 메시지를 발행하는 역할을 담당하고, 소비자는 해당 메시지를 수신하여 처리하는 역할을 담당한다.

### Queue

큐는 FIFO(First In First Out), 즉 선입선출 구조이며 대기열이라고도 불린다.

수강 신청이나 티켓팅 등 서비스에 여러 이용자가 몰리면 "1000명이 앞에 대기 중입니다."라는 안내문을 볼 수 있다.

이처럼 서비스의 처리 속도가 이용자의 요청 속도를 따라갈 수 없을 때, 앞선 요청들을 처리하는 동안 대기하는 요청들을 잠시 큐에 담아두고 먼저 들어온 순서대로 처리하는 것이 예시이다.

다만 메시지 큐에서는 여러 소비자가 병렬로 메시지를 처리할 수 있으므로, 메시지가 큐에 들어온 순서와 실제 처리가 완료되는 순서가 반드시 일치하지는 않는다.

#### 큐를 사용한 이유

1. 메시지를 안정적으로 전달하고 처리하기 위해 사용
2. 요청이 급증했을 때 작업을 큐에 적재하여 처리 부하를 조절하기 위해 사용

#### 메시지 큐

생산자의 요청 정보를 바로 소비자에게 전달하는 것이 아닌, 큐에 저장해 두었다가 소비자가 처리할 수 있을 때 전달하는 시스템이다.

이를 통해 생산자와 소비자 간의 처리 속도 차이를 완화할 수 있으며, 각자가 담당하는 역할(발행, 소비)에 집중할 수 있으므로 서비스 간 결합도가 낮아지고 작업을 효율적으로 처리할 수 있다.

##### 비동기 / 동기 (결과를 어떻게 받는가?)

**동기(Synchronous): 작업의 완료를 기준으로 다음 작업을 진행하는 방식**

![[../../../../attachments/screenshots/동기.png]]

동기는 요청한 작업의 완료 여부에 맞춰 다음 작업을 진행하는 방식이다.

작업이 완료된 후 다음 작업을 진행하므로 처리 흐름이 직관적이고 순서를 관리하기 쉽다.

다만 작업 완료를 기다리는 동안 다음 작업의 진행이 지연될 수 있다.

동기 방식 자체가 스레드를 반드시 멈추게 하거나 여러 요청을 동시에 처리하지 못한다는 의미는 아니다.

**비동기(Asynchronous): 작업 완료를 기다리지 않고 다음 작업을 진행하는 방식**

![[../../../../attachments/screenshots/비동기.png]]

비동기는 요청한 작업의 완료를 기다리지 않고 다음 작업을 진행할 수 있는 방식이다.

작업의 결과는 이후 콜백, Future, 이벤트, 메시지 등을 통해 전달받거나 확인할 수 있다.

여러 작업을 독립적으로 진행할 수 있다는 장점이 있지만, 동기 방식보다 작업의 완료 시점과 결과를 관리하는 과정이 복잡해질 수 있다.

비동기 방식이 항상 동기 방식보다 빠르거나 느린 것은 아니며, 작업의 특성과 처리 구조에 따라 성능이 달라진다.

##### 블로킹 / 논블로킹 (기다리는 동안 스레드가 무엇을 하는가?)

**블로킹(Blocking): 작업이 완료될 때까지 호출한 스레드가 대기하는 방식**

학생이 시험지를 선생님에게 건넨 후, 채점이 끝나 시험지를 돌려받을 때까지 가만히 기다린다면 블로킹 상태에 비유할 수 있다.

**논블로킹(Non-blocking): 작업이 완료되지 않았더라도 호출한 스레드가 대기하지 않고 제어권을 돌려받는 방식**

학생이 시험지를 선생님에게 건넨 후, 채점이 완료될 때까지 다른 과목을 공부하거나 다른 일을 할 수 있다면 논블로킹 상태에 비유할 수 있다.

##### 스프링 비동기 처리 방식

비동기 처리 도구인 `@Async`, `CompletableFuture` 등을 활용하여 작업을 별도 스레드에서 실행하거나 비동기적으로 결과를 처리할 수 있다.

**예시 상황**

- 동기 + 블로킹 → Spring MVC에서 일반적인 JPA 조회를 호출하고 결과가 반환될 때까지 기다리는 경우
- 비동기 + 블로킹 → 비동기로 실행한 작업의 결과를 `CompletableFuture.get()`으로 기다리는 경우
- 비동기 + 논블로킹 → WebFlux에서 논블로킹 I/O를 활용하여 비동기적으로 요청을 처리하는 경우
- 동기 + 논블로킹 → 논블로킹 호출을 사용하지만 호출자가 작업 완료를 확인한 뒤 다음 단계로 진행하는 경우

참고로 동기/비동기는 작업의 완료와 후속 작업 간의 관계를, 블로킹/논블로킹은 호출 시 제어권을 반환하는 방식을 구분하는 개념이다.

###### 이벤트

이벤트는 "어떤 일이 발생했다"는 사실을 의미한다.

또한 이벤트는 도메인 상태 변화가 발생했을 때 후처리를 분리하기 위한 수단이기도 하다.

사고 레포트가 등록되면 Spring Event를 발행하고, 리스너가 해당 이벤트를 받아 RabbitMQ에 견적 요청 메시지를 발행한다.

Spring Event는 같은 애플리케이션 내부의 후처리를 분리하기 위해 사용하고, RabbitMQ는 AI 서버처럼 별도 시스템과 비동기적으로 연동하기 위한 메시지 브로커로 사용했다.

### RabbitMQ

RabbitMQ는 AMQP 프로토콜을 지원하는 메시지 브로커이다.

Producer가 보낸 메시지를 Exchange를 통해 적절한 Queue로 라우팅하고, Consumer가 이를 비동기적으로 처리할 수 있도록 중계한다.

이를 통해 서비스 간 직접 호출을 줄이고 비동기 아키텍처를 구현할 수 있다.

#### RabbitMQ는 비동기이다

메시지 큐에서 생산자는 메시지를 발행하고, 소비자가 해당 메시지를 처리하는 과정과 분리되어 동작할 수 있다.

생산자는 소비자의 작업 완료를 기다리지 않고 다음 작업을 진행할 수 있으므로 비동기적인 처리가 가능하다.

다만 RabbitMQ에 메시지를 발행하는 호출 자체가 항상 논블로킹이라는 의미는 아니다.

#### RabbitMQ vs Kafka vs Redis

##### RabbitMQ

RabbitMQ는 **작업 큐(Work Queue)** 방식에 적합한 메시지 브로커이다.

먼저 RabbitMQ와 Kafka는 기술이 지향하는 점이 다르다.

RabbitMQ는 메시지를 적절한 소비자에게 전달하고, 작업을 안정적으로 처리하는 데 초점을 맞춘다.

- 메시지를 Exchange와 Queue를 통해 소비자에게 전달
- 소비자가 메시지를 정상적으로 처리하고 ACK하면 큐에서 제거
- 안정적인 작업 처리에 적합
- AI 처리, 메일 발송, 이미지 변환, 알림 발송 등에 많이 사용

##### Kafka

Kafka는 **이벤트 로그(Event Log) 저장소**에 가깝다.

Kafka는 이벤트를 저장하고 여러 소비자가 독립적으로 읽을 수 있도록 하는 데 초점을 맞춘다.

- 메시지를 소비해도 즉시 삭제되지 않음
- 설정된 보관 정책에 따라 메시지 유지
- Offset으로 읽은 위치를 관리
- 재처리(Replay) 가능
- 여러 Consumer Group이 독립적으로 소비 가능

그래서 Kafka를 분산 커밋 로그(Distributed Commit Log) 기반의 이벤트 스트리밍 플랫폼이라고 부른다.

##### Redis Pub/Sub

Redis는 주로 캐시 및 인메모리 데이터 저장소로 사용되며, Pub/Sub 기능은 **실시간 메시지 전달**에 적합하다.

- 빠른 메시지 전달
- 메모리 기반
- 구독자가 없으면 메시지 유실
- 메시지 저장 기능 없음
- 재처리 불가능

##### 요약

|항목|RabbitMQ|Kafka|Redis Pub/Sub|
|---|---|---|---|
|주요 목적|메시지 전달 및 작업 처리|이벤트 저장 및 스트리밍|실시간 메시지 전달|
|메시지 보관|큐에 보관|보관 정책에 따라 유지|보관 안 함|
|소비 후|ACK 시 큐에서 제거|보관 정책에 따라 유지|즉시 소멸|
|재처리|재큐잉 및 DLQ 등으로 구현 가능|Offset을 통한 재처리 가능|기본적으로 불가능|
|장애 복구|영속화 및 재전달 설정에 따라 지원|복제 및 로그 보관을 통해 지원|메시지 복구 기능 없음|
|처리량|높음|대규모 스트리밍에 적합|높음|
|대표 용도|작업 큐|이벤트 스트리밍|실시간 알림|

#### RabbitMQ 사용 이유

Kafka도 고려했지만, 카우머치 팀에서는 이벤트를 장기간 저장하고 재처리하기보다는 메시지를 안정적으로 전달하여 비동기 작업을 수행하는 것이 목적이었다.

메시지를 소비한 이후 계속 보관할 필요는 없었으며, 처리 실패 시 DLQ를 활용하여 실패한 메시지를 별도로 보관하고 재처리할 수 있다는 점이 적합했다.

또한 Kafka에 비해 현재 프로젝트의 요구사항을 충족하는 구성을 상대적으로 간단하게 구현할 수 있다고 판단하여 RabbitMQ를 도입했다.

#### DLQ

Dead Letter란 정상적인 처리 흐름에서 제외되어 별도의 처리가 필요한 메시지를 의미한다.

이러한 Dead Letter 메시지를 별도로 수집하기 위한 큐를 DLQ(Dead Letter Queue)라고 한다.

RabbitMQ에서는 다음과 같은 상황에서 메시지가 Dead Letter로 처리될 수 있다.

- 소비자가 메시지를 `requeue=false`로 Reject 또는 Nack한 경우
- 메시지가 큐에서 TTL을 초과하여 만료된 경우
- 큐의 최대 길이 제한을 초과하여 메시지가 제거되는 경우
- Quorum Queue에서 전달 횟수 제한을 초과한 경우

이러한 Dead Letter는 DLX(Dead Letter Exchange)를 통해 DLQ로 라우팅할 수 있다.

DLQ를 사용하면 처리에 실패한 메시지를 확인하고 장애 원인을 분석하거나 재처리 전략을 수립할 수 있다.

카우머치에서는 소비 실패 이후 DLQ로 이동한 메시지를 별도의 DB 테이블에 저장했다. 이후 스케줄러를 통해 재처리하고, 반복적으로 실패한 메시지는 상태를 관리하여 대응할 수 있도록 구현했다.

#### 재시도와 유실 메시지 처리

재시도는 2단계로 구성했다.

먼저 Listener 레벨에서 지수 백오프(Exponential Backoff)를 적용하여 최대 4회까지 처리를 시도한다.

모든 시도가 실패하면 메시지를 DLQ로 이동시키고, 이를 DB에 저장한 뒤 스케줄러가 다시 메시지를 발행하도록 했다.

장기적으로 처리에 실패한 메시지는 최대 10회까지 재처리하고, 이후에는 `GIVE_UP` 상태로 전환하도록 했다.

### Worker 노드

Worker를 분리한 이유는 무거운 AI 처리와 메인 비즈니스 서버의 역할을 분리하기 위해서이다.

AI 분석은 일반적인 CRUD 작업보다 연산량이 많고, 처리 시간이 길며, 리소스 사용량도 클 수 있다.

이를 메인 서버에서 함께 처리하면 서버 자원 경쟁이 발생할 수 있다고 판단했다.

따라서 AI 분석을 별도의 Worker 서버에서 수행하도록 분리하여 메인 서버의 요청 처리와 AI 작업이 서로 영향을 덜 받도록 설계했다.

또한 서비스의 부하 특성에 따라 메인 서버와 Worker 서버를 독립적으로 확장할 수 있는 구조를 고려했다.
