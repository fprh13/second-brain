# JWT 개선

---

## 📄 본문
### JWT 개선
JWT는 stateless하고 빠르다는 장점을 가지고 있는데, 기존 구조에서는 매 JWT 검증마다 DB에 select 쿼리를 날리면서 검증을 하고 있었다. 마치 세션 처럼 동작하고 있었던 것이다.

이유는 로그인 과정에서 사용하던 UserDetailsService에 loadUserByUsername의 호출을 검증 과정에도 사용했기 때문인다. 결국 JWT의 특성을 제대로 활용하지 못한 상태였고 개선하기로 했다.

로그인 요청은 JWT를 발급하는 하나의 비즈니스라고 판단했다. 기존에는 Spring Security의 Form Login을 위한 기본 인증 흐름들을 사용하고 있었지만, 이는 세션 기반 로그인을 위한 구조로 JWT 기반 API에는 적합하지 않는다고 판단했다.

따라서 로그인 기능을 JWT를 발급한다는 비즈니스로 Application계층으로 이동하여 검증한 뒤 JWT를 발급하도록 Form Login 인증 흐름을 제거했다.

이후 JWT 인증 요청에는 키로 디코드 되는지만 확인한 뒤 권한 객체를 직접 생성하여 SecurityContextHolder에 저장하도록 변경했다.

이를 통해서 인증 과정에서 발생하던 불필요한 DB 조회를 제거하고 JWT 특성에 맞는 인증 구조를 구성할 수 있었다.

#### JWT
JWT는 인증에 필요한 정보들을 암호화시킨 JSON 토큰을 의미합니다. JWT 인증은 JWT 토큰(Access Token)을 HTTP 헤더에 실어 서버가 클라이언트를 식별하는 방식입니다. 빠르고 stateless하고 분산 환경에 좋습니다. 하지만 탈취라는 위험함이 존재하고 누구나 내부의 구성된 값을 볼 수 있어서 민감정보를 담지말아야한다.

##### JWT 구성
###### Header
토큰의 종류와 시그니쳐 생성을 위해 어떤 알고리즘이 사용했는지 명시되는 곳이다.
```json
{
    "alg" : "HS256",
    "tpy" : "JWT"
}
```

###### Payload
내가 로그인한 유저임을 증명할 수 있는 정보들이다. 레피로드에 담는 정보의 한 조각을 클레임이라고한다. 클레임은 키 벨류 한쌍으로 구성된다.

###### Signature
토큰을 인코딩하거나 유효성 검증을 할 때 사용하는 고유한 암호화 코드이다.
```
1. 헤더와 페이로드 값을 각각 Base64로 인코딩
2. 인코딩한 값을 설정한 비밀키를 이용해 헤더에서 정의한 알고리즘으로 해싱
3. 이 값을 다시 Base64로 인코딩
```

#### JWT에 사용한 키
HMAC 알고리즘을 대칭키 방식으로 사용했다. HMAC + SHA을 사용했다. 우리 서비스는 토큰 발급과 검증을 동시에 수행하니, 연산 속도가 빠른 HMAC 대칭키 방식을 사용했다. HMAC 방식에는 해시 알고리즘이 사용되고 SHA 방식을 통해서 진행했다. SHA 512를 사용했기에 물론 키에 크리가 늘어난 만큼 속도가 느리지만 충분히 커버가 될 정도였으며, 키는 재발급과 엑세스 2개로 두어서 별도로 관리해 키유출에 대비했다.

#### 대칭키와 비대칭키
**대킹키 암호화: 하나의 키를 사용**
하나의 동일한 키로 암호화와 복호화를 모두 수행하는 방식이다.
- 같은 키를 양쪽이 공유해야 함
- 속도가 빠르고 연산 비용이 낮음
- 같은 키를 사용해 암호화, 복호화를 수행하기 때문에 속도가 빠름
- 대표적으로 HMAC 암호화 알고리즘이 있음
- 값에 SHA-256을 적용해서 해싱 후 private key(== secret key, 대칭키 역할)로 암호화
- private key를 알고있는 서버만 Signature 유효성 검증이 가능(== JWT를 복호화 가능)

단점: 키가 유출되면 전체 보안이 무너짐, 여러 서비스가 있으면 **키를 공유해야 해서 관리가 어려움**
예: HMAC (JWT에서 사용), AES

**비대칭키 암호화: 공개키 + 개인키 두개를 사용**
서로 다른 두개의 키를 사용하는 방식이다.
- 비밀키는 한 곳만 보관
- 공개키는 여러 곳에 배포 가능
- 키를 공유하지 않아도 됨 → 보안성 높음
- 암호화 복호화 키가 다른 방식
- 다른 키를 사용해 암호화, 복호화를 수행하기 때문에 속도가 느리지만 그만큼 안전
- 대표적으로 RSA 암호화 알고리즘이 있음
- 마찬가지로 SHA-256 단방향 암호화 알고리즘과 함께 쓰임
- 값에 SHA-256를 적용해서 해싱후 private key(비밀키)로 암호화
- public key(공개키)는 공개적으로 제공. 어떠한 서버든 이 public key를 통해 JWT를 복호화 가능

단점:대칭키보다 연산이 느림

예: RSA, ECDSA

#### 해시 알고리즘
해시 알고리즘마다 Hash 길이가 다르고 이미 보안이 뚫린 해시 함수가 존재한다. MD5, SHA-1, HAS-180는 사용하면 안되며, SHA-256, SHA-512 등 을 사용하기를 권고한다.

#### 세션
세션은 서버에 사용자별로 세션을 저장해서 관리한다. 서버는 메모리에 사용자에 해당하는 세션값을 생성한 뒤 저장하고 세션 식별 값인 세션 아이디를 쿠키로 전달한다. 서버에서 인증 과정을 처리하므로 안전하다. 서버의 메모리 내부에 세션 값이 적재되서 클라이언트 수가 늘러나면 서버 메모리의 부하도 늘어나는 단점이 있다. 쿠키는 단일 도메인, 서브 도메인에서만 작동하도록 되어있어 여러 도메인에서 관리하기 번거롭다.

#### 쿠키
쿠키는 브라우저에 저장되는 작은 데이터로, 서버가 클라이언트를 식별하기 위해 사용한다. 대표적인 예시는 다음과 같다.
- 로그인 상태 유지 (세션 ID, JWT 등)
- 사용자 설정 저장 (언어, 테마 등)
- 트래킹 (방문 기록, 광고 등)
HTTP는 기본적으로 stateless이기 때문에 요청마다 사용자를 기억할 수 없는데, 이것을 해결하기 위해 쿠키를 사용한다. 즉, 쿠키는 상태를 유지하기 위한 클라이언트 저장소라고 할 수 있다.

쿠키에는 인증정보가 들어있는 경우가 많아 탈취 된다면 계정 탈취로 바로 이어질 수 있다. 대표적인 공격은 다음과 같다.
- XSS → JS로 쿠키 탈취
- CSRF → 사용자가 모르게 요청 보내기
- 네트워크 스니핑 → 평문 쿠키 탈취

##### 쿠키 보안 옵션
###### HttpOnly
- **설명**: JavaScript에서 `document.cookie`로 접근 불가능
- **막는 공격**: XSS 기반 쿠키 탈취
- **요약**: JS에서 쿠키 접근을 막아서 XSS로부터 보호합니다.
###### Secure
- **설명**: HTTPS에서만 쿠키 전송됨 (HTTP에서는 전송 안됨)
- **막는 공격**: 네트워크 스니핑 (중간자 공격)
- **요약**: 암호화된 HTTPS 환경에서만 쿠키를 전송하도록 강제합니다.
###### 3) SameSite
- **설명**: 다른 사이트에서 요청 시 쿠키를 보낼지 여부 제어
- **값 종류**:

|옵션|설명|
|---|---|
|Strict|완전 차단 (외부 요청에서는 쿠키 X)|
|Lax|일부 허용 (GET 정도만 허용)|
|None|모두 허용 (단, Secure 필수)|

- **막는 공격**: CSRF
- **요약**: 크로스 사이트 요청에서 쿠키 전송을 제한하여 CSRF를 방지합니다.
### Spring Security
Spring에서 보안과 인증인가를 담당하는 스프링의 하위 프레임워크이다. Spring Security는 인증과 인가에 대한 부분을 필터의 흐름에 따라 처리한다. Spring Security를 사용하면 보안과 관련된 많은 옵션을 제공해주기 때문에 일일이 보안 관련 로직을 작성하지 않아도 된다는 장점이 있다.
![[../../../../attachments/screenshots/SpringSecurity.png]]

#### 인증 인가
Authentication : 인증은 해당 사용자가 본인이 맞는지를 확인하는 절차
Authorization: 인가는 인증된 사용자가 요청한 자원에 접근 가능한지를 결정하는 절차

#### Spring Security 필터
usernamePasswrodAuthenticationFilter를 사용했다. 로그인 과정은 해당 필터로 진행했다. API서버에서 JWT를 사용하기 위해서 JWT를 발급하는 부분을 구현 부에 커스텀해서 사용했다. Java Docs를 확인하니, Form Login에 적합하다고 하며, 로그인 행위는 토큰을 발급하는데 관심이 있다고 판단되어, 비즈니스 레이어에 구현하기 위해 해당 필터는 현재 사용하지 않는다.

#### 시큐리티 필터 체인
JWT는 인증에 필요한 정보들을 암호화 시킨 JSON 토큰을 의미한다. 그리고 JWT 기반 인증은 JWT 토큰을 HTTP 헤더에 실어 서버가 클라이언트를 식별하는 방식이다.

#### 필터
필터는 서블릿이 제공하는 기능이다. 여러 로직에서 공통으로 관심이 있는 것을 공통 관심사라고 하는데 웹과 관련된 공통 관심사는 서블릿 필터 혹은 스프링 인터셉터로 해결한다. HTTP 요청 -> WAS -> 필터 -> 서블릿 -> 컨트롤러의 흐름을 가지고 있고 디스패처 서블릿 이전에 실행된다. 필터는 체인으로 구성되고 중간에 필터를 자유롭게 추가할 수 있다.

#### 인터셉터
필터가 서블릿에서 제공하는 기능이라면, 스프링 인터셉터는 스프링 MVC가 제공하는 기술이다.
HTTP 요청 -> WAS -> 필터 -> 서블릿 -> 스프링 인터셉터 -> 컨트롤러 요청 흐름을 가지고 있다. 스프링 인터셉터는 디스패처 서블릿과 컨트롤러 사이에서 호출된다. 스프링 인터셉터도 체인으로 구성되어 중간에 인터셉터를 자유롭게 추가할 수 있다.

정보보호 3요소 기밀성 무결성 가용성
**기밀성**: 인증된 사용자만 접근한다.
**무결성**: 데이터를 무결하게 보존한다.
**가용성**: 인가된 사용자는 언제든지 자원을 사용한다.

#### XSS와 CSRF
둘 다 Javascript 를 통해 공격자가 의도된 행위를 하는 JavaScript를 통한 공격이지만 XSS는 악성 스크립트가 클라이언트 쪽에서 실행된다면 ( 악성 스크립트가 포함된 사이트를 클릭하는 등의 행위를 통해 실행  ) CSRF는 정상적인 사용자의 요청이 서버에 전달되어 클라이언트의 의도와 관계없이 악성 스크립트가 서버에서 실행되는 차이가 있다. ( 요청자체는 정상적이지만 그 이후의 실행 내용이 악의적임 )
