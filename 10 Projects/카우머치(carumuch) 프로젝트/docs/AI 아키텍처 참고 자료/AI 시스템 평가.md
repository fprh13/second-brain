# 차량 사고 분석 AI 시스템 문제점 정리

## 1. 요약

현재 시스템은 손상 이미지를 직접 이해해서 수리 부품과 공임을 예측하는 구조가 아니다.  
실제로는 `입력 이미지와 가장 비슷한 과거 사고 사진 1장`을 찾고, 그 사진에 연결된 견적 JSON을 그대로 가져오는 방식이다.

그래서 아래와 같은 문제가 자연스럽게 발생한다.

- 실제로 손상된 부품과 다른 부품이 추천될 수 있다.
- 예상 공임비 총금액이 실제보다 과대 또는 과소 추정될 수 있다.
- "정확도가 몇 %냐"는 질문에 현재 코드 기준으로는 답할 수 없다.

## 2. 왜 예상 수리 부품이 이상하게 나오는가

### 2.1 부품 자체를 직접 판별하지 않는다

현재 `/classify` 로직은 부품 분류 모델을 쓰지 않는다.  
`VGG16`으로 이미지 특징을 뽑고, 기존 사례 중 가장 비슷한 이미지 1장을 찾은 뒤 그 사례의 `수리내역`을 그대로 반환한다.

즉, 시스템이 실제로 하는 일은 아래와 같다.

`사고 이미지 -> 유사 사례 검색 -> 그 사례의 부품 목록 재사용`

따라서 입력 차량의 실제 손상 부위가 달라도, 외형적으로 비슷한 다른 사고 사례가 선택되면 전혀 다른 부품이 추천될 수 있다.

### 2.2 일반 이미지용 VGG16을 사고 검색에 사용한다

`VGG16`은 원래 ImageNet 일반 사물 분류용 모델이다.  
현재 코드에서는 이 모델을 사고 차량 검색용 임베딩으로 그대로 사용한다.

문제는 다음과 같다.

- 차량 부품 단위 차이를 구분하도록 학습된 모델이 아니다.
- 사고 부위보다 배경, 차 색상, 촬영 각도, 조명 영향을 많이 받을 수 있다.
- 앞범퍼와 펜더처럼 실제 수리 항목이 다른데도 시각적으로 비슷하면 잘못 매칭될 수 있다.

즉 "비슷해 보이는 사진"은 찾을 수 있어도, "같은 수리 부품이 필요한 사고"를 정확히 찾는다고 보장할 수 없다.

### 2.3 이미지 전체를 보고 비교한다

현재 파이프라인은 사고 부위만 잘라서 비교하지 않고 전체 이미지를 사용한다.

그래서 아래 요소가 검색 결과에 영향을 줄 수 있다.

- 촬영 거리
- 차량의 방향
- 주변 배경
- 차체 색상
- 빛 반사

이 구조에서는 손상 위치보다 사진 전체 분위기가 더 비슷한 사례가 선택될 수 있다.

### 2.4 가장 유사한 사례 1개만 사용한다

현재는 `Top-1` 사례 하나만 선택하고 끝낸다.  
다수 후보를 평균내거나, 공통 부품만 뽑거나, 유사도 임계치를 두는 로직이 없다.

이 때문에 한번 잘못 매칭되면 결과 전체가 통째로 틀어질 수 있다.

### 2.5 부품 세그멘테이션 모델이 실제 견적에 쓰이지 않는다

저장소에는 `[PART]Unet.pt` 파일이 있지만, 현재 서비스 코드에서는 사용하지 않는다.

즉 시스템은 아래 정보를 견적 단계에서 활용하지 못한다.

- 실제 손상된 부품 영역
- 부품별 손상 면적
- 부품별 손상 유형

결과적으로 "어느 부품이 망가졌는지"를 근거 있게 판정하지 못한 채, 유사 사례의 부품명을 가져오고 있다.

## 3. 왜 예상 공임비 총금액이 이상하게 나오는가

### 3.1 공임비는 계산 예측이 아니라 사례 복사다

현재 총금액은 AI가 산출한 값이 아니다.  
가장 유사한 사례의 JSON에서 `부품가격 + 공임`을 모두 더한 값이다.

즉 아래 차이를 반영하지 못한다.

- 실제 손상 범위 차이
- 교환 vs 판금/도장 여부 차이
- 연식 차이
- 트림 차이
- 센서/ADAS 장착 여부
- 부품 수급 상황
- 지역별 공임 차이

그래서 사진이 비슷해도 실제 수리비는 크게 달라질 수 있다.

### 3.2 유사도 점수는 계산하지만, 결과 필터링에 쓰지 않는다

코드에서 `highest_similarity`는 계산한다.  
하지만 응답에 넣지도 않고, 임계치 검증에도 쓰지 않는다.

즉 아래 같은 상황도 그대로 통과한다.

- 정말 비슷한 사례를 찾은 경우
- 그냥 그나마 덜 이상한 사례를 찾은 경우

둘 다 동일한 형식으로 견적이 반환되기 때문에, 사용자는 결과 신뢰도를 알 수 없다.

### 3.3 제조사만 나누고 차종/연식/트림을 반영하지 않는다

현재 분기는 `kia`, `hyundai` 두 개뿐이다.

그러나 실제 수리비는 아래 영향을 강하게 받는다.

- 정확한 차종
- 연식
- 트림
- 옵션
- 부품 규격

제조사 단위로만 과거 사례를 묶으면 견적 오차가 커질 수밖에 없다.

### 3.4 단일 JSON 구조 의존성이 높다

코드는 JSON 형식이 조금만 바뀌어도 비용 계산이 흔들릴 수 있다.

- 기아는 `손해사정후` 아래 필드를 읽음
- 현대는 최상위 필드를 읽음
- 빈 값은 모두 `0`으로 처리

이 구조는 데이터 누락이나 포맷 불일치가 생기면 실제보다 금액이 작아지는 방향의 오류를 만들 가능성이 있다.

## 4. 왜 정확도를 설명하지 못했는가

정확도를 말하려면 최소한 아래 중 하나가 있어야 한다.

- 검증용 데이터셋
- 정답 라벨
- 평가 코드
- 저장된 평가 결과
- 운영 로그 기반 오차 통계

하지만 현재 저장소 기준으로는 이런 정보가 없다.

- 부품 예측 정확도 리포트 없음
- 총금액 오차율 리포트 없음
- 세그멘테이션 IoU/Dice 리포트 없음
- 유사 사례 검색 Top-k 정확도 없음

즉 지금 상태에서는 "정확도 몇 %"라고 답하면 근거 없는 수치가 된다.

## 5. 현재 코드 구조만 보고 추정한 예상 정확도

아래 수치는 `실측값이 아니라 코드 구조를 보고 보수적으로 추정한 운영 기대치`다.  
대외 발표용 정확도로 쓰면 안 되고, 내부 문제 인식용 참고치로만 봐야 한다.

### 5.1 예상 수리 부품 정확도

정의: 입력 사고 이미지에 대해 실제 필요한 수리 부품 목록과, 시스템이 제시한 부품 목록이 얼마나 맞는지

보수적으로 보면 현재 구조의 `Top-1 부품 적중 정확도`는 높게 보기 어렵다.

- 낙관적 가정: `40~60%`
- 보수적 가정: `20~40%`

이유는 다음과 같다.

- 일반용 `VGG16` 특징을 사용한다.
- 부품 자체를 직접 인식하지 않는다.
- 사고 부위보다 전체 이미지 유사도에 영향을 받는다.
- 유사 사례 1개만 사용한다.

즉 실제 현장 체감은 "대략 비슷한 부품군은 맞추지만, 정확한 교환 대상은 자주 틀릴 수 있는 수준"으로 보는 것이 현실적이다.

### 5.2 예상 총금액 정확도

금액은 절대 정확도보다 `오차율`로 보는 편이 맞다.

정의: 실제 견적 금액 대비 시스템 출력 금액의 차이

현재 구조에서는 `총금액 정확도`보다 `MAPE(평균 절대 백분율 오차)`로 설명하는 것이 적절하다.

코드 구조만 보면 예상 오차는 아래처럼 보는 것이 더 현실적이다.

- 낙관적 가정: `MAPE 20~35%`
- 보수적 가정: `MAPE 35~60% 이상`

정확도처럼 뒤집어 표현하면 아래 정도로 이해할 수 있다.

- 낙관적 환산 정확도: `65~80%`
- 보수적 환산 정확도: `40~65%`

다만 이 수치는 실제 평가 결과가 아니라, "유사 사례 복사형 견적 시스템"의 구조적 한계를 반영한 추정치다.

### 5.3 세그멘테이션 시각화 신뢰도

손상 시각화는 정량 평가가 없다.  
또한 세그멘테이션 결과가 견적 계산에 직접 연결되지도 않는다.

따라서 현재 상태에서는 아래 정도가 맞다.

- 시각적으로 참고는 가능
- 견적 근거로 쓰기에는 불충분
- 정확도 수치를 말할 근거 없음

## 6. 대외 설명 시 사용할 수 있는 안전한 표현

현재 시스템 소개나 고객 응대에서는 아래처럼 말하는 것이 안전하다.

`현재 버전은 AI가 과거 유사 사고 사례를 검색해 예상 수리 항목과 금액을 제시하는 방식이며, 정식 검증 데이터셋 기준의 정확도 수치는 아직 확보되지 않았습니다. 따라서 결과는 참고용 추정치로 보는 것이 맞습니다.`

또는 더 짧게 말하면 아래와 같다.

`현재 시스템은 정량 검증된 자동 견적 모델이 아니라, 유사 사고 사례 기반 추천 시스템에 가깝습니다.`

## 7. 가장 큰 문제점 정리

현재 시스템의 핵심 문제는 아래 네 가지다.

1. `예상 수리 부품`이 실제 부품 인식 결과가 아니라 유사 사례 복사 결과다.
2. `예상 공임비 총금액`이 실제 사고 정도를 반영한 계산이 아니라 사례 금액 재사용이다.
3. `정확도`를 설명할 평가 체계가 전혀 없다.
4. `신뢰도 점수`나 `검증 불가 안내` 없이 결과가 단정적으로 반환된다.

## 8. 개선 우선순위

### 8.1 가장 먼저 할 일

- 검증 데이터셋 구축
- 실제 정답 부품 라벨 정리
- 실제 견적 금액 정답 확보
- 부품 정확도, 금액 오차율, 세그멘테이션 IoU 측정

이 단계가 없으면 정확도 질문에 계속 답할 수 없다.

### 8.2 그 다음 할 일

- 유사 사례 1개 대신 `Top-k` 후보 기반 앙상블
- `highest_similarity`를 응답에 포함
- 유사도 임계치 이하일 때 "신뢰도 낮음" 반환
- `[PART]Unet.pt`를 실제 파이프라인에 연결
- 손상 부위와 부품 인식을 결합한 견적 로직으로 변경

### 8.3 최종적으로 필요한 방향

목표는 아래 구조로 바뀌어야 한다.

`부품 검출/분할 -> 손상 유형 판정 -> 손상 면적/심각도 계산 -> 규칙/모델 기반 견적 산출 -> 신뢰도와 함께 반환`

이 방향으로 바뀌어야 "예상 부품"과 "예상 공임비"의 설명력이 생긴다.

## 9. 한 문장 결론

현재 시스템은 정확한 자동 견적 AI라기보다 `유사 사고 사례 검색 기반 추천 시스템`에 가깝기 때문에, 예상 수리 부품과 예상 공임비 총금액이 이상하게 나올 수 있고, 현재 상태만으로는 정확도를 수치로 자신 있게 설명할 수 없다.
