# 차량 사고 분석 AI 시스템 구현 메커니즘 분석

## 1. 시스템 개요

이 프로젝트는 하나의 사고 차량 이미지를 받아 두 가지 결과를 동시에 만드는 구조다.

1. `유사 사고 사례 검색`을 통해 가장 비슷한 기존 사고 이미지를 찾는다.
2. 해당 사례에 연결된 `수리 내역 JSON`을 읽어 예상 수리 항목과 총 비용을 계산한다.
3. 별도의 `손상 세그멘테이션 모델`로 파손 부위를 색상 오버레이 이미지로 시각화한다.

즉, 이 시스템은 "이미지 자체로 직접 견적을 회귀 예측하는 모델"이 아니라, `특징 벡터 기반 유사 사례 검색 + 규칙 기반 견적 합산 + 세그멘테이션 시각화`를 조합한 하이브리드 구조다.

## 2. 진입점과 실행 구조

실행 진입점은 `app.py`다.

- Flask 서버를 실행한다.
- 서버 시작 시점에 `VGG16` 특징 추출 모델을 메모리에 올린다.
- 서버 시작 시점에 손상 유형별 `U-Net` 모델 4개를 모두 메모리에 올린다.
- 주요 API는 `/health-check`, `/segment`, `/classify` 세 개다.

핵심 구현 파일은 다음과 같다.

- `app.py`: API, 모델 로드, 추론, 유사도 계산, 비용 산정, 응답 생성
- `U_Model.py`: `segmentation_models_pytorch` 기반 `Unet` 래퍼
- `models/*.pt`: 손상 세그멘테이션 가중치

## 3. 모델 구성

### 3.1 VGG16 특징 추출 모델

`app.py`에서 TensorFlow Keras의 `VGG16(weights='imagenet')`를 로드한 뒤, 마지막 분류 출력이 아니라 `fc1` 레이어 출력을 특징 벡터로 사용한다.

- 입력 크기: `224 x 224`
- 전처리: `preprocess_input`
- 출력: `fc1` 특징 벡터 1개
- 역할: 사고 이미지 검색용 임베딩 추출

이 벡터는 사전 계산된 피처 딕셔너리(`kia_features_dict.pkl`, `h_features_dict.pkl`)와 코사인 유사도로 비교된다.

### 3.2 U-Net 손상 세그멘테이션 모델

`U_Model.py`를 보면 `segmentation_models_pytorch.Unet`를 감싼 단순 래퍼다.

- 백본 인코더: `resnet34`
- 사전학습 가중치: `imagenet`
- 입력 채널: `3`
- 클래스 수: `2`

`app.py`에서는 손상 유형별로 아래 4개의 모델을 각각 로드한다.

- `Breakage_3`
- `Crushed_2`
- `Scratch_0`
- `Seperated_1`

각 모델은 해당 손상 타입에 대해 `배경/손상`의 2클래스 마스크를 출력하는 구조로 보인다.

참고로 `models/[PART]Unet.pt` 파일도 저장소에 있지만, 현재 코드에서는 로드되지 않는다. 즉 현재 서비스 로직은 `부품 분할 모델`이 아니라 `손상 유형 분할 모델 4개`만 사용한다.

## 4. API별 동작 메커니즘

### 4.1 `/segment`

이 API는 손상 시각화 전용이다.

동작 순서는 다음과 같다.

1. 요청 JSON에서 이미지 URL을 읽는다.
2. 이미지를 다운로드한다.
3. OpenCV로 디코딩하고 RGB로 변환한다.
4. `256 x 256`으로 리사이즈한다.
5. `0~1` 정규화 후 `CHW` 형태 텐서로 변환한다.
6. 4개의 U-Net 모델을 각각 실행한다.
7. 각 모델의 `argmax` 결과에서 손상 클래스로 예측된 픽셀만 색칠한다.
8. 원본 이미지와 색상 마스크를 alpha blending 해서 PNG로 반환한다.

손상 타입별 색상 매핑은 다음과 같다.

- `Breakage_3`: 빨강
- `Crushed_2`: 초록
- `Scratch_0`: 파랑
- `Seperated_1`: 노랑

중요한 점은 이 API가 손상 면적 비율, 바운딩 박스, 심각도 점수 등을 계산하지는 않는다는 것이다. 현재는 어디가 어떤 손상인지 `시각적으로 보여주는 용도`에 가깝다.

### 4.2 `/classify`

이 API가 실제 사고 분석의 핵심이다. 이름은 `classify`지만 실제로는 `분류 + 유사 사례 검색 + 견적 조회 + 세그멘테이션 시각화`를 한 번에 수행한다.

입력값은 다음 두 개다.

- `url`: 사고 차량 이미지 URL
- `manufacturer`: `kia` 또는 `hyundai`

동작 순서는 다음과 같다.

1. 이미지를 다운로드한다.
2. 이미지를 `224 x 224`로 리사이즈한다.
3. `VGG16 fc1` 특징 벡터를 추출한다.
4. 제조사별 피처 딕셔너리와 코사인 유사도를 계산한다.
5. 가장 유사한 기존 사고 이미지 1장을 선택한다.
6. 그 이미지와 같은 이름의 JSON 견적서를 연다.
7. `수리내역` 배열을 순회하면서 부품가격과 공임을 합산한다.
8. `작업항목 및 부품명`을 리스트로 수집한다.
9. 같은 입력 이미지에 대해 U-Net 4개를 다시 실행해 세그멘테이션 이미지를 만든다.
10. 세그멘테이션 결과를 Base64 PNG 문자열로 인코딩한다.
11. `list_repair`, `total_cost`, `segmented_image`를 JSON으로 반환한다.

즉 최종 결과는 모델이 직접 계산한 견적이 아니라, `가장 비슷한 과거 사례의 수리 내역을 가져와 합산한 결과`다.

## 5. 견적 산정 로직

견적 계산은 머신러닝 회귀가 아니라 JSON 파싱 기반 규칙 처리다.

### 5.1 유사 사례 선택

유사도 계산 함수는 `1 - cosine(feature_a, feature_b)`를 사용한다.  
가장 큰 값을 갖는 사례를 최종 매칭 결과로 채택한다.

따라서 실제 성능은 아래 요소에 크게 좌우된다.

- VGG16 특징이 사고 부위 유사성을 얼마나 잘 반영하는지
- 피처 딕셔너리에 얼마나 다양한 사례가 들어 있는지
- 데이터셋 이름과 견적 JSON 이름이 정확히 1:1로 매핑되는지

### 5.2 제조사별 JSON 처리 차이

`close_cost()` 함수는 JSON 구조 차이를 감안해 두 가지 형식을 처리한다.

- 기아: 각 항목 안의 `손해사정후` 아래에서 `부품가격`, `공임`을 읽음
- 현대: 최상위 항목에서 바로 `부품가격`, `공임`을 읽음

그리고 모든 수리 항목에 대해 다음을 수행한다.

- 빈 값 또는 `None`은 `0`으로 처리
- 쉼표가 있는 문자열 금액을 정수로 변환
- `부품가격 + 공임`을 누적
- `작업항목 및 부품명`을 수리 항목 리스트에 추가

즉 이 시스템의 견적 메커니즘은 다음 공식으로 정리할 수 있다.

`입력 사고 이미지 -> 가장 유사한 과거 이미지 선택 -> 연결된 견적 JSON 로드 -> 항목별 금액 합산`

## 6. 전처리와 후처리

### 6.1 특징 추출용 전처리

- PIL 로드
- `224 x 224` 리사이즈
- 배열 변환
- 배치 차원 추가
- `preprocess_input`

### 6.2 세그멘테이션용 전처리

- OpenCV 디코딩
- BGR -> RGB 변환
- `256 x 256` 리사이즈
- `255`로 나눠 정규화
- `HWC -> CHW`
- Float Tensor 변환
- 배치 차원 추가

### 6.3 후처리

- 세그멘테이션 결과는 `argmax`로 이진 마스크 생성
- 유형별 고정 색상 적용
- 원본 이미지와 `alpha=0.3` 비율로 합성
- `/segment`에서는 PNG 파일로 직접 반환
- `/classify`에서는 Base64 문자열로 반환

## 7. 구현 관점에서의 핵심 메커니즘 정리

이 시스템은 일반적인 end-to-end 사고 분석 AI와 다르게, 아래 세 층으로 나뉜다.

### 7.1 시각 특징 검색 층

VGG16으로 이미지 전체 특징을 뽑고, 과거 사고 이미지와 가장 비슷한 사례를 찾는다.

### 7.2 규칙 기반 견적 층

찾아낸 사례에 연결된 JSON에서 수리 항목과 금액을 읽어 총 비용을 계산한다.

### 7.3 손상 시각화 층

U-Net 4개가 각각 손상 유형별 픽셀 단위 마스크를 만들고, 이를 색상으로 겹쳐 보여준다.

결론적으로 이 시스템의 "AI"는 두 부분에만 직접 들어간다.

- `VGG16`: 사례 검색용 특징 추출
- `U-Net`: 손상 위치 분할

반면 "견적 산출"은 AI 예측값이 아니라 `검색된 유사 사례의 정답 데이터 재활용`에 가깝다.

## 8. 현재 저장소 기준의 한계와 주의점

코드를 기준으로 보면 다음 사항이 중요하다.

### 8.1 분류 결과는 실제 분류기가 아니다

`/classify`라는 이름과 달리, 제조사 판별이나 손상 클래스 분류를 학습 모델이 직접 수행하지 않는다.  
핵심은 `nearest neighbor 검색`이다.

### 8.2 견적 필수 데이터가 저장소에 없다

코드에는 아래 파일/폴더 의존성이 있다.

- `kia_features_dict.pkl`
- `h_features_dict.pkl`
- `kia_견적서/`
- `hyundai_견적서/`

하지만 현재 저장소에는 이 파일들이 보이지 않는다.  
따라서 현재 체크아웃 상태만으로는 `/classify`가 정상 동작하지 않을 가능성이 높다.

### 8.3 모든 추론이 CPU 기준으로 고정되어 있다

- TensorFlow GPU를 비활성화한다.
- PyTorch 디바이스도 `cpu`로 고정한다.

즉 배포 환경은 GPU 추론이 아니라 CPU 서버 기준으로 설계된 것으로 보인다.

### 8.4 세그멘테이션 결과 병합 방식이 단순하다

4개 손상 모델의 결과를 차례대로 같은 오버레이 배열에 덮어쓴다.  
동일 픽셀에서 여러 손상 모델이 동시에 1을 예측하면 마지막에 적용된 색이 남을 수 있다.

### 8.5 신뢰도 활용이 없다

유사 사례 검색에서 `highest_similarity`를 계산하지만, 응답에는 포함하지 않는다.  
즉 "얼마나 비슷한 사례인지"에 대한 신뢰도 정보 없이 결과를 반환한다.

## 9. 한 문장 요약

이 차량 사고 분석 AI는 `입력 이미지를 VGG16으로 임베딩해 과거 사고 사례 중 가장 비슷한 이미지를 찾고, 그 사례의 견적 JSON을 합산해 비용을 산출하며, 동시에 U-Net 4개로 손상 위치를 색상 마스크로 시각화하는 구조`로 구현되어 있다.
