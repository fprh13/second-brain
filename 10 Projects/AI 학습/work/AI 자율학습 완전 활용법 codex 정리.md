# AI 자율학습 완전 활용법 codex 정리

---

## 📄 개요
AI 자율학습 클로드 코드, 코덱스 CLI, 제미나이 CLI 완전 활용법의 Codex CLI 부분을 정리한 내용입니다.

---

## ✏️ 메모
### AGENTS.md는 간결하게
프로젝트 전반에서 반드시 공유되어야 할 핵심 규칙만 포함하는 것이 좋습니다. 문서가 길 경우 정보를 빠르게 파악하기 어렵습니다.
- 프로젝트 전반에 공통으로 적용되는 핵심 지침만 포함
- 한두 문단과 몇 개의 명확한 규칙 수준으로 유지
- 배경 설명이나 세부 기준은 별도 문서로 분리


### AGENTS.md와 상세 문서를 분리해 관리한다.
AGENTS.md는 핵심 규칙만 간단히 요약하고, 세부 지침은 별도 문서로 관리하는 방식이 효과적입니다.
일반적으로는 docs 폴더와 같은 위치에 상세문서를 둡니다.

```
docs/
|--- architecture.md # 시스템 설계 및 전체 구조 요약
|--- coding-style.md # 코딩 컨벤션 및 네이밍 규칙
|--- testing-guide.md # 테스트 작성 및 실행 절차
|--- deployment.md # 배포 절차와 환경 설정 설명
```
AGENTS.md는 다음 내용만 담아도 충분합니다.
- 프로젝트 개요(3~5): 프로젝트가 무엇을 하는지 요약
- 기술 스택과 실행 환경: Codex가 참고해야 할 최소 정보
- 핵심 구조 요약: 주요 디렉터리 역할을 한 줄씩 정리
- 절대 준수해야 할 규칙(3개 내외): 금지 항목 또는 필수 규칙
- 기본 테스트/빌드 명령: Codex가 자동 실행할 기본값

세부 내용이 필요할 때는 대화 중에 명시적으로 파일을 참조합니다.
```
> @docs/coding-style.md의 오류 처리 규칙을 적용해 리팩터링해줘.
```
역할을 분리하면 프로젝트 규모가 커지더라도 규칙을 정리하고 유지하는 부담을 줄일 수 있습니다.

### AGENTS.md 템플릿 예시

```
## 프로젝트 개요
Go 기반 실시간 투표 마이크로서비스
SSE를 사용해 결과를 스트리밍한다.
아키텍처 개요는 docs/architecture.md 문서를 참고한다.

## 개발 환경
go mod download
cp .env .example .env

## 실행
go run cmd/pulse/main.go
# 기본 접속 주소: http://localhost:8080

## 구조 요약
domain/ # 비즈니스 로직(외부 의존성 없음)
app/ # 유즈케이스(domain만 의존)
adapters/ # HTTP, DB, Redis 어댑터 구현
의존성 방향: adapters -> app -> domain

## 테스트
go test ./... # 전체 테스트
go test -race ./... # 동시성 검증(필수)

## 반드시 지켜야 할 사항
1. domain/에 외부 라이브러리 import 금지
2. 오류는 `%w`로 래핑해 전달
3. 전역 변수 금지 (DI 사용)
4. 테스트 커버리지 80% 이상 유지
```

### AGENTS.md 위치와 적용 범위
가장 안정적인 방식은 프로젝트 루트에 하나의 AGENTS.md를 두고, 필요할 경우에만 서브폴더 단위로 보조 문서를 추가하는 것입니다. 이렇게 구성하면 협업 환경에서도 규칙을 명확하게 전달하고, 복잡한 프로젝트 구조에서도 혼선을 줄일 수 있습니다.

**서브폴더 AGENTS.md - 영역별 규칙 문서(선택)**
```
./frontend/AGENTS.md
./backend/AGENTS.md
./service/bidding/AGENTS.md
```
- 서로 다른 서비스가 하나의 저장소에 존재하는 모노레포 구조일 때
- 프론트엔드, 백엔드의 기술 스택과 규칙이 완전히 다를 때
- 레거시 코드와 신규 코드가 섞여 있어 영역별 규칙 분리가 필요할 때
```
# frontend/AGENTS.md
이 폴더의 규칙은 루트 규칙을 따른다.
단, 스타일링은 아래 규칙을 우선 적용한다.
- Tailwind CSS만 사용
- Styled Components 금지
```
여러 AGENTS.md를 사용하는 경우에는 현재 작업 대상과 함께 어떤 문서를 참고해야 하는지 대화에 명시하는 것이 안전합니다.

### AGENTS.md 주요 항목
| 구분 | 내용 |
| --- | --- |
| 프로젝트 개요 | 기술 스택, 주요 기능, 실행 환경 |
| 개발 환경 | 설치 및 실행 명령(npm install, docker compose up 등) |
| 코딩 규칙 | ESLint/Prettier 규칙, 함수형 패턴, 변수명 규칙 등 |
| 테스트 절차 | 테스트 실행 방법, 기본 테스트 범위 |
| 리뷰 및 배포 지침 | 커밋 메시지, PR 제목 규칙, 배포 전 점검 항목 |
| 보안 및 예외 처리 | API 키, 개인정보 처리, 대용량 데이터 처리 주의 사항 |

**Codex가 항상 강제하지는 않습니다.**
작업 방향을 이해하도록 돕는 참고 지침에 가깝습니다.
정말 중요한 작업이라면 요청 시 다시 한번 명시적으로 지시하는 것이 안전합니다.

### 대화가 길어졌을 때 컨텍스트 최적화하기
Codex로 작업을 이어가다 보면 대화가 길어지면서 현재 작업 맥락에 사용할 수 있는 컨텍스트 여유가 줄어드는 상황이 발생합니다. 이때 화면 하단에는 남아 있는 컨텍스트 사용량을 나타내는 지표가 표시되며, 수치가 낮아질수록 이전 대화나 파일 정보를 충분히 활용하기 어려워질 수 있습니다.

**해결 방안 - 1**
```
> /compact 최근 대화의 핵심만 남기고 이전 내용을 요약해줘.
```
- 핵심 결정과 중요한 요청만 남기고, 불필요한 과거 대화는 자동 요약합니다.


**해결 방안 - 2**
특정 기능 개발처럼 주제가 완전히 바뀐다면 컨텍스트를 남기지 않고 /new로 시작하는 편이 더 효율적입니다. 주요한 결정 사항은 AGENTS.md 또는 docs/notes.md에 정리해두면 컨텍스트가 변해도 Codex가 일관되게 작업을 이어갑니다.

### 컨텍스트 점검

**Codex가 참고하는 정보와 구조**

| 순서 | 구성 요소 | 설명 |
| --- | --- | --- |
| 1 | 시스템 지침 | Codex의 기본 동작 원칙에 해당하는 내부 지침 |
| 2 | 프로젝트 규칙 | 현재 작업 디렉터리를 기준으로 불러온 AGENTS.md 등 프로젝트 관련 지침 |
| 3 | 도구 설정 정보 | 연결된 MCP 도구와 관련된 설정 및 사용 정보 |
| 4 | 첨부 리소스 | 대화 중 명시적으로 참조된 파일, 이미지, 기타 리소스 |
| 5 | 대화 이력 | 사용자 요청, Codex의 응답, 코드 변경 내역 등 누적된 작업 기록 |
- 필요한 순간에만 파일, 이미지, 리소스 첨부하기
- AGENTS.md는 최대한 간결하게 유지하기
- 대화 이력은 /compact로 정기적으로 정리하기

**컨텍스트 점검**

| 상태 | 여유 공간 | 권장 조치 |
| --- | --- | --- |
| 70% 이상 | 여유 | 긴 설명이나 파일 첨부 가능 |
| 40% ~ 70% | 정상 | 기능 단위로 마무리한 후 정리 시점 검토 |
| 20% ~ 40% | 주의 | 응답 지연 가능성, 요약 필요성 증가 |
| 20% 미만 | 위험 | 작업 흐름 정리 또는 새 흐름 시작 고려 |
- 정확한 토큰 수는 /status 명령으로 확인

**컨텍스트를 정리하는 두 가지 도구**

| 구분 | 작동 방식 | 사용 시점 |
| --- | --- | --- |
| /compact | 최근 대화는 유지하고 과거 내용을 자동 요약 | 기능 단위 작업 종료 후, 컨텍스트 부담이 커졌을 때 |
| 새 작업 흐름 시작(/new) | 이전 대화 기록은 세션에 남아 있고, 이후 요청은 새로운 주제를 중심으로 이어감 | 주제가 명확히 전환되거나 작업 성격이 완전히 달라질 때 |

### 컨텍스트를 지키면서 공유 정보를 늘리는 방법
1. AGENTS.md + resume 조합
	- 규칙, 원칙, 아키텍처: AGENTS.md에 정리
	- 현재 작업 현황: 세션 종료 직전에 한두 줄로 간단히 정리
	- 세션 종료 전: /compact로 대화 요약
	- 다음 작업 시작 시: codex --continue, codex resume --last, /resume 사용

2. TODO 체크리스트로 진행 상황 기록
	Codex는 체크리스트 형식을 매우 잘 인식합니다. 핵심 작업을 체크리스트로 남겨두면 대화를 요약(/compact)한 이후에도 현재 진행 상태를 빠르게 파악할 수 있는 기준점으로 활용하기 좋습니다.
```
- [ ] API 인증 로직 정리
- [x] 로그인 페이지 리펙토링 완료
```

### MCP 연결하기
~/.codex/config.toml 파일에 작성합니다.

```toml
[mcp._servers.playwright] # MCP 서버 이름은 playwright로 지정
command = "npx" # 별도 설치 없이 npx로 실행
args = ["-y", "@playwright/mcp@latest"] # 자동 확인(-y) 후 최신 MCP 실행
```
- Codex 재실행 후 /mcp 명령으로 enabled로 표시되었는지 확인

**npx를 인식하지 못할 때 해결 방법**
npx의 절대 경로를 직접 지정해야 합니다.
```toml
[mcp._servers.playwright]
command = "/opt/homebrew/bin/npx"
args = ["-y", "@playwright/mcp@latest"]
```

### MCP 환경 변수 관리
```toml
[mcp._servers.github]
command = "npx"
args = ["-y", "@modelcontextprotocol/server-github@latest"]
# env = {GITHUB_PERSONAL_TOKEN = "ghp_xxx"} # 토큰 직접 작성은 위험
env = {GITHUB_PERSONAL_TOKEN = ${GITHUB_PERSONAL_TOKEN}}
```

**환경 변수로 분리하기(권장)**
codex가 실행될 때 자동으로 불러옵니다.
```
export GITHUB_PERSONAL_TOKEN="ghp_xxx"
```

**운영체제의 보안 저장소 활용하기(고급)**

```
security add-generic-password -a "codex-github" -s "codex" -w "ghp_xxx"
```
```
export GITHUB_PERSONAL_TOKEN=${security find-generic-password -a "codex-github" -s "codex" -w}
codex
```

### PRD란?
제품 요구 사항 정의서는 "무엇을 만들것인가"를 정의하는 문서입니다. 전통적인 PRD 구성 요소는 다음과 같습니다.
- 개요
- 배경
- 목표/성공 지표
- 대상 사용자
- 기능 요구사항
- 비기능 요구 사항
- 제약 사항
- 범위 및 제외 범위
- 릴리스 계획
기업에서는 PRD가 수십 페이지로 확장되기도 하지만, AI 기반 개발에서는 이렇게 상세할 필요가 없습니다. 중요한 것은 AI가 프로젝트 의도, 기능, 범위를 정확히 이해할 만큼 구조화 되어있느냐입니다.

**AI 개발 과정에서 PRD의 역할은?**
- 프로젝트 목표와 범위 명확화
- AI 코드 생성 시 일관된 방향성 제공
- 컨텍스트 파일(AGENTS.md) 생성의 기반

### AI와 함께하는 PRD 작성법
문서를 완벽하게 만드는것이 목적 X
AI가 참고할 핵심 기준을 만드는 목적 O

1. 최소한으로 필요한 항목
	- 제품 개요 (한 문장)
	- 핵심 기능 3~5개
	- 대상 사용자
	- 기술 스택
	- 비기능 요구 사항(선택)
	- 제외 범위(선택)
	
2. 직접 작성하기
	- 입문자는 직접 작성해보는 것이 요구 정리, 기능 정의 감각을 익히는데 도움이 됩니다.
	
3. AI에 초안 생성 요청하기
	- 혼자 작성하기 어렵다면 AI 다음과 같이 초안 작성을 요청한 뒤 보완해도됩니다.
		```
		> 개인용 TODO 관리 웹 서비스를 만들려고 해. 다음 항목을 포함해 PRD를 작성해줘.
		- 제품 개요
		- 핵심 기능 5개 이하
		- 기술 스택 (FastAPI + HTML+CSS+JS)
		- 비기능 요구 사항
		```
4. 작성 시 유의 사항
	- 지나치게 상세하게 작성할 필요 없음
	- 기능 목록을 필요 이상으로 확장하지 않기
	- 기술 스택은 반드시 명시하기
	- AI에 제공할 파일로 사용할 수 있도록 구조화하기

### 예시: 개인용 TODO 웹 서비스 PRD
```
제품명: 심플 TODO

개요: 사용자가 할 일을 추가, 조회, 수정, 삭제할 수 있는 웹 기반 TODO 관리 도구입니다.

목표
1) AI 터미널 도구(Codex, Gemini CLI)를 활용한 풀스택 개발 학습
2) 30분 이내 프로토타입 제작
3) 프론트엔드-백엔드-API 구조를 단일 프로젝트로 경험
   
대상 사용자: 입문자, 개인 사용자, 학습 목적의 실습자

핵심 기능(MVP)
1) 할 일 목록 조회
2) 할 일 추가
3) 완료 처리
4) 삭제

기술 스택
1)백엔드: FastAPI
2)프론트엔드: HTML/CSS/JS
3)저장 방식: 로컬 스토리지(또는 간단한 인메모리 저장)

비기능 요구 사항
1) 직관적인 UI 구성
2) 최신 웹 브라우저에서 정상 동작
3) 입문자도 이해할 수 있는 단순한 구조
   
제외 범위
1) 사용자 인증(회원가입, 로그인)
2) 데이터베이스 연동
3) 다중 사용자 지원
4) 고급 정렬, 검색 기능
   
API 설계
백엔드 연동 방식으로 학습할 경우 다음과 같은 API를 제공합니다.
1) GET /todos: 할 일 목록 조회
2) POST /todos: 새로운 할 일 추가
3) PUT /todos/{id}: 완료 처리 또는 상태 변경
4) DELETE /todos/{id}: 할 일 삭제
```

### 실행 계획과 WBS
PRD는 "무엇을 만들 것인가"를 정의했다면, 이제는 "어떻게 만들 것인가"를 실행 계획과 WBS로 정리하는 단계입니다.

실행 계획은 프로젝트를 어떤 순서로 진행할지 정리한 로드맵입니다. 예를 들어 "백엔드 API 개발 -> 프론트엔드 구현 -> 통합 테스트"와 같이 전체 흐름을 정의합니다.

WBS는 큰 작업을 작은 단위로 분해해 관리하기 쉽게 만든 구조입니다. 예를 들어 백엔드 개발이라는 큰 항목을 데이터 모델 정의, API 엔드포인트 구현, 오류 처리 로직 추가와 같이 세분화합니다.

**AI 시대의 새로운 접근법**
AI 터미널 도구가 등장하면서 실행 계획을 수립하는 방식이 크게 변화했습니다. 이제는 모든 작업을 사람이 직접 나열하고 순서를 결정할 필요가 없습니다.
Claude Code, Codex, Gemini CLI는 모두 다음 기능을 내장합니다.
- 작업 단위 자동 분해
- 구현 순서 설계
- 작업 간 의존성 분석
- 부족한 요건이 있을 경우 확인 질문

즉, PRD만 명확히 정리해두면 AI가 논리적 흐름을 기반으로 계획을 자동 생성합니다. 이제 실행 계획의 핵심은 문서의 분량이 아니라 PRD와 컨텍스트 파일의 구체성과 일관성입니다.

### Plan 모드 활용
[shift] + [tab] -> plan 모드 on

```
> 개인용 TODO 웹앱을 만들려고 해.
@PRD.md 파일을 참고해 전체 작업을 단계별로 나누고, 필요한 세부 작업을 정리해줘
```

이후 생성된 계획 예시
```
1단계: 프로젝트 초기 설정
	- 기술 스택 선택
	- 프로젝트 구조 생성
2단계: 기본 UI 구조 작성
	- HTML 레이아웃 구성
	- 기본 스타일링
	- 반응형 디자인 적용
...
```

### AI 시대에도 WBS가 필요한 이유
AI가 순서를 제시할 수 있어도 WBS는 개발자에게 다음과 같은 중요한 가치를 제공합니다.

1. 요구 사항을 더 구체적으로 파악할 수 있다.
	- 이 기능을 구현하려면 먼저 데이터 모델이 필요하겠구나.
	- 삭제 기능은 예외처리가 꽤 많을 수 있겠네.

2. 프로젝트 구조를 직접 설계해볼 수 있다.
	- 어떤 순서로 구현되어야 하는지 등 사고 과정은 문제 분해 능력을 길러줍니다.

3. AI가 생성한 계획을 검증할 기준이 된다.
	예를 들어, AI가 "프론트엔드를 먼저 만들고 나중에 백엔드를 연결하자"라고 제안을 합니다.
	하지만 백엔드가 준비되지 않으면 화면 테스트가 어렵기 때문에 비효율적입니다. WBS가 있으면 AI 계획을 평가하고 필요한 수정 방향을 판단할 수 있습니다.

4. 학습 효과가 매우 크다.
	- 작업을 작은 단위로 분해하는 연습
	- 백엔드, 프론트엔드, 테스트이 관계 이해
	- 전체 개발 흐름 구조화

### AI를 활용한 단계별 계획 수립
#### 1단계: 큰 흐름만 정리하는 가벼운 WBS 작성
처음 부터 모든 작업을 세밀하게 나누려 하면 부담이 큽니다. AI 터미널 도구는 세부 분해를 자동으로 수행할 수 있으므로 핵심 단꼐를 중심으로 큰 흐름만 먼저 정리하면 충분합니다.

#### 2단계: AI에 초안을 검증받고 개선 방향 보완
```
> 다음은 내가 작성한 WBS야. 누락된 항목이나 순서가 어색한 부분이 있다면 검토해줘.
[WBS 초안 붙여 넣기]
```

### 간단한 WBS 템플릿
```
phase 1: 초기 설정
- 프로젝트 폴더 구조 생성
- 백엔드 환경 설정 (pyhon/FastAPI 또는 Node.js/Express 등)
- 프론트엔드 환경 설정 (HTML/CSS/JS 또는 프레임워크)
- Git 저장소 초기화 및 첫 커밋
- 프로젝트 컨텍스트 파일(AGENTS.md) 작성

phase 2: 백엔드 개발
- 데이터 모델 설계
- API 엔드포인트 구현
  - 조회 API
  - 생성 API
  - 수정 API
  - 삭제 API
- 오류 응답 구조 정의 및 예외 처리
- API 단위 테스트 및 동작 검증
  
phase 3: 프론트엔드 개발
- HTML 기본 레이아웃 구성
- CSS 스타일링
- JS 기능 구현(API 연동, UI 상호작용)
- 프론트엔드 기능 테스트

phase 4: 통합 및 배포
- 백엔드와 프론트엔드 연동
- 전체 기능 테스트
- 버그 수정 및 리펙토링
- (선택) 배포 환경 구성 및 실제 배포
```

### 컨텍스트 파일과 별도 문서의 역할 분리
컨텍스트 파일은 핵심 요약에 집중하고, 상세 내용은 다음과 같이 분리하는것이 효율적입니다.
- PRD.md: 전체 요구 사항, 기능 목록, 제외 범위 등
- api-spec.md, openapi.yaml 등: 상세 API 스펙
- db-shema.md: 데이터베이스 스키마
- designs: 화면 구조, 컴포넌트 배치, 생상 규칙, 크기 규칙 등

### 디자인과 UI 정보를 위한 별도 컨텍스트 구조화
디자인을 자연어로만 설명하면 모호성이 커집니다. "버튼 크게해줘"라고 요청하면 크게가 어느정도 크기를 의미하는지 애매할것 입니다. 그래서 디자인 정보를 별도의 구조화된 파일로 관리할 것을 권장합니다.
```
designs/
|--- main-screen.xml
|--- login-screen.xml
|--- settings-screen.xml
```

**XML을 선택한 이유는?**
- 태그와 속성으로 UI 구조를 표현할 수 있어 AI가 해석하기 쉬움
- HTML/CSS로 변환하기에 자연스러운 형태
- 몇 가지 구칙만 익히면 입문자도 읽고 수정하기 쉬움

```
> @designs/main-screen.xml을 참고해 메인 화면 UI를 만들어줘.
```

### 실전 개발 흐름
계획 모드에서 전체 계획 수립
```
> @PRD.md @AGENTS.md를 참고해 전체 개발 계획을 plan.md로 만들어줘.
```

단계별 개발 시작
```
> @plan.md의 Phase 1-1을 실행해줘
초기 폴더 구조와 기본 파일을 생성해줘.
```

백엔드 구현
```
> phase 2-1: FastAPI 기본 앱 생성
> phase 2-2: TODO 모델 정의
...
```

기본 동작 테스트
```
> 서버 실행해줘
> http://localhost:8080/docs 페이지가 정상적으로 표시되는지 확인해줘.
```

프론트엔드 개발
```
> phase 3-1: HTML 기본 레이아웃 작성
> phase 3-2: CSS 스타일 적용
...
```


통합 테스트
```
> 백엔드 서버가 실행 중인 상태에서 forntend/index.html을 열어 전체 기능을 테스트해줘
```

**plan.md 단계가 크다면?**
단계를 더 작은 단위로 나누도록 요청하세요.
```
> phase 2 백엔드 개발 범위가 너무 커, 각 API 엔드 포인트를 별도 단계로 분리해줘.
```
