## 왜 이런 순서로 진행했는가  
  
수강 신청 시스템은 단순 CRUD보다 상태 전이와 정원 관리가 중요한 과제라고 판단했습니다.  
  
특히 아래 세 가지를 먼저 구조적으로 풀어야 이후 구현이 흔들리지 않는다고 봤습니다.  
  
- 사용자 권한이 분리되어야 강사 전용 기능과 수강생 기능을 구분할 수 있습니다.  
- 강의와 수강 신청은 서로 연결되지만 책임이 다르기 때문에 도메인 경계를 먼저 분리해야 합니다.  
- 정원 초과, 결제 확정, 취소, 웨이팅 승격은 모두 상태 전이 문제이기 때문에 트랜잭션 경계와 도메인 규칙을 초기에 정리해야 합니다.  
  
그래서 기능 구현보다 먼저 `common`, `identity`, `course`, `enrollment` 중심의 구조와 문서화/테스트 기반을 준비한 것으로 보입니다.  
  
---  
  
## 프로젝트 정의  
  
이 프로젝트는 단순한 강의 CRUD가 아니라 아래 범위를 다루는 수강 신청 시스템으로 정의합니다.
  
- 강의 등록, 목록, 상세 조회  
- 수강 신청, 수강 확정, 수강 취소  
- 강의 상태 관리와 신청 상태 관리  
- 정원 초과 상황 처리  
- 취소 가능 기간 제한  
- 웨이팅과 강의별 수강생 조회  

조건
  
- 결제는 외부 PG 연동 없이 내부 상태 변경으로 단순화했습니다.  
- 정원이 가득 찬 경우 완전 거절 대신 `WAITING`으로 등록합니다.  
- 웨이팅 승격은 가장 오래 기다린 신청자 우선입니다.  
- 현재 신청 인원은 `PENDING`, `CONFIRMED` 기준으로 계산합니다.  
  
구현 범위
  
- `identity`, `course`, `enrollment`는 controller, application, domain, infrastructure가 모두 연결된 상태입니다.  
- 강의 상태 전이 메서드는 도메인에 존재하지만, 이를 여는 공개 API는 아직 없습니다.  
- 동시성은 정합성을 우선하는 방향으로 다뤘지만 운영 규모 검증은 별도 과제로 남아 있습니다.

## 개발 과정에서 드러난 설계 방향  
  
### 1. 도메인 기준 패키지 분리  
  
이 프로젝트는 기능이 아니라 도메인 기준으로 `identity`, `course`, `enrollment`, `common`을 나눴습니다.  
  
이 방식의 장점은 명확합니다.  
  
- 강의 관련 규칙은 `course`에 모입니다.  
- 수강 신청 라이프사이클은 `enrollment`에 모입니다.  
- 인증과 사용자는 `identity`가 담당합니다.  
  
수강 신청 시스템은 기능 간 연결은 많지만 변경 이유는 다르기 때문에, 이 분리는 유지보수 관점에서 타당합니다.  
  
### 2. 상태 전이 중심 설계  
  
강의와 수강 신청 모두 상태가 핵심입니다.  
  
- 강의: `DRAFT -> OPEN -> CLOSED`  
- 신청: `PENDING -> CONFIRMED -> CANCELLED`  
- 확장 상태: `WAITING`  
  
이 프로젝트는 CRUD보다 상태 전이 설계를 먼저 잡으려는 흔적이 분명합니다.  
  
그 결과, 단순 테이블 조작이 아니라 "어떤 상태에서 어떤 행동이 가능한가"를 중심으로 기능이 확장되었습니다.  
  
### 3. 트랜잭션 안에서 정원과 신청 상태를 함께 관리  
  
정원 관리는 단순 숫자 변경이 아닙니다.  
  
신청 생성, 취소, 웨이팅 승격은 모두 강의 인원 수와 연결됩니다.  
  
이 프로젝트는 이 문제를 애플리케이션 서비스의 트랜잭션 경계 안에서 함께 다루는 방향을 선택했습니다.  
  
이는 실무적으로도 맞는 선택입니다.  
좌석 수와 신청 상태가 따로 놀기 시작하면, 나중에 오류를 복구하는 비용이 더 커지기 때문입니다.  
  
### 4. 구현과 문서화를 함께 가져가는 방식  
  
초기부터 API 명세 환경, 테스트 가이드, 아키텍처 문서, README, ERD를 꾸준히 보강했습니다.  
  
과제 제출용을 넘어, "이 저장소를 다른 사람이 이해할 수 있게 유지한다"는 관점이 반영된 부분입니다.  
  
특히 `docs/code-style.md`, `docs/architecture.md`, `docs/test-guide.md`가 분리되어 있는 점은 이후 작업에서 기준이 흔들리지 않도록 하려는 의도가 분명합니다.

## DDD 관점에서 정리한 설계 방식  
  
이 프로젝트는 완전한 전략적 DDD 전개까지는 아니더라도, 적어도 전술적 DDD의 핵심 요소를 적극적으로 사용한 구조로 볼 수 있습니다.  
  
### 어그리게이트 경계  
  
코드 기준으로 보면 `Course`와 `Enrollment`는 각각 독립적인 어그리게이트 루트입니다.  
  
- `Course`는 강의 상태, 정원, 강사 권한이라는 규칙을 소유합니다.  
- `Enrollment`는 신청 상태, 결제 확정, 취소 가능 여부, 접근 가능 여부를 소유합니다.  
  
두 도메인이 서로 연결되어 있어도 책임은 섞지 않았습니다.  
예를 들어 정원이라는 개념은 `Course`가 가지고, 신청 상태 전이는 `Enrollment`가 가집니다.  
수강 신청 유스케이스는 이 둘을 `EnrollmentService`에서 조합합니다.  
  
이런 분리는 실무적으로 중요합니다.  
강의 규칙을 바꿀 때와 신청 규칙을 바꿀 때 수정 지점을 분리할 수 있기 때문입니다.  
  
### 값 객체와 의미 있는 상태 변경  
  
정원은 단순 정수 두 개가 아니라 `Capacity`라는 값 객체로 분리되어 있습니다.  
  
- 최대 정원 검증  
- 현재 신청 인원 증가/감소  
- 정원 초과 여부 판단  
  
이 로직을 `Course` 밖의 서비스나 컨트롤러에 두지 않고 값 객체에 모아 둔 것은, 도메인 규칙을 타입 안으로 밀어 넣은 전형적인 DDD 스타일입니다.  
  
또한 상태 변경은 setter가 아니라 의미 있는 메서드로만 이뤄집니다.  
  
- `Course.open()`  
- `Course.close()`  
- `Enrollment.confirmPayment()`  
- `Enrollment.cancelApplication()`  
- `Enrollment.cancelConfirmed()`  
- `Enrollment.promoteToPending()`  
  
즉, "필드 값을 바꾼다"가 아니라 "도메인 행위를 수행한다"는 관점으로 모델을 세운 것입니다.  
  
### 애플리케이션 계층의 역할 분리  
  
`docs/architecture.md`에 적힌 것처럼, 이 프로젝트는 `presentation -> application -> domain -> infrastructure` 계층을 비교적 일관되게 유지하고 있습니다.  
  
특히 `EnrollmentService`는 도메인 규칙을 직접 소유하지 않고 아래 역할만 수행합니다.  
  
- 트랜잭션 경계 설정  
- 여러 어그리게이트 조회  
- 접근 권한 검증  
- 상태 전이 호출 순서 제어  
- 웨이팅 승격 후속 처리 연결  
  
이 점이 중요합니다.  
도메인 규칙은 엔티티/정책에 두고, 유스케이스 흐름은 애플리케이션 서비스가 조율하는 구조이기 때문입니다.

## 상태 전이 설계를 어떻게 풀었는가  
  
이 프로젝트의 핵심은 CRUD보다 상태 전이 설계에 있습니다.  
  
### 강의 상태 전이  
  
강의는 아래 흐름으로 모델링되어 있습니다.  
  
```text  
DRAFT -> OPEN -> CLOSED  
```  
  
여기서 드러나는 정책은 명확합니다.  
  
- 초안 강의만 모집을 시작할 수 있습니다.  
- 모집 중인 강의만 마감할 수 있습니다.  
- `DRAFT` 강의는 상세 조회에서도 공개하지 않습니다.  
- 수강 신청은 `OPEN` 상태에서만 가능합니다.  
  
즉, 강의는 단순 게시물이 아니라 모집 가능 여부를 가진 상태 머신으로 다뤄집니다.  
  
### 수강 신청 상태 전이  
  
수강 신청은 아래 상태를 중심으로 움직입니다.  
  
```text  
PENDING -> CONFIRMED -> CANCELLED  
WAITING -> PENDING  
```  
  
실제 흐름은 조금 더 구체적입니다.  
  
- 신청 시 정원이 남아 있으면 `PENDING`  
- 신청 시 정원이 가득 찼으면 `WAITING`  
- 결제 확정 시 `PENDING -> CONFIRMED`  
- 결제 대기 취소 시 `PENDING` 신청 제거  
- 결제 확정 취소 시 `CONFIRMED -> CANCELLED`  
- 좌석이 생기면 가장 오래된 `WAITING -> PENDING`  
  
이 설계의 장점은 상태마다 가능한 행동을 명확히 제한한다는 점입니다.  
  
- `PENDING`만 결제 확정할 수 있습니다.  
- `PENDING`만 일반 취소할 수 있습니다.  
- `CONFIRMED`만 환불 취소할 수 있습니다.  
- `WAITING`만 웨이팅 취소할 수 있습니다.  
  
결과적으로 잘못된 API 호출이 들어와도, 컨트롤러 분기문이 아니라 도메인 메서드 내부에서 규칙을 막을 수 있습니다.  
  
### 상태 전이와 정원 변경을 분리하지 않은 이유  
  
이 프로젝트는 상태 전이와 정원 수 변경을 별개의 후처리로 흩뿌리지 않았습니다.  
  
예를 들어,  
  
- `Enrollment.apply()`는 신청 상태를 만들면서 필요하면 `Course` 정원도 함께 증가시킵니다.  
- `cancelApplication()`과 `cancelConfirmed()`는 취소 상태 판단과 정원 감소를 함께 묶습니다.  
- 웨이팅 승격도 `promoteOldestWaitingEnrollment()` 안에서 상태 변경과 정원 증가를 같이 처리합니다.  
  
이렇게 해야 정원 수와 신청 상태가 어긋나는 중간 상태를 줄일 수 있습니다.

## 락 선택과 동시성 처리 판단  
  
이 프로젝트에서 가장 실무적인 설계 결정 중 하나는 락 전략입니다.  
  
### 왜 락이 필요한가  
  
수강 신청은 아래 순서의 읽기-판단-쓰기 흐름을 가집니다.  
  
```text  
강의 조회  
-> 정원 확인  
-> 신청 상태 결정(PENDING 또는 WAITING)  
-> 현재 신청 인원 반영  
```  
  
취소와 웨이팅 승격도 비슷합니다.  
  
```text  
신청 조회  
-> 취소 가능 여부 판단  
-> 정원 감소  
-> 가장 오래된 WAITING 조회  
-> WAITING 승격  
-> 정원 증가  
```  
  
이 흐름은 모두 공유 자원인 `Course.capacity.current`와 웨이팅 순서에 동시에 영향을 줍니다.  
  
### 현재 구현이 선택한 방식  
  
현재 구현은 낙관적 락이 아니라 비관적 락을 사용합니다.  
  
- `CourseRepository.findByIdForUpdate()`  
- `JpaCourseRepository`의 `@Lock(LockModeType.PESSIMISTIC_WRITE)`  
- 웨이팅 승격 조회의 `@Lock(PESSIMISTIC_WRITE)`  
  
즉, 같은 강의의 좌석 수를 바꾸는 작업은 먼저 잠그고 순차적으로 처리하는 전략입니다.  
  
### 왜 비관적 락이 맞았는가  
  
이 과제에서 중요한 것은 처리량보다 정합성이었습니다.  
  
특히 마지막 자리 경쟁이나 동시 취소 상황에서는 아래 두 문제가 바로 생길 수 있습니다.  
  
- 두 명이 동시에 정원이 남았다고 판단하는 문제  
- 둘 이상의 요청이 같은 웨이팅 신청을 동시에 승격하는 문제  
  
이 프로젝트는 이 문제를 "충돌이 나면 나중에 재시도" 방식보다, "처음부터 같은 강의 단위 변경을 직렬화"하는 쪽으로 풀었습니다.  
  
이 판단은 현재 요구사항과 잘 맞습니다.  
  
- 정원은 작고 명확한 공유 자원입니다.  
- 웨이팅 승격 순서는 꼬이면 안 됩니다.  
- 실제 운영급 대량 트래픽보다 정확한 상태 전이가 우선입니다.

## 구현 중 부딪혔던 핵심 문제  
  
### 정원 초과와 마지막 좌석 경쟁  
  
수강 신청 시스템에서 가장 민감한 문제입니다.  
  
단순 조회 후 저장 방식으로 처리하면 동시에 여러 요청이 들어왔을 때 정원 초과가 발생할 수 있습니다.  
  
이 저장소는 관련 커밋 흐름상 비관적 락과 정원 카운팅 보강으로 이 문제를 풀었습니다.  
  
즉, 성능보다 정합성을 우선한 판단입니다.  
  
### 대기열을 어디까지 구현할 것인가  
  
웨이팅은 단순히 상태 하나 추가한다고 끝나지 않습니다.  
  
- 누가 먼저 기다렸는가  
- 취소가 발생했을 때 누구를 승격할 것인가  
- 승격 후 상태를 무엇으로 바꿀 것인가  
  
이 프로젝트는 가장 오래 기다린 신청자를 `PENDING`으로 승격하는 선에서 범위를 정했습니다.  
  
실무적으로도 과제 범위에서 과하지 않으면서, 요구사항 해석을 분명하게 보여주는 선택입니다.  
  
### 취소 정책을 얼마나 구체화할 것인가  
  
`CONFIRMED` 취소는 결제 후 7일 제한이 있고, `PENDING` 취소는 처리 방식이 다릅니다.  
  
이 저장소는 취소를 하나의 API로 뭉개지 않고 상태별 정책을 분리해 구현했습니다.  
  
이 부분은 도메인 규칙을 더 명확하게 만든 지점입니다.

## 작업 방식에 대한 회고  
  
### 잘한 점  
  
- 공통 기반과 문서화를 먼저 잡아 이후 기능 확장이 안정적이었습니다.  
- 도메인을 `identity`, `course`, `enrollment`로 분리해 책임이 비교적 선명합니다.  
- 강의보다 수강 신청이 더 어렵다는 점을 인식하고, 신청 도메인을 별도로 키워 나간 흐름이 좋습니다.  
- 웨이팅과 동시성까지 다뤄 과제 수준 이상의 완성도를 만들었습니다.  
- 릴리즈 직전에 README, ERD, 더미 데이터까지 정리해 제출 품질을 높였습니다.  
  
### 아쉬운 점  
  
- 강의 상태 전이 API와 자동 마감 같은 운영 기능은 아직 열려 있지 않습니다.  
- `PENDING` 만료 처리나 웨이팅 승격 알림 같은 후속 운영 기능은 빠져 있습니다.  
- 동시성 정합성은 고려했지만, 실제 부하 테스트나 운영 규모 기준의 성능 검증은 아직 부족합니다.  
  
### 다음에 확장한다면  
  
- 강의 `OPEN/CLOSED` 전환 API와 스케줄 기반 자동 마감 기능을 추가할 수 있습니다.  
- 결제 대기 만료 배치 또는 이벤트 기반 정리 로직이 필요합니다.  
- 웨이팅 승격 알림과 결제 유도 흐름을 붙이면 사용자 경험이 더 완성됩니다.  
- 동시성 시나리오에 대한 통합 테스트와 부하 테스트를 보강하면 운영 신뢰도가 올라갑니다.
