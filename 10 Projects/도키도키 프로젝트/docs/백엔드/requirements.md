# 백엔드 기능 요구사항

근거는 [화면 흐름](references/frontend/docs/01-screens-and-flows.md), [API 설계](references/frontend/docs/03-api-and-msw.md), 실제 `references/frontend/src/features/`와 `src/mocks/`입니다. 아래 API는 모두 `/api/v1` 기준의 **현재 초안**입니다. DTO 세부 타입은 [API 비교](api-contract-review.md)를 따릅니다.

## R01 사용자 및 인증

- 기능: 이메일·비밀번호 회원가입/로그인, 세션 확인, 로그아웃, 쓰기용 CSRF 발급입니다.
- 데이터/요청: `SignupInput={email,password,nickname}`, `Credentials={email,password}`; 응답 `User={id,email,nickname}`, `CsrfToken={token}`입니다.
- API: GET `/auth/csrf` 200, POST `/auth/signup` 201, POST `/auth/login` 200, POST `/auth/logout` 204, GET `/me` 200입니다. 앞의 CSRF·가입·로그인만 익명 접근입니다.
- 요구: 서버에서 사용자 식별·권한을 검증하고 비밀번호를 안전한 단방향 해시로 보관합니다. 응답·로그에 비밀번호나 비밀 정보를 노출하지 않습니다.
- 가정: 가입 즉시 로그인, `doki_session` 쿠키와 CSRF, 이메일 중복 409입니다. 가입 비밀번호 8~128자, 로그인 1~128자, 이메일 최대 254자, 닉네임 trim 1~16자는 임시입니다. 이메일 대소문자·정규화·인증/복구는 미정입니다.
- 변화/예외: 가입/로그인 후 User를 캐시에 반영하고 다른 사용자의 캐시를 제거합니다. 401은 인증 실패/만료, 403은 CSRF 실패, 422는 필드 검증, 429는 재제출 대기입니다. 네트워크 오류는 로그아웃 성공이 아닙니다. 이미 만료된 로그아웃 401은 프론트가 종료로 수용합니다.
- 수용 기준: 가입→내 정보→로그아웃→재로그인, 세션 지속성·회전·만료, 사용자 전환 데이터 격리를 실제 HTTP/브라우저에서 검증해야 합니다. 메모리 인증 검증으로 대체하지 않습니다.

## R02 애니메이션 작품 데이터

- 기능: 검색·상세·기록·추천이 공통으로 참조하는 카탈로그를 제공합니다. 관리자/적재 API는 현재 프론트에 없습니다.
- 데이터: `Anime={id,title,posterUrl,recordId}`이며 posterUrl과 recordId는 필수 키지만 null 허용입니다. title은 표시용이고 ID는 불투명 문자열입니다.
- 요구: 제목을 PK로 쓰지 않고 고유 ID로 참조합니다. 다국어·별칭·동명·시즌/시리즈를 구별해야 하지만 현재 프론트 DTO/fixture에는 해당 필드가 없습니다.
- 가정/제안: 카탈로그 원본과 외부 ID 매핑·수집 권리·갱신 주기를 먼저 확인합니다. 제목 목록/시즌 관계의 별도 모델은 후보입니다. 12개 fixture를 운영 데이터셋으로 간주하지 않습니다.
- 권한/상태: 현 초안의 조회는 로그인 필요이고 recordId는 현재 사용자에게만 해당합니다. 다른 사용자 기록 ID를 섞지 않습니다. 작품 삭제/병합 시 기존 기록·추천의 참조 처리 정책은 미정입니다.
- 수용 기준: 동일 제목의 다른 작품을 ID로 분리하고, 미존재 작품을 기록/추천에 사용하지 않습니다. 다국어 원본 제공과 매칭 검증은 실제 데이터 확보 후 수행합니다.

## R03 작품 검색·상세

- API: GET `/anime?q=&cursor=&limit=` → 200 AnimePage, GET `/anime/{animeId}` → 200 AnimeDetail, 없는 작품은 404입니다.
- 관찰: 제목 trim·대소문자 무시 부분 검색, 빈 q는 초기 목록입니다. Mock은 한국어 locale 기준 title 오름차순 후 id 순입니다. 기본 limit 20, 최대 50, q 최대 100자입니다. 명시적 sort/장르 필터는 없습니다.
- 데이터: `{items:Anime[],nextCursor:string|null}`과 `Anime + {recommendation:RecommendationInfo|null}`입니다. 전체 건수는 작품 목록 DTO에 없습니다.
- 권한: 세션으로 본인 기록을 조합하며 인증 실패는 401입니다. 잘못된 파라미터/커서는 400입니다.
- 프론트 기대: 300ms 한글 조합 종료 후 URL 검색, 조건 변경 시 커서 초기화, 더 보기, recordId 유무에 따른 등록/수정 분기, 상세 null 추천 안내입니다.
- 미결정: 별칭·언어 검색 범위, Unicode/DB 정렬, 빈 검색의 우선순위, 데이터 변경 시 커서 유효성·중복/누락 허용 범위입니다. Mock offset 커서를 운영 알고리즘으로 확정하지 않습니다.

## R04 사용자 시청 기록 CRUD

- API: GET/POST `/records`, GET/PUT/DELETE `/records/{recordId}`, GET `/records/summary`입니다. 조회/수정 200, 생성 201, 삭제 204입니다.
- 입력: 생성 `{animeId,entry}`, 수정 `{entry}`입니다. `entry`는 `{status:"completed",rating:1~5 정수}` 또는 `{status:"stopped",reason:문자열}`입니다. 생성 animeId와 수정 대상 작품은 분리되며 PUT으로 작품 변경은 지원하지 않습니다.
- 요구: 완료 정수 평가와 중단 필수 사유를 서버에서 검증하고 본인 소유 기록에만 접근합니다. 상태에 맞지 않는 입력 처리 규칙을 명시합니다.
- 현재 초안/관찰: 중단 사유 trim 1~200자, 원시 요청 inactive/unknown 필드는 422, API 모듈은 inactive 필드를 제거합니다. 완료↔중단 전체 교체 때 이전 상태 값은 사라집니다. 완료 사유와 나중에 보기는 미구현·A09 미결정입니다.
- 가정: 사용자·작품당 1개, 중복 409 `RECORD_ALREADY_EXISTS`와 본인 `existingRecordId`, 생성 UUID `Idempotency-Key` 성공 결과 24시간 재사용입니다. 재시청 다중 기록은 승인되지 않았습니다.
- 수정/삭제: 읽은 version을 따옴표 포함 `If-Match`로 보냅니다. 누락 428, 문법 오류 400, 충돌 412입니다. 타인/없는 기록은 404이며 소유권은 서버에서 확인합니다.
- 목록/집계: q/status/cursor/limit, 전체 필터는 status 생략입니다. 기록은 updatedAt 내림차순 후 id 순, 집계는 `completedCount,stoppedCount,totalCount`로 본인 전체 기록 기준입니다.
- 프론트 기대: 응답 성공 후에만 결과 화면, 실패 입력 보존, 중복 시 기존 수정 링크, 충돌 후 명시적 최신 조회·입력 초기화, 삭제 확인 후 성공 시 캐시 제거입니다. 기록·집계·작품 recordId·추천 캐시는 함께 무효화합니다.
- 제안/수용 기준: 소유권·조건부 갱신·중복·멱등 성공 저장의 원자성과 동시 요청을 검증합니다. 추천 장애가 이미 성공한 기록 저장을 실패로 보이게 해서는 안 됩니다. hard/soft delete와 삭제 후 멱등 응답 재생은 결정이 필요합니다.

## R05 사용자 프로필 관리

- API: GET `/me`, PATCH `/me` `{nickname}` → 전체 User 200입니다. 이메일·비밀번호 변경 API는 없습니다.
- 가정/관찰: trim 1~16자, 빈 값 422, UI에서 미변경 제출을 막습니다. Mock은 동일 닉네임 PATCH도 받아들이므로 미변경 거부는 서버 계약이 아닙니다.
- 권한: 세션 사용자만 수정합니다. 사용자 ID를 요청 body로 받지 않습니다. 401/403/422/429/5xx에서 입력을 유지하거나 인증을 갱신합니다.
- 프론트 기대: 저장 응답의 nickname을 결과 화면과 me 캐시에 반영하고 오래된 GET을 취소합니다. 세션 전환 뒤 늦은 PATCH 응답을 반영하지 않습니다.
- 미결정/수용 기준: 중복 닉네임, 변경 횟수, 동시 수정, 보관/탈퇴 정책을 합의합니다. 현재 version/If-Match가 없으며 마지막 쓰기 우선은 Mock 관찰일 뿐입니다. 재로그인 이후 최신 프로필을 반환해야 합니다.

## R06 개인화 추천·AI 연동

- API: GET `/recommendations` → RecommendationList 200입니다. 생성/재계산 POST나 job/SSE API는 없습니다. 상세는 같은 작품의 nullable 추천 정보를 제공합니다.
- 데이터: status `ready|updating|unavailable`, mode `personalized|starter`, items 최대 10개, generatedAt은 날짜 문자열 또는 null입니다. 항목은 anime, level `high|medium|low`, 비어 있지 않은 reason입니다.
- 요구: AI 응답 구조와 필수 데이터를 검증하고 DB에 존재하는 정확한 작품으로 매칭합니다. 동명·시즌 모호성이나 미매칭을 임의 보완하지 않습니다. 불필요한 개인정보·비밀값을 AI로 보내지 않습니다.
- 초안 기대: 이력 없는 starter와 개인화를 구분하고, 기등록 작품을 제외하며 0~9개도 정상입니다. level은 확률/별점이 아닙니다. 계산은 기록 저장과 분리하고 updating이면 보이는 화면에서 2초 간격 최대 30초 재조회, 이후 수동 재조회입니다.
- 관찰: Mock은 기록 존재에 따라 mode만 바꾸고 정적 카탈로그 순서/문구를 사용합니다. 실제 AI 호출·개인화 계산·비용/품질 검증은 없습니다.
- 예외/미결정: unavailable과 503의 구분, 오래된 결과·상세 이유의 일관성, 재시도 주체, 타임아웃·할당량·잘못된 JSON·부분 매칭, 생성 시각·갱신 SLA입니다.
- 제안/수용 기준: AI 호출을 DB 트랜잭션 밖에서 수행하고 최신 기록 기준 결과만 공개합니다. Mock/Stub으로 오류·모호성·허구 작품·중복·타임아웃을 검증하며 유료 호출 없는 자동 테스트를 구성합니다.

## 범위 제외와 우선 결정

커뮤니티, 재생, 찜, 소셜 로그인, 관리자, 알림, 결제는 프론트 착수 범위 밖입니다. 이메일 인증/복구·탈퇴는 출시 정책 미정으로 남깁니다. 나중에 보기와 완료 사유는 요구 이력이 있으나 A09에서 포함/연기를 결정해야 합니다. 새 기능을 암묵적으로 제외하거나 구현하지 않습니다.
