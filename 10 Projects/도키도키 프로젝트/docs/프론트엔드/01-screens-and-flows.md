## 흐름 규칙

1. 첫 방문: 로그인 → 가입 → 가입 완료 → 작품 검색 → 기록 등록 → 등록 완료 → 시청 이력 → 홈 추천입니다. 가입 직후 세션 발급은 가정 A01입니다. 최초 이력이 없는 추천은 개인화되었다고 단정하지 않습니다.
2. 탐색: 홈 대표/가로 카드 → 해당 작품 상세, 홈 전체 보기 → 추천 10개 → 해당 작품 상세입니다. FigCraft 여러 링크가 노드 397에 모이지만 React에서는 실제 `animeId`를 전달합니다. 배열 인덱스를 영구 ID로 쓰지 않습니다.
3. 기록: 검색 결과 `recordId`가 있으면 수정, 없으면 등록합니다. 상세에도 동일한 분기를 적용합니다. 목록 한 페이지만 보고 중복 여부를 판단하지 않습니다. 등록 중 다른 탭에서 기록이 생기면 409를 받아 기존 수정 경로를 안내합니다.
4. 완료는 정수 평가 1~5, 기본 5입니다. 중단은 공백 제거 후 1~200자의 사유입니다. 상태 전환 중 로컬 입력은 보존할 수 있으나 요청에는 활성 상태 필드만 보냅니다. 완료 요청에 사유, 중단 요청에 평가는 보내지 않습니다.
5. 수정은 현재 서버 값을 불러온 뒤 폼을 초기화합니다. 백그라운드 재조회로 사용자의 편집 내용을 덮지 않습니다. 삭제 버튼 → 확인 대화상자(추가 설계) → DELETE 성공 → 삭제 결과입니다. 취소는 폼을 유지합니다.
6. 성공 화면은 클릭 즉시가 아니라 2xx 응답 후 진입합니다. 등록·수정은 응답의 기록을, 삭제는 삭제 전에 보관한 제목을 사용합니다. 추천 갱신 실패를 기록 저장 실패로 표시하지 않습니다.
7. 마이 건수는 전체 서버 집계를 사용하며 현재 검색 결과나 페이지 길이로 계산하지 않습니다. 프로필 수정은 닉네임만입니다. 로그아웃은 서버 세션 종료 후 사용자 캐시와 결과 상태를 비웁니다.

## 라우터와 복원

- `/login`, `/signup`은 공개 경로입니다. 나머지는 세션 로딩 → 인증/비인증/오류를 구분하는 보호 레이아웃 안에 둡니다. 네트워크 오류를 로그아웃으로 취급하지 않습니다.
- `createBrowserRouter`의 Data Mode를 쓰되 서버 데이터는 TanStack Query 한 곳에서 관리합니다. route loader가 필요하면 같은 query 옵션의 `ensureQueryData`를 사용하고 별도 fetch 캐시를 만들지 않습니다.
- 탭바는 `/`, `/history`, `/my`에만 표시합니다. 로그인은 앱바가 없고, 폼/결과는 하단 CTA를 사용합니다. 상세의 기록 버튼은 원본처럼 콘텐츠 흐름 안에 있습니다.
- 목록 `q`, 이력 `status=all|completed|stopped`는 URL이 소유합니다. 빈 값은 생략합니다. 검색 입력은 로컬 상태에서 한글 조합 종료 후 300ms debounce하여 URL을 replace하고, 필터 변경 시 커서를 초기화합니다. 필터 선택은 history entry로 남겨 뒤로 복원합니다.
- 목록 복귀 시 검색/필터/스크롤을 복원합니다. 상세·폼의 뒤로는 앱 내 진입 위치가 확인되면 이전 경로, 직접 진입이면 상세는 `/recommendations`, 기록/검색은 `/history`, 프로필은 `/my`, 가입은 `/login`으로 보냅니다. 외부 `returnTo`는 금지하고 내부 허용 경로만 받습니다.
- 결과 데이터는 `location.state`의 `{kind, entityId, summary}`를 사용합니다. 새 탭·직접 진입 등 state가 없으면 기록 결과는 `/history`, 프로필 결과는 `/my`, 가입 결과는 세션 유무에 따라 `/search` 또는 `/login`으로 replace합니다. 새로고침에서 state가 남아도 mutation을 재실행하지 않습니다. state는 인증 근거가 아닙니다.
- 성공 이동은 폼 history entry를 replace합니다. 미저장 변경 시 내부 이동과 탭 닫기 경고를 적용합니다. 저장 중에는 중복 제출과 이탈을 제어합니다.
- 앱 전체 404와 route error boundary를 추가합니다. 배포 서버는 `/api/*`와 정적 파일을 제외한 앱 경로에 `index.html` fallback을 제공합니다.

## 원본 해석 주의점

`out/journey.md`는 중단 사유 선택+직접 입력을 가정했지만 실제 HTML 및 FigCraft 상태 명세는 textarea입니다. 1차는 직접 입력만 구현합니다. 추천 예상도는 평점이나 확률이 아니므로 퍼센트로 변환하지 않습니다. 5개 결과 화면은 독립된 샘플이며 초기 데이터에 결과를 일괄 반영하지 않습니다.

## P0-2에서 제공하는 범위

위 표의 16개 경로를 등록했습니다. 기능 화면 11개는 공통 `RoutePendingPage`로 화면 이름과 동적 ID, 필요한 이동 링크만 표시합니다. 저장·로그인·회원가입을 흉내 내는 동작은 없습니다. 성공 응답을 생성할 API가 없으므로 결과 경로 5개는 항상 replace 복귀하며, 가입 결과는 현재 `/login`으로 복귀합니다. P2에서 세션과 가입 성공 state를 연결하면 `/search` 분기를 추가합니다. 기록/프로필 결과는 각 mutation 구현 시 성공 state 검증과 함께 교체합니다.

인증이 필요한 경로의 보호 레이아웃은 P0-3의 `/me` 검증과 P2에서 연결합니다. 현재 준비 화면은 공개 접근이 가능하며 개인정보를 조회하지 않습니다. 현재 복귀 링크는 명시적인 안전 경로이고, 앱 내부 진입 위치를 추적하는 뒤로 버튼·returnTo 검증·검색 debounce/필터·미저장 이탈 방지는 해당 기능 단계에서 구현합니다. URL의 기존 query string과 브라우저 뒤로/앞으로 이동은 유지합니다.

## P2 현재 상태

인증 세 화면·보호 라우트·성공 결과 state·Query 세션·로그아웃을 연결했습니다. 가입 성공 CTA는 `/search`, 로그인은 허용된 내부 복귀 경로 또는 `/`로 이동합니다. API 계약 초안은 변경하지 않았으며 구현·검증·Mock 메모리 세션의 제한은 [인증 구현 안내](10-auth.md)를 확인합니다.

## P3 검색·P4 현재 상태

history/search/record/record-done은 실제 Query/API 화면으로 전환했습니다. q/status URL 복원, 더 보기, 한글 조합·debounce, 미저장 이탈 안내를 연결했습니다. 등록 결과 state는 `{kind:'record-created', userId, entityId, summary:{title,entry}}`를 검증하고 성공 응답 이후 replace합니다. P5에서 수정·삭제 결과도 연결했으며 프로필 결과는 후속 단계입니다. [구현 안내](12-watch-records.md)를 확인합니다.


## P5 현재 상태

edit/edit-done/delete-done을 실제 조회·수정·삭제 흐름으로 연결했습니다. 편집 시작 시 서버 값과 version을 고정하고, 충돌 시 명시적 최신 조회로만 입력을 초기화합니다. 삭제 확인 dialog는 추가 설계이며 API 204 뒤에만 결과로 이동합니다. 결과 state는 수정 `record-updated`와 삭제 `record-deleted`를 구분하며 삭제 summary에는 제목만 보관합니다. 인증된 상태의 증거 없는 직접 접근은 `/history`로 복귀합니다. 비인증 접근의 로그인 복귀는 기존 안전한 returnTo 정책에 따릅니다.


## P6 현재 상태

my/profile/profile-done을 기존 me·집계 Query와 연결했습니다. 닉네임 PATCH 성공 응답으로 사용자 정보를 갱신하고 결과 state의 사용자 ID를 검사합니다. 마이 전체 건수·로그아웃·입력 오류·직접 결과 접근 복귀를 연결했습니다. 16개 화면의 Mock 기반 기능 구현을 완료했으며 [마이·프로필 구현 안내](13-profile.md)에 검증과 실제 서버 연결 제약을 기록했습니다. 앞의 P0~P5 설명은 각 단계의 이력입니다.
