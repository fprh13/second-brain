# 실시간 음성 스트리밍

---

## 📄 본문
### WebRTC란?
WebRTC는 웹 브라우저 간에 실시간으로 오디오와 비디오 같은 데이터를 직접 주고 받을 수 있게 하는 기술이다. 브라우저에서 별도의 플러그인 없이 실시간 통신을 가능하게 하는 웹 표준 기술이며, 화상 회의, 음성 통화, 실시간 스트리밍 등에 사용된다. WebRTC를 이용한 미디어 전달 구조는 Mesh 방식, MCU방식, SFU방식이 있다.

#### WebRTC Mesh
브라우저 간 Peer-to-Peer로 연결되며, N 구조로 확장할 경우 Peer 연결 수가 증가하면서 클라이언트의 부하가 커지는 특징이 있다.

#### WebRTC MCU
MCU 방식은 서버와 브라우저가 Peer Connection을 맺는 구조이다. 서버는 각 참가자의 미디어 스트림을 수신한 후 하나의 스트림으로 합성하여 다시 전달한다.
- 장점: 클라이언트의 부담이 적다.
- 단점: 미디어 합성 과정으로 인해 서버의 CPU 사용량이 크다.

#### WebRTC SFU
서버와 브라우저가 Peer Connection을 맺는 구조이다. 서버는 여러 참가자의 미디어를 수신한 후 합성하지 않고 필요한 참가자에게 그대로 전달한다.
- 장점: MCU 방식에 비해 서버의 연산 부담이 적고 확장성이 좋다. 1 구조에 적합하다.
- 단점: 클라이언트가 여러 개의 스트림을 처리해야 한다.

#### SFU와 MCU의 1 대 N 구조 차이
1 대 N 구조에서는 SFU가 MCU에 비해 서버의 CPU 부담이 적다.
SFU는 발표자의 미디어 스트림을 별도로 합성하지 않고 각 청중에게 전달한다.

`발표자 음성 → SFU → 전달 → 청중 100명`

반면 MCU는 수신한 미디어를 디코딩하고 합성한 뒤 다시 인코딩하여 전달하는 방식이다.

`발표자 음성 → MCU → 디코딩·합성·인코딩 → 전달 → 청중 100명`

발표자가 한 명인 1 대 N 구조에서는 합성해야 할 여러 미디어 스트림이 없기 때문에 MCU의 합성 기능을 사용할 이점이 크지 않다. 따라서 단순한 1 대 N 미디어 전달에는 SFU 방식이 더 적합할 수 있다.

#### SFU를 선택한 이유
웹앱 환경에서 실시간 오디오 스트리밍 기능을 구현하기 위해 WebRTC를 사용하였다. 그중 발표자 1명의 음성을 다수의 청중에게 전달하는 1 대 N 구조에 적합하다고 판단하여 SFU 방식을 선택하였다.

#### WebRTC를 통한 실시간 음성 스트리밍
핏 프로젝트는 Kurento Media Server를 미디어 중계 서버로 사용하는 WebRTC 기반의 실시간 음성 스트리밍 구조로 구현했다.

발표자 한 명의 음성을 여러 명의 청중에게 전달해야 하는 서비스였기 때문에, 브라우저끼리 직접 연결하는 Mesh 방식은 참가자가 늘어날수록 발표자가 유지해야 하는 Peer Connection의 수도 증가하는 문제가 있다.

그래서 모든 미디어를 Kurento를 통해 중계하는 1 대 N 구조를 선택했다.

이 구조에서는 발표자가 Kurento와 하나의 Peer Connection만 유지하고, Kurento가 발표자의 미디어를 여러 청중에게 전달하기 때문에 Mesh 방식에 비해 발표자 클라이언트의 부담을 줄일 수 있다고 판단했다.

**시그널링은 STOMP/WebSocket**, **미디어 전송은 WebRTC(SRTP)**, **미디어 중계는 Kurento**가 담당하도록 역할을 분리하여 기능을 구현했다.

이를 통해 브라우저 간의 다수 Peer Connection을 직접 관리하지 않아도 되었고, 발표자는 참가자 수와 관계없이 Kurento와 하나의 Peer Connection만 유지하도록 구성할 수 있었다.

또한 시그널링과 실제 미디어 전송 경로를 분리하여 각각의 역할을 명확하게 관리할 수 있도록 구성했다.

##### 구현 흐름
먼저 브라우저가 SDP Offer를 생성하면 STOMP/WebSocket 기반의 시그널링 서버를 통해 Kurento로 전달한다.

Kurento는 SDP Offer를 처리한 후 SDP Answer를 생성하여 브라우저로 반환하고, 이를 통해 미디어 세션 정보를 협상한다.

이후 브라우저와 Kurento는 각각 ICE Candidate를 수집하고 시그널링 서버를 통해 교환한다.

ICE를 통해 통신 가능한 네트워크 경로가 결정되면 DTLS 협상 등을 거쳐 WebRTC 연결이 수립되고, 실제 오디오 미디어는 SRTP를 통해 전송된다.

서비스에서는 발표자가 입장하면 Kurento에 발표자용 `WebRtcEndpoint`를 생성하고, 청중이 입장할 때마다 청중용 `WebRtcEndpoint`를 생성한다.

이후 Kurento 내부에서 발표자의 `WebRtcEndpoint`와 각 청중의 `WebRtcEndpoint`를 연결하여 발표자의 음성이 여러 청중에게 전달되도록 구현했다.

#### 용어 정리
| 용어                   | 뜻                                                                                               |
| -------------------- | ----------------------------------------------------------------------------------------------- |
| **SDP Offer/Answer** | 연결 협상을 위해 코덱, 미디어 유형, 전송 및 보안 정보 등을 담아 주고받는 텍스트                                                 |
| **ICE Candidate**    | 통신에 사용할 수 있는 IP 주소와 포트의 후보 정보                                                                   |
| **STUN**             | NAT 환경의 클라이언트가 외부에서 보이는 자신의 IP 주소와 포트를 확인하기 위해 사용하는 서버                                          |
| **TURN**             | 직접적인 미디어 통신이 어려울 때 미디어를 대신 중계하는 릴레이 서버                                                          |
| **SFU**              | Selective Forwarding Unit. 수신한 미디어 스트림을 합성하지 않고 필요한 참가자에게 전달하는 방식                               |
| **시그널링 서버**          | SDP와 ICE Candidate 등의 정보를 교환하기 위한 서버. WebSocket, STOMP 등을 사용할 수 있으며 실제 미디어는 시그널링 서버를 통해 전달되지 않음 |

### Kurento
Kurento는 WebRTC 기반의 실시간 미디어 애플리케이션을 구축할 수 있도록 지원하는 오픈소스 미디어 서버이다.

오디오와 비디오 스트림의 전달, 믹싱, 녹화 등의 기능을 Media Pipeline을 통해 구성할 수 있다.

핏 프로젝트에서는 Kurento의 `WebRtcEndpoint`를 연결하여 발표자의 오디오 스트림을 여러 청중에게 전달하는 **SFU 방식의 1 대 N 미디어 중계 구조**로 사용하였다.

#### Kurento를 사용한 이유
Kurento와 mediasoup가 가장 유력한 선택지로 남았다. Kurento는 Java 기반 API를 제공하지만, 당시에는 업데이트와 유지보수가 비교적 활발하지 않았다.

반면 mediasoup는 커스터마이징의 자유도가 높고 많이 사용되는 기술이었지만, JavaScript 기반으로 제공되어 Java에 익숙한 팀원들이 단기간에 구축하기에는 어려움이 있을 것으로 판단했다.

PM으로부터 테스트 완료까지 1주일의 시간이 주어졌기 때문에, 팀 회의를 통해 익숙한 Java 환경에서 빠르게 구축하는 것을 우선하기로 결정했고 Kurento를 미디어 서버로 선택했다.

### Coturn
Stun, Turn 서버를 제공하는 대표적인 오픈소스 프로젝트이다. Stun서버는 자신의 공인 IP와 포트를 확인하는 역할을 하고, 직접 역결이 불가능한 경우 Turn 서버가 미디어를 중계하여 연결을 보장한다.

#### NAT
NAT는 사설망의 사설 IP주소를 공인 IP 주소로 변환해주는 기술이다. 주로 공유기나 방화벽에서 사용되며, 사설망 내부 여러 장치가 하나의 공인 IP로 인터넷과 통신활 수 있도록 한다. 덕분에 IPv4 주소를 절약하고, 내부 네트워크를 외부로부터 숨겨 보안성을 높일 수 있다.

IPv6는 주소 공간이 매우 넓어서 각 장치가 공인 IP를 가질 수 있게 설계되었고 IPv4는 주소 부족 문제 때문에 대부분 사설 IP와 NAT를 사용하는 구조가 되었다.

```
PC
192.168.0.10
    ↓
공유기 NAT
    ↓
123.123.123.123
```
외부 인터넷은 192.168.0.10를 모르고 123.123.123.123만 보게 된다.

#### 사용이유
WebRTC는 NAT 환경에서 P2P 연결이 실패할 수 있기 때문에 STUN/TURN 서버가 필요했다. Coturn은 STUN과 TURN 기능을 모두 제공하는 대표적인 오픈소스 프로젝트였고 무료로 사용할 수 있어 도입했다. 그래서 배포 환경에서 스트리밍이 가능하게 Coturn을 사용했다.

- **STUN 서버**: 클라이언트가 “내 공인 IP가 뭐냐”를 알아내는 서버.
- **TURN 서버**: P2P로는 연결이 안 될 경우, 미디어를 중계해 주는 서버.

물론 모바일 데이터망이 Wi-Fi보다 STUN 성공률이 높은 건 맞지만, 통신사망도 CGNAT 환경이기 때문에 NAT 트래버설이 100% 보장되진 않는다. UDP hole punching이 실패하는 경우가 있어서, WebRTC는 항상 TURN 서버를 fallback 경로로 두는 게 안정적이다.

##### IP
IP 주소는 네트워크에서 장치를 식별하기 위한 주소이다.
현실 세계의 주소화 비슷하다. (서울시 강남구, 192.168.0.10)

##### 공인 IP
인터넷 전체에서 유일한 주소이다. ISP(KT, SKT, LG 등) 또는 클라우드 사업자가 할당한다. AWS EC2에 동적 IP를 붙이면 공인 IP가 된다. 인터넷 어디서든 접근 가능하다.
```
52.78.xxx.xxx
13.125.xxx.xxx
```

##### 사설 IP
내부 네트워크에서만 사용하는 주소이다. 인터넷에서는 접근할 수 없다.
집 공유기에서 흔히 보이는 주소이다.
```
192.168.x.x
10.x.x.x
172.16.x.x ~ 172.31.x.x
```

##### IPv4
현재 가장 많이 사용하는 IP 체계이다. 192.168.0.1와 같은 모양이며 32비트 주소로 2^32로 약 43억 개가 존재한다. 인터넷 사용자, 모바일, IoT, 클라우드 등이 늘어나면서 43억 개로는 부족해졌으며, 그래서 NAT를 사용하게 되었다.

##### IPv6
IPv4를 대체하기 위해 만든 차세대 IP이다. 2001:db8::1와 같은 모양이며 128비트 주소로 2^128로 사실상 무한대 수준이다.

###### IPv4 vs IPv6
|항목|IPv4|IPv6|
|---|---|---|
|길이|32비트|128비트|
|주소 수|약 43억|사실상 무한|
|NAT 필요|많음|거의 불필요|
|표기|192.168.0.1|2001:db8::1|

##### 브로드캐스트
같은 네트워크에 있는 모든 장치에게 메세지를 보내는것이다.
```
"192.168.0.xxx 전부 들어!"
```
대표적인 사례로는 ARP가 있다. "192.168.0.10 가진 사람 누구야?"라고 네트워크 전체에 외치면 당사자가 응답을 하는 구조이다.

###### 브로드캐스트는 라우터를 넘지 못한다.
브로드캐스트는 인터넷 전체로 가지 않는다. 라우터를 넘지 못하며, 브로드캐스트 범위는 같은 네트워크(서브넷) 내부이다.

##### 서브넷
네트워크를 작은 단위로 나눈것이다.
```
192.168.0.0/24 이라면

192.168.0.1
~
192.168.0.254
까지 같은 네트워크이다.
```

##### 라우터
다른 네트워크로 패킷을 전달하는 장비이다.
```
내 집 네트워크
↓
공유기
↓
인터넷
↓
AWS 서버
```
여기서 공유기가 라우터 역할도 한다.

##### 게이트웨이
현재 네트워크 밖으로 나갈 때 거치는 출입구이다. 보통 192.168.0.1 같은 공유기 주소이다.

##### VPC
AWS에서 제공하는 가상의 사설 네트워크이다. AWS 안에 자신이 만든 회사 네트워크라고 할 수 있다. 예를 들어 아래와 같이 구성할 수 있다.
```
VPC
├─ Public Subnet
├─ Private Subnet
├─ Route Table
├─ Security Group
```

###### Public 서브넷
인터넷과 직접 통신 가능한 네트워크이다.
```
인터넷
↓
Internet Gateway
↓
Public Subnet
↓
EC2
```
외부에서 접근 가능하다. 웹서버를 둔다.

###### private 서브넷
인터넷에서 직접 접근 할 수 없다.
```
인터넷
X

Private Subnet
↓
DB
```
보통 RDS, Redis, 내부 API를 둔다.

###### private 서브넷은 인터넷이 어떻게 나가는가
NAT Gateway를 사용한다. 업데이트나 패키지 설치는 가능하다. 외부에서 직접 들어오는 건 안된다.
```
Private EC2
↓
NAT Gateway
↓
Internet
```

##### NAT 환경에서 STRUN이 필요한 이유
브라우저가 알고 있는 주소는 대부분 사설 IP이다. 상대방은 그 주소로 접근할 수 없기 때문에 STUN 서버를 통해 NAT가 변환한 공인 IP와 포트를 확인하고 ICE Candidate로 교환한다. 그래도 연결이 안되는 NAT 환경에서는 TURN 서버가 미디어를 중계한다.

##### 방화벽
네트워크 트래픽을 허용하거나 차단하는 보안 장치(소프트웨어)이다.
예를 들어 아래와 같은 규칙을 설정한다.
```
내 서버
↓
80 포트 (HTTP) 허용
443 포트 (HTTPS) 허용
22 포트 (SSH) 차단
```

###### AWS 방화벽
AWS에서는 보통 두가지를 이야기 한다.
1. 보안 그룹: 인스턴스 수준 방화벽이며, 허용 규칙만 설정하고 stateful하게 허용 규칙만 통과되면 응답을 한다.
2. 네트워크 ACL: 서브넷 수준의 방화벽이다. 허용, 거부 설정 둘 다 가능하며, stateless하게 요청 응답 허용 규칙을 설정할 수 있다.

### WebSocket과 STOMP를 사용한 이유
WebRTC 연결 과정에서는 SDP Offer/Answer와 ICE Candidate를 실시간으로 교환해야 한다. HTTP Polling 방식은 주기적으로 요청을 보내야 하므로 불필요한 요청이 반복해서 발생할 수 있기 때문에, 양방향 통신이 가능한 WebSocket을 사용했다.

순수 WebSocket만으로도 구현할 수 있지만, 메시지의 목적지와 이벤트를 구조적으로 분리하고 싶었다. Spring에서 제공하는 STOMP를 사용하면 `@MessageMapping`을 기반으로 Controller와 유사한 방식으로 메시지를 처리할 수 있어 유지보수와 흐름 추적에 용이하다고 판단했다.

요약하면, SDP Offer/Answer, ICE Candidate, 채팅 메시지 등을 목적지별로 구분하여 처리할 수 있었고, Spring MVC와 유사한 방식으로 개발할 수 있어 생산성을 높일 수 있었다.


### 실시간 음성 스트리밍 테스트의 어려움
WebRTC 기반의 실시간 음성 스트리밍을 테스트하는 과정에서 지연 시간을 어느 정도까지 허용할 것인지 판단하는 데 어려움이 있었다. 실제 발표자의 모습을 보면서 음성을 청취할 경우 영상으로 보이는 동작과 전달되는 음성 사이의 지연이 크게 느껴지면 사용자 경험에 영향을 줄 수 있다고 판단했다.

이에 커뮤니티를 통해 설문조사를 진행했고, 약 0.5~0.6초 정도의 지연은 크게 불편하지 않은 수준이라고 판단했다. 이를 바탕으로 예상 동시 청취 인원인 30명을 기준으로 약 0.5~0.6초 이내의 지연 시간을 목표로 테스트를 진행했다.

먼저 테스트 계정 30개와 각 계정에 필요한 인증 토큰을 준비했다. 팀원은 청취자 역할의 브라우저를 여러 개 실행하고, 나는 발표자 역할의 브라우저를 실행하여 테스트를 진행했다.

테스트 과정에서는 Wireshark를 이용해 UDP 패킷의 송수신 여부와 패킷 손실 여부를 확인하고, Chrome의 WebRTC 통계 분석 도구를 이용해 미디어 전송 상태와 지연 관련 지표를 확인했다.

테스트 결과 약 0.4~0.5초 수준의 지연이 확인되어 설정한 목표 범위 내에서 동작하는 것을 확인했다.

### ConcurrentHashMap을 사용한 이유
발표방 정보를 서버 메모리에서 관리하기 위해 `ConcurrentHashMap`을 사용했다. 발표자와 청중이 입장하거나 퇴장하는 과정에서 여러 스레드가 동시에 방 정보에 접근할 수 있기 때문에, 일반적인 `HashMap` 대신 `ConcurrentHashMap`을 사용하여 동시 접근에 안전하도록 구성했다.

해당 데이터는 영속적으로 보관할 필요가 없다고 판단했다. 발표자가 퇴장하면 방도 함께 종료되는 구조였기 때문에 서버가 재시작되어 데이터가 사라지더라도 방과 관련된 자원을 해제한 후 다시 생성하면 됐다.

또한 발표자가 존재해야 청중도 존재할 수 있다는 조건을 두었다. 발표자가 퇴장하거나 서버가 재시작된 상황에서 청중의 세션 정보만 별도로 유지하며 발표자의 재접속을 기다리기보다는, 기존 방을 종료하고 필요할 때 새로운 방을 생성하는 것이 서비스 구조에 더 적합하다고 판단했다.

다만 현재 구조는 단일 서버를 전제로 한다. 시그널링 서버를 여러 대로 확장할 경우 각 서버의 메모리에 저장된 방 정보를 서로 공유할 수 없기 때문에, Redis와 같은 외부 저장소를 이용해 공유가 필요한 세션 상태를 관리하는 방식을 고려해야 한다.

#### ConcurrentHashMap 참고
`ConcurrentHashMap`을 사용한 이유는 방 정보에 대한 여러 스레드의 동시 접근을 안전하게 처리하면서도, 방 자체는 서버가 실행되는 동안에만 유지되는 일시적인 상태로 관리하고 싶었기 때문이다.

발표자가 퇴장하거나 서버가 재시작되면 관련 자원을 해제하고 방을 종료하며, 이후 필요한 경우 새로운 방을 생성하는 구조로 설계했다.
