# AWS 정지

---

## 📄 본문
### AWS 정지
환경 설정을 서브모듈을 통해 분리하여 관리하고 있었다. 민감 정보는 {St} 형태의 환경 변수로 관리된다는 전제 하에 메인 브랜치에 별도의 검증 절차 없이 반영되고 있었다. 이 과정에서 팀원이 AWS Acess Key를 실수로 커밋했다가 다시 환경 변수 형태로 수정하는 일이 있었고, 해당 커밋 이력이 Git 히스토리에 남으면서 AWS 보안 정책에 의해 계정이 위험 상태로 판단되어 정지되었다.
- 환경 변수 관리에 대한 검증 및 리뷰 체계 X
- 민감 정보 커밋에 대한 차단 장치 X
- 서브 모듈 특성상 변경 이력이 상대적으로 눈에 띄지 않았던 점

### AWS Access Key
AWS API를 호출하기 위한 자격 증명이다. IAM 사용자의 ID/PW 같은 개념인데, Access Key ID와 Secret Access Key가 노출되면 AWS 콘솔 로그인 없이도 API 를 통해 리소스를 생성하거나 삭제할 수 있다. 공격자가 EC2를 수백 대 띄우거나 S3 데이터를 조회할 수 있기 때문에 매우 위험하다.

#### 정지 이유
AWS는 Github 같은 공개 저장소를 지속적으로 스캔한다. 노출된 Access Key가 발견되면 자동으로 비활성화하거나 계정을 위험 상태로 판단하여 제한 조치를 할 수 있다. 핏 프로젝트에서는 Git 히스토리에 남아있던 키가 탐지되어 계정이 정지되었다.

### 현재 관리
Access Key 자체를 사용하지 않는 방향으로 개선했다. EC2 내부에서는 IAM ROLE을 부여하여 임시 자격 증명을 사용하도록 변경했고, 애플리케이션 설정은 환경 변수 또는 AWS Secrets Manager를 사용하는 방향을 검토했다.

### 환경 변수 노출
환경 변수도 결국 노출된다. 환경 변수가 Git에 올라가지 않을 뿐이지 서버에 존재하는 값이다. 따라서 최소 권한 원칙을 적용하고, 운영 서버 접근 권한을 제한하여, 필요 시 Secrets Manager 같은 별도 비밀 관리 서비스를 사용하는 것이 좋다.

### 서브 모듈
Git SubModule은 다른 Git Repository를 현재 Repository안에 포함 시키는 기능이다. 핏 프로젝트는 환경 설정 저장소를 별도 Repository로 분리해서 관리하기 위해 사용했다. 메인 Repository에는 실제 설정 파일이 아니라 특정 커밋 위치만 참조하는 방식이다.

#### 서브모듈 사용 이유
민감한 설정 파일을 애플리케이션 코드와 분리하기 위해 사용했다. 코드 저장소 권한과 설정 저장소 권한을 분리할 수 있고, 설정 변경 이력을 별도로 관리할 수 있다는 장점이 있었다.

### 사고 방지
세 가지를 적용해야한다고 판단된다.
1. 코드 리뷰 과정에서 환경 변수나 민감 정보 변경 여부를 확인하는 체크리스트를 운영해야한다.
2. Github Secret Scanning 같은 도구를 통해 커밋 단계에서 차단해야한다.
3. AWS Access Key 대신 IAM ROLE과 임시 자격 증명을 사용하여 키 자체를 최소화한다.
