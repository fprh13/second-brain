# 혼잡도 계산

---

## 📄 본문
### 원인
미리담기라는 말에 대한 오차에서 발생했다. 유비쿼터스언어가 확립되지 않았다. PM 디자이너, 프론트, 백엔드에서 해당 미리담기 기능은 여러가지로 불렸다. "시간표 기능", "스케줄 기능", "미리담기 기능" 등 으로 불리며, 미리 담기를 한 세션은 무조건 세션 당일에 들어야하는 세션으로 치부되었다. 해당 미리담기 기능은 자신의 대략적인 일정을 시간표로 확인하기 위한 기능으로 어떠한 객관적인 지표가 되지 않는다. 하지만, 해당 미리담기를 한 인원을 대상으로 데이터를 집계하여 혼잡도를 계산하게 되어 신뢰할 수 없는 데이터를 제공하게 되었다.

### 세션 혼잡도 인원 카운팅 문제
프로젝트에서 혼잡도 분석 기능의 정확도를 높이기 위해 미리담기 데이터를 사용하는 방식에서 실제 사용자 행동을 반영하는 방식으로 개선했다.

초기에는 세션 혼잡도를 계산할 때 미리담기한 인원을 기준으로 분석하고 있었다. 하지만 프로젝트의 핵심 컨셉은 사용자가 자유롭게 세션을 이동하고 오디오 채널을 변경하며 청취하는 서비스였다. 즉 미리담기를 했다고 해서 실제로 해당 세션을 듣는 것은 아니다.

예를들어, XX세션을 미리담기한 사람이 30명일 때, QR체크인을 한사람이 20명이고, 그중 실제로 XX 세션을 듣는 사람이 8명이라면 혼잡도는 8명을 기준으로 계산이 되어야한다. 기존 방식은 서비스의 실제 사용 패턴을 반영하지 못한다고 판단한다.

그래서 혼잡도 계산 기준을 변경하자고 제안했다. 먼저 세션과 오디오 채널을 1:1로 매핑하도록 설계했다. 사용자가 QR 체크인을 하면 Redis에 사용자 식별자를 저장하고, 이후 사용자가 특정 오디오 채널에 접속하면 해당 사용자의 현재 청취 채널을 Redis에 함께 기록했다.

혼잡도를 계산할 때는 **QR 체크인을 완료한 사용자 중 현재 해당 세션의 오디오 채널을 청취하고 있는 사용자만 집계하도록 구현했다.** 

이를 통해 신뢰할 수 있는 혼잡도 데이터를 활용할 수 있게 되었고, 서비스의 핵심 컨셉인 자유로운 세션 이동까지 반영한 기능으로 개선할 수 있었다.


### 혼잡도 계산
#### 기존 접근 방식 
QR 입장 인원의 세션 미리담기 정보를 해당 세션의 현재 청취자로 취급하여 계산한다.
`혼잡도 = (QR, 미리담기 인원 / 기준 인원) X 100`
실제 오디오 채널 청취자 수와 무관환 혼잡도를 제공

#### 개선된 접근 방식
세션별 청취자 수를 집계하여 혼잡도를 계산
`혼잡도 = (실제 청취자 수 / 기준 인원) X 100`
예측 값이 아닌 실제 세션장의 청취자 수를 기반으로 혼잡도를 제공

#### 퍼센트
0~40: 여유
40~80: 적정
80 이상: 혼잡
