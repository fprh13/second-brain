# 과거 커밋 조회 및 복원

---

## 📄 본문

### 개념

Git은 각 커밋에 프로젝트의 파일 상태를 기록한다. 따라서 특정 커밋으로 이동하여 당시의 코드를 확인하거나 실행할 수 있다.

대표적인 활용 사례:

- JPA/Querydsl 쿼리 최적화 전후 성능 비교
    
- 이전 버전에서 발생했던 버그 재현
    
- 특정 기능이 추가되기 전의 코드 확인
    
- 라이브러리 업데이트 전후 동작 비교
    
- 과거 커밋의 테스트 실행
    
- 특정 시점의 소스 코드 복원
    

**핵심:** 과거 커밋을 확인하는 것과 현재 브랜치의 이력을 변경하는 것은 다르다.

과거 코드를 확인하는 목적이라면 `git switch --detach` 또는 `git worktree`를 사용한다.

### 관련 Git 명령어 비교

|명령어|역할|사용 목적|
|---|---|---|
|`git log`|커밋 이력 조회|과거 커밋 찾기|
|`git show`|커밋의 변경사항 확인|코드 변경 내용 분석|
|`git switch --detach`|특정 커밋으로 HEAD 이동|과거 버전 실행 및 테스트|
|`git switch <branch>`|브랜치 이동|원래 작업으로 복귀|
|`git worktree add`|별도 작업 디렉터리 생성|이전·이후 버전 병렬 관리|
|`git restore --source`|특정 커밋의 파일 가져오기|일부 파일만 복원|
|`git revert`|기존 커밋을 취소하는 새 커밋 생성|변경사항 되돌리기|
|`git reset`|현재 브랜치의 HEAD 이동|커밋 이력 재설정|

> 단순히 과거 코드를 확인하려는 경우 `git reset --hard`를 사용하는 것은 권장하지 않는다. 현재 브랜치의 위치와 작업 상태가 변경될 수 있기 때문이다.

---

### 1. 과거 커밋 조회

현재 브랜치의 커밋 이력을 확인한다.

```
git log --oneline
```

모든 브랜치의 커밋 관계를 그래프로 확인한다.

```
git log --all --oneline --graph --decorate
```

특정 파일의 변경 이력 확인:

```
git log --oneline -- src/main/java/com/example/EstimateRepository.java
```

특정 커밋의 변경사항 확인:

```
git show <commit-hash>
```

특정 커밋의 파일 내용 확인:

```
git show <commit-hash>:src/main/java/com/example/EstimateRepository.java
```

커밋으로 이동하지 않아도 과거 코드를 조회할 수 있다.

### 2. 특정 커밋으로 이동 — Detached HEAD

**사용 상황:** 과거 버전의 프로젝트를 실행하거나 테스트하고 싶을 때.

예시 커밋 이력:

```
a1b2c3d  ← JPA 쿼리 최적화 이전
e4f5a6b  ← Querydsl 조회 최적화 적용
f7a8b9c  ← 현재 최신 커밋 (HEAD)
```

#### STEP 1. 현재 상태 확인

```
git branch --show-current
git status
git log -1 --oneline
```

현재 브랜치 이름과 커밋을 기록해 둔다.

미커밋 변경사항이 있다면 먼저 커밋하거나 Stash로 보관한다.

#### STEP 2. 과거 커밋으로 이동

```
git switch --detach a1b2c3d
```

특정 커밋으로 직접 HEAD를 이동한다.

```
이동 전:

a1b2c3d ── e4f5a6b ── f7a8b9c
                            ↑
                     feature/estimate
                            HEAD

이동 후:

a1b2c3d ── e4f5a6b ── f7a8b9c
    ↑                       ↑
   HEAD              feature/estimate
```

브랜치 자체가 이동하는 것은 아니다.

HEAD만 과거 커밋을 직접 가리키며, 현재 작업 디렉터리는 해당 커밋의 파일 상태로 변경된다.

이를 **Detached HEAD 상태**라고 한다.

#### STEP 3. 이전 버전 실행

```
git status
git log -1 --oneline

./gradlew test
```

필요하다면 Spring Boot 애플리케이션을 실행한다.

```
./gradlew bootRun
```

이 상태에서 과거 버전의 기능, API 동작 및 성능을 확인할 수 있다.

#### STEP 4. 기존 브랜치로 복귀

```
git switch feature/estimate
```

현재 브랜치가 최신 커밋을 가리키고 있다면 해당 상태로 돌아온다.

```
git log -1 --oneline
git status
```

**주의:** Detached HEAD 상태에서 새로운 커밋을 생성했다면 브랜치 이동 전에 해당 커밋을 보존할 브랜치 또는 태그를 만들어야 한다. 또한 과거 버전 실행 중 생성한 파일이나 변경사항 때문에 브랜치 전환이 막힐 수 있다.

---

### 3. Worktree로 과거·현재 버전 비교

**사용 상황:** JPA 쿼리 최적화 전후를 여러 번 비교하거나, 이전 버전과 현재 버전을 각각 실행하고 싶을 때.

`git switch --detach`는 하나의 작업 디렉터리에서 버전을 전환하는 방식이다.

반면 Worktree는 **서로 다른 커밋의 파일 상태를 별도 디렉터리에 동시에 유지**할 수 있다.

#### STEP 1. 커밋 확인

```
git log --oneline
```

예시:

```
a1b2c3d  JPA 쿼리 최적화 이전
e4f5a6b  JPA 쿼리 최적화 이후
```

#### STEP 2. Worktree 생성

기존 프로젝트 루트에서 실행한다.

```
git worktree add --detach ../project-before a1b2c3d

git worktree add --detach ../project-after e4f5a6b
```

생성 결과:

```
Repository/
├── project/          ← 기존 작업 디렉터리
├── project-before/   ← 최적화 이전 코드
└── project-after/    ← 최적화 이후 코드
```

모두 동일한 Git 저장소에 연결되어 있지만, 각각 독립적인 작업 디렉터리를 가진다.

#### STEP 3. 이전 버전 실행

```
cd ../project-before

./gradlew test
./gradlew bootRun
```

최적화 이전 버전의 테스트 및 성능 측정을 수행한다.

#### STEP 4. 이후 버전 실행

이전 서버를 종료한 뒤 원래 프로젝트 기준 경로로 이동하거나, 각 Worktree의 터미널을 별도로 사용한다.

```
cd ../project-after

./gradlew test
./gradlew bootRun
```

동일한 조건으로 최적화 이후 버전을 측정한다.

두 서버를 동시에 실행하려면 포트, DB, Redis 등의 리소스 충돌을 방지해야 한다.

#### STEP 5. Worktree 정리

기존 프로젝트 루트로 돌아와 실행한다.

```
git worktree list

git worktree remove ../project-before
git worktree remove ../project-after
```

미커밋 변경사항이 있거나 실행 중인 프로세스가 있다면 먼저 확인한다.

---

### 4. 특정 파일만 과거 버전으로 복원

**사용 상황:** 전체 프로젝트를 과거로 되돌리는 것이 아니라 특정 파일만 이전 버전으로 복원하고 싶을 때.

```
git restore --source=<commit-hash> -- path/to/file
```

예시:

```
git restore --source=a1b2c3d -- src/main/java/com/example/EstimateRepository.java
```

해당 파일의 작업 디렉터리 내용이 지정한 커밋의 버전으로 변경된다.

- 현재 브랜치의 HEAD는 이동하지 않는다.
    
- 다른 파일은 변경되지 않는다.
    
- 복원한 파일의 변경사항은 아직 커밋되지 않은 상태다.
    

복원 결과 확인:

```
git diff
git status
```

실수로 복원했다면 추가 수정이 없는 상태에서 다음처럼 현재 HEAD 버전으로 되돌릴 수 있다.

```
git restore --source=HEAD -- src/main/java/com/example/EstimateRepository.java
```

단, 이 명령어는 해당 파일의 미커밋 변경사항을 덮어쓸 수 있으므로 주의한다.

---

### 5. 과거 코드 확인과 실제 되돌리기의 차이

|목적|추천 명령어|
|---|---|
|과거 커밋 변경사항만 확인|`git show`|
|과거 커밋의 코드 실행|`git switch --detach`|
|이전·이후 버전 동시 관리|`git worktree`|
|특정 파일을 과거 버전으로 복원|`git restore --source`|
|이미 공유한 커밋을 안전하게 취소|`git revert`|
|로컬 브랜치의 커밋 이력 재설정|`git reset`|

단순히 코드를 확인하는 경우와 실제 변경 이력을 수정하려는 경우를 구분하는 것이 중요하다.

### 6. 실무 사례 — JPA 쿼리 최적화 전후 성능 비교

#### 시나리오

카우머치 프로젝트의 공개 견적 목록 조회 API에서 성능 저하가 발생했다.

Querydsl 쿼리 개선 및 인덱스 최적화를 적용했으며, 개선 이전과 이후의 실제 성능을 비교하려고 한다.

#### 권장 흐름

```
1. 최적화 이전·이후 커밋 확인
             ↓
2. Worktree 2개 생성
             ↓
3. 테스트 DB 환경 구성
             ↓
4. 이전 버전 성능 측정
             ↓
5. 이후 버전 성능 측정
             ↓
6. EXPLAIN ANALYZE 및 k6 결과 비교
             ↓
7. 결과 문서화
             ↓
8. Worktree 정리
```

#### 측정 조건

코드가 과거 상태로 돌아갔다고 해서 모든 실행 환경이 과거 상태로 복원되는 것은 아니다.

성능 비교 시 다음 조건을 통제해야 한다.

|항목|확인 사항|
|---|---|
|Commit|최적화 이전·이후 커밋 해시|
|Java/Spring|런타임 및 프레임워크 버전|
|DB|MySQL 버전과 설정|
|데이터|전체 건수 및 데이터 분포|
|인덱스|각 버전의 인덱스 구성|
|API 조건|필터, 정렬, 페이지 크기|
|실행 환경|CPU, 메모리, 컨테이너 자원|
|워밍업|JVM 및 DB 캐시 영향|
|측정|반복 실행, 평균, p95, 처리량|

DB 스키마 변경이나 Flyway 마이그레이션이 포함됐다면 각 버전에서 호환되는 DB 상태를 재현해야 한다.

운영 DB에서 직접 성능 실험을 진행하기보다는 격리된 테스트 환경을 사용하는 것이 좋다.

#### 측정 도구

**EXPLAIN ANALYZE**

- SQL 실제 실행 계획 확인
    
- 인덱스 사용 여부 확인
    
- JOIN 처리 및 실행 시간 분석
    
- 예상 행 수와 실제 행 수 비교
    

**k6**

- HTTP API 응답 시간 측정
    
- p95 및 p99 지연 시간 확인
    
- 초당 요청 처리량 측정
    
- 동시 사용자 부하 테스트
    

쿼리 실행 시간과 HTTP API 응답 시간은 서로 다른 지표이므로 구분한다.

#### 결과 기록 양식

|측정 항목|최적화 이전|최적화 이후|
|---|---|---|
|Commit Hash|||
|DB 인덱스|||
|SQL 실행 시간|||
|HTTP 평균 응답 시간|||
|HTTP p95|||
|처리량(RPS)|||
|EXPLAIN 분석 결과|||

측정값은 반드시 동일하거나 비교 가능한 조건에서 수집한 결과를 기록한다.

## ✏️ 메모

### Detached HEAD란?

일반적으로 HEAD는 브랜치를 가리키지만, Detached HEAD 상태에서는 특정 커밋을 직접 가리킨다.

```
git switch --detach <commit-hash>
```

단순한 코드 확인이나 테스트 목적이라면 문제가 없는 정상적인 상태다.

단, 새로운 커밋을 만들고 유지하려면 해당 커밋을 가리키는 브랜치를 생성하는 것이 좋다.

### 과거 커밋 확인 시 reset을 사용하지 않는 이유

```
git reset --hard <commit-hash>
```

이 명령어는 현재 브랜치의 HEAD를 과거 커밋으로 옮기고 Index 및 작업 디렉터리까지 재설정한다.

미커밋 변경사항이 사라지거나 브랜치 이력이 의도치 않게 변경될 수 있다.

따라서 단순 확인 목적이라면 `git switch --detach`가 더 적합하다.

### 빠른 명령어 요약

```
# 커밋 이력 확인
git log --oneline

# 과거 커밋으로 이동
git switch --detach <commit-hash>

# 원래 브랜치 복귀
git switch <branch-name>

# 이전 버전 Worktree 생성
git worktree add --detach ../project-before <commit-hash>

# Worktree 제거
git worktree remove ../project-before

# 특정 커밋의 파일 확인
git show <commit-hash>:path/to/file
```

### 개인 학습 기준

- 일회성 과거 코드 확인: `git switch --detach`
    
- 반복적인 전후 비교: `git worktree`
    
- 파일 하나만 복원: `git restore --source`
    
- 미커밋 변경사항 임시 보관: `git stash`
    
- 공유된 변경사항 취소: `git revert`
